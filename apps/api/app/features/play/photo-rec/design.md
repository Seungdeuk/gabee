# 찰칵! 탐정단 가비 추천 설계 (v1, 2026-11-19)

상태: 설계 초안(사용자 승인 전). 코드는 아직 건드리지 않았다. 이 문서 안의 **[내 결정]** 은 사용자가 정한 것이 아니라 에이전트가 정한 것이므로 읽고 고쳐 주세요. **[확인]** 은 사용자 답이 필요한 것이다.

## 1. 무엇을 왜
가족 놀이터 "찰칵! 탐정단"은 내는 사람이 사진 한 장을 골라 확대할 위치·질문·보기·정답을 정해 올리고 가족이 맞힌다. 사진을 고르고 질문을 짓는 일이 번거롭다. 이게 뭐게·골든벨의 "가비 추천"처럼, **가비가 사진과 질문·보기·정답·확대 위치를 같이 골라 주고 가족은 마음에 들면 그대로, 아니면 고쳐서 내게** 한다. 사진은 가족 앨범(가족 전체방에 올라온 사진)에서 고르고, 모자라면 흔한 사진으로 채운다.

## 2. 사용자가 정한 것
- 사진은 **가족 앨범**에서 고르고, 질문·보기는 그 사진에 관련해서 만든다. 가정통신문·알림장 같은 **공문서가 아닌 사적 사진**만 쓴다.
- 데이터가 부족하면 **흔한 사진**으로 채운다.
- 방식 **A**: 후보 사진(공문서 아닌 것으로 확인된 사진)에서 문제를 만들되, 사진 내용을 AI에 보내지 않는 문제(촬영 월·일정 맞추기)는 항상 가능하고, 내용 질문은 **가족이 AI에 동의했을 때만** AI가 사진을 한 번 보고 만든다.
- **한 사진으로 문제를 두 번 내지 않는다**(이후 사용자가 바꿈: 가족 사진·공통 사진 모두 보낸 뒤 **14일**이 지나면 다시 나올 수 있다. 사진당 문제는 하나라 같은 문제가 다시 나온다).
- 한 번에 만드는 문제는 **3개**(5개 아님). 같은 날 다시 열어도 같은 3개이고, 다 쓰면 직접 내기로 간다.
- 흔한 사진 문제도 **문제 내기 점수**를 받는다(하루 한도는 기존 그대로).
- 문제 종류: ① **몇 월에 찍었을까**(일은 어려우니 월만) ② **어느 일정 때 찍었을까**(장소 포함) ③ **사진 내용 질문**(AI 동의 가족만). **대화를 읽어 유추하는 문제는 나중에** 다른 문제로 한다. 사진 속 사람을 맞히는 문제는 하지 않는다(얼굴 태그·인식 없음).
- 저장 테이블은 **사진 문제 보관용 한 개**. 가족(`group_id`)·출처(`source`) 칸으로 흔한 사진과 가족 앨범을 구분하고, 나머지 칸은 같다.
- 흔한 사진은 **전체 가족이 같은 풀을 공유**한다(`group_id` 로 가르지 않음). 풀은 **기본 시드 50장**이고, 자동 보충(2차)이 붙으면 **매일 +3**씩 늘어난다. 가족끼리는 독립이지만 같은 풀에 모두 접근한다.
- 카드 3개는 **가족 사진 1~2개 + 흔한 사진 1~2개**로 섞는다(가족 사진 후보가 2장 이상이면 2개, 1장이면 1개, 0장이면 0개이고 나머지는 흔한 사진이라 흔한 사진은 1~3개). 가족 사진이 많아도 흔한 사진이 최소 1개 들어간다.
- 흔한 사진의 **질문·보기는 AI가 한 번 만들고 사람(사용자)이 검수**한다. 처음 **시드 50장은 사용자가 검수**한다.
- 이미지는 **DB에 저장해도 된다**(운영 파일 저장소를 새로 정하지 않아도 되게).
- 출제자가 보내기 전에 직접 보고 고칠 수 있고 별로면 안 쓰면 되므로, 자동 보충분은 사람 검수 없이 간다(안전장치는 6절).
- 사진 사이트(출처·약관)는 **나중에 확인**한다.

## 3. 목표 / 아닌 것
목표: 가족이 사진 고르기·질문 짓기 부담 없이 탐정단을 낸다. 문제에 우리 가족의 시간·일정이 묻어난다. 문서·개인정보가 AI로 나가지 않는다.
아닌 것(이번 범위 밖): 대화로 유추하는 문제, 사진 속 인물 식별, 먼저 준비(백그라운드), 사진 사이트 자동 가져오기(후속 2차), 신고 기능, 예전 사진 재판별.
실패로 보는 경우: 공문서·민감 사진이 후보에 섞임, 정답이 틀린 문제가 그대로 노출됨, AI 동의 없는 가족의 사진이 외부로 나감, 같은 사진이 14일 안에 두 번 문제가 됨.

## 4. 이미 있는 것(조사 결과, `release/1.3` 기준)
- **사진 판별 상태**: 팀원이 만든 `chat_photo_checks`(PR #409·#411, 마이그레이션 `d7a41c9e5b02`·이력 표)에 가족 전체방 사진마다 `pending·photo·document·unsure·failed·excluded`(올린 사람이 타임라인에서 뺀 사진) 가 저장된다. 자동 판별은 `photo` 를 만들지 못하고(D-13), `photo` 는 올린 사람이 "일반 사진으로 확인"해야 된다. `confirmed_photo_ids(db, group_id, attachment_ids)` 가 `photo` 인 것만 돌려준다(fail-closed). **예전 사진은 줄이 없어 처음엔 모두 빠지고 재판별은 없다.**
- **사진 메타**(`message_attachments`): `taken_at`(촬영 시각 UTC, EXIF 또는 앱 값, 없으면 NULL), `batch_id`, `width`·`height`, `thumb_path`, 경로 등. EXIF 위치는 저장 전에 버린다. 사진 내용 라벨·AI 설명·OCR 글자는 저장하지 않는다(AI 설명 저장 여부는 사진 담당 팀원에게 확인 필요).
- **판별 도우미**: `ingest/photo_judge.to_judge_jpeg`(긴 변 1024px JPEG, EXIF 제거)를 AI에 보낼 사진 만들기에 재사용한다. 외부 AI 전송은 `ai_guard.is_enabled(db, group_id)`(가족 AI 동의)에서만.
- **탐정단 저장**(`play_photos`): `play_id`·`image_path`·`source`(1 가족 앨범, 2 내 폰)·`zoom`(4·6·8·16·32)·`box_x`·`box_y`·`question`(20자)·`options`(JSON 2~4개)·`answer`(보기 순서 비트 글자 "0100")·`comment`. 앱 `PhotoCreateScreen.js` 는 가족 앨범 고르기를 서버 연결 시 숨긴 상태다.
- **추천의 틀**: `quiz_rec.py`·이게 뭐게 추천(PR #459)과 같은 모양 — `ai_guard.run(feature, cache_key, call, cache_until)`, `GET /play/.../recommendations` 가 `{state, items}`, 한도 사용자 3·가족 5·쿨다운 5초, 가족 캐시 오늘 자정까지, 이미 낸 것은 30일 숨김, 공동 일정은 `shared_events`(골든벨과 같은 재료).

## 5. 접근과 선택
1. **A (채택)**: 후보 = `photo` 확인 사진. 모든 후보에 AI 없는 문제(월·일정) 가능, 동의 가족은 AI 내용 질문 추가, 모자라면 흔한 사진.
2. B 메타 질문만 — 사진 관련 질문이 아니라 **채택 안 함**.
3. C 내용 질문만(동의 가족) — 동의 안 한 가족은 흔한 사진뿐이라 **채택 안 함**.
흔한 사진: 전체 가족이 공유하는 풀(시드 50장 + 매일 +3)에서 사용자 id·날짜 시드로 1~3개를 고른다(사용자). 이미지 보관은 DB(bytea) [내 결정: 컬럼 형식], 운영 파일 저장소 대신.

## 6. 설계
**하루 카드 3개 구성**(서버)
1. 후보 사진 = 그 가족 전체방 사진 중 `confirmed_photo_ids` 에 든 것, 그 가족이 **최근 14일 안에 문제로 보내지 않은 것**(`play_photos.rec_id` 로 판단. 사용자 결정으로 가족 사진의 영구 제외를 풀고 공통 사진과 같은 기간으로 통일, 14일은 10~17일의 가운데라 [내 결정]이고 상수로 조정; 문서·1:1 방 사진은 애초에 없음).
2. 후보에서 **가족 사진 문제를 최대 2개** 고른다(후보가 2장 이상이면 2개, 1장이면 1개, 0장이면 0개) [사용자 결정: 가족 1~2 + 흔한 1~2]. 한 사진에서 만들 수 있는 종류 중 하나만 쓰고, 가족 사진 2개는 가능하면 서로 다른 종류로 고른다 [내 결정]. 사진당 종류 우선순위 [내 결정]: 일정 맞추기 가능 → 일정, 아니면 동의 가족이면 내용 질문 → 아니면 촬영 월.
3. 나머지를 **흔한 사진**(공유 풀, 아래)으로 채운다. 그래서 흔한 사진은 1~3개이고 가족 사진이 아무리 많아도 최소 1개 들어간다(가족 사진 문제가 AI 실패·후보 부족이어도 3개가 보장된다).
4. **구성은 저장하지 않고** 가족·**사용자 id**·한국 시간 날짜를 시드로 한(사람마다 다른 카드가 나와 같은 가족이 미리 본 정답을 덜 알게 한다, 사용자 결정. 같은 가족 4명 안팎이라 겹침은 어쩔 수 없다고 받아들임) 같은 방식(정렬 뒤 시드로 선택)으로 매번 고른다 [사용자 결정 (가)]. 가족 사진과 흔한 사진 모두 이 시드로 고른다. 하루 중 사진이 새로 확인되거나 빠지면 카드가 바뀔 수 있다. "하루 3개로 끝"은 오늘(한국 시간) 이 추천으로 보낸 문제(`rec_id` 가 있는 것)가 3개이면 추천을 끝내고 직접 내기로 가는 것으로 센다.

**문제 종류**
- **촬영 월**(AI 없음): `taken_at` 이 있는 사진만(없으면 올린 날로 대신하지 않고 건너뜀, 오답 방지). 질문 "이 사진은 몇 월에 찍었을까요?", 보기 월 4개(정답 월 + 다른 월 3개), 연·일은 묻지 않는다. 한국 시간 기준.
- **일정 맞추기**(AI 없음): 촬영일(한국 시간)과 **같은 날의 공동 일정**(골든벨과 같은 재료, 부탁에서 생긴 일정 제외)이 정확히 하나일 때만. 일정은 하루짜리라 기간이 아니라 날짜 일치이고, 골든벨의 ±30일·60건 조회는 오늘 기준이라 쓰지 않고 촬영일 기준으로 따로 조회한다(그래서 오래된 사진도 가능) [내 결정]. 일정 제목·장소가 보기 상한(20자)을 넘으면 자르지 않고(뜻이 바뀔 수 있음) 그 일정은 건너뛴다 [내 결정]. 질문 "이 사진은 어느 일정 때 찍었을까요?"(일정에 장소가 있으면 "어디서 찍었을까요?"도 가능), 보기는 정답 일정 + 같은 가족의 다른 일정 제목 2~3개. 같은 날 일정이 둘 이상이면 모호해서 건너뜀. 일정 제목은 AI로 보내지 않는다(서버가 만든다).
- **내용 질문**(AI, 동의 가족만): 사진 한 장을 `to_judge_jpeg` 로 줄여 AI에 한 번 보낸다. 사진 외 가족 정보는 보내지 않는다. AI는 쓸 수 있는 사진인지(`usable`), 질문(20자 이내), 보기 2~4개, 정답, 확대 위치(`box_x`·`box_y`, 0~1)를 돌려준다. 사람 얼굴이 크게 나오거나 글자·서류면 `usable=false`(거부)로 저장해 다시 부르지 않는다. 결과는 사진 단위로 저장해 재사용한다.
- 확대 배율 기본값은 구현자 몫(기본 8배 [내 결정]); 내는 사람이 고칠 수 있다.

**흔한 사진(공유 풀)**
- 흔한 사진은 `group_id` 가 비고 `source` 가 흔한 사진(시드/자동 구분)인 행이다. 전체 가족이 같은 풀을 읽는다.
- **1차(이번 범위)**: **시드 50장**(AI가 질문·보기·정답·확대 위치를 한 번 만들고 사용자가 검수, 이미지는 DB). 풀에서 사용자 id·한국 시간 날짜 시드로 필요한 개수(1~3개)를 고른다 [내 결정: 선택 방식]. 그 가족이 최근 14일에 **보낸** 사진은 뺀다. 보내지 않은 것은 다시 나와도 된다(사용자). 시드 50장이 하루 최대 3개 보내는 가족 하나에 14일 제외를 적용해도 바닥나지 않는다(14일 × 3 = 42 < 50).
- 사용자 결정: 안 쓴 문제가 10~17일 안에 다시 보여도 괜찮다(30일 간격은 지키지 않는다). 자동 보충(2차)으로 풀이 매일 +3 늘면 간격은 자연히 늘어난다.
- 시드 넣기는 마이그레이션이 아니라 별도 시드 스크립트(이미지 폴더 + JSON을 읽어 멱등으로 넣음) [내 결정]. 운영 DB 반영은 DB 담당자.
- **2차(후속, 약관 확인 뒤)**: 그날 처음 열린 요청에서 사진 사이트 API로 3장을 받아 AI로 만들어 같은 표에 쌓는다(풀이 매일 +3)(먼저 준비 아님, 동시 생성 잠금 필요). 안전장치: 검색어를 음식·동물·풍경 같은 일상 소재로 제한, AI가 얼굴·글자·브랜드가 크면 거부. 이미지는 DB에 두고 오래된 것은 지운다. 이 단계도 같은 표에 행만 더한다. **사용자 결정(11/19): 하루 3개를 받아올 때도 그 사진의 질문·보기·정답·확대 위치(관련 내용)를 AI 프롬프트로 만들어 같이 저장한다**(내용 질문 프롬프트 `photo_rec_ai.content_prompt` 그대로, 사용한 `prompt_version` 도 행에 기록). 시드와 같은 규칙으로 간결한 보기·색깔 질문 금지·친숙한 소재 위주(아래 시드 기준)로 프롬프트에 반영하고, 사진 출처(Pixabay 작성자·원본 페이지·라이선스·검색어)도 같이 보관한다(출처 표기 요건, 저장 칸은 2차에서 추가).

**시드·자동 보충 소재 기준(사용자 결정 11/19)**: 일상적이고 친숙한 것만 — 음식(햄버거·피자·짜장면 등 완성 음식, 재료보다 과일), 친숙한 동물(강아지·고양이·병아리·기린·다람쥐·코끼리·호랑이·원숭이·레서판다·고래 등; 뱀·도마뱀·곤충·파충류 등 징그럽거나 무서운 동물 제외), 쉬운 꽃(장미·튤립·개나리·진달래 등), 일상 풍경(산책로·단풍·바다 등; 극지·우주·사막·무인도·성 같은 낯선 풍경 제외), 일상 물건·장소(카페·교실·커피·자전거 등), 정적이거나 무슨 사진인지 알 수 없는 사진 제외. 질문 보기는 한두 단어로 간결하게(예: 숲속→숲, 고기패티→고기), **색깔을 묻는 질문은 쓰지 않는다**(너무 쉬움).

**저장 테이블**(새 테이블 한 개, 이름 [내 결정]: `play_photo_rec`)
- `id`(문자열 기본키), `group_id`(NULL 가능, 비면 공통), `source`(가족 앨범 / 흔한 사진 시드 / 흔한 사진 자동 — 값은 구현자 몫), `attachment_id`(가족 앨범 행만, 유일 → 한 사진 한 문제), `image`(공통 행만, DB 바이너리; 가족 행은 첨부 파일을 가리킨다), `kind`(월·일정·내용), `usable`(bool), `question`·`options`·`answer`·`box_x`·`box_y`·`zoom`(`play_photos` 와 같은 형식), `prompt_version`, `created_at`.
- 이미 보낸 것 추적: `play_photos` 에 **nullable `rec_id` 칸 하나를 더한다** [사용자 승인: 기존 표 변경 허용]. "이 문제로 쓰기"로 보낼 때 채우고, "그 가족이 보낸 추천"(공통·가족 사진 모두 최근 14일)은 `play_items`(가족·시각)와 `play_photos.rec_id` 를 조인해 구한다(별도 사용 표를 안 만든다).
- "이 문제로 쓰기"가 보낼 때, 가족 사진 행은 서버가 첨부 파일을 `play_photos` 용 파일(`play/photos/<가족id>/<놀이id>.jpg`)로 복사하고(`source=1`), 공통 행은 DB 이미지를 파일로 쓴다. 파일 저장소가 운영에서 정해지지 않은 건 기존 남은 일 그대로다(탐정단·이게 뭐게 업로드 공통).

**저장·삭제·API 규칙**(구현자 검토 반영, 모두 [내 결정])
- `attachment_id` 는 `message_attachments.id` 를 가리키는 외래키에 **ON DELETE CASCADE** 를 걸고(`chat_photo_checks` 와 같은 방식), 채팅 메시지 삭제 코드(`family_chat/repository.py`)도 이 표의 행을 함께 지운다. 지운 사진의 AI 결과는 남기지 않는다.
- 가족이 **AI 동의를 끄면 그 가족의 내용 질문(AI) 행을 지운다**(`ai_guard.set_enabled` 가 AI 결과 캐시를 지우는 것과 같은 취지). 월·일정 행은 AI 결과가 아니라 남긴다.
- **"이 문제로 쓰기"**: 기존 `POST /play/photos` 를 고친다 — 파일 업로드를 선택으로 하고 `rec_id` 를 선택값으로 더한다. `rec_id` 가 있으면 서버가 그 행의 사진(가족 행은 첨부 파일, 공통 행은 DB 이미지)을 `play_photos` 용 파일로 복사하고 질문·보기·정답·확대는 요청 값(출제자가 고친 값)을 쓴다. `play_photos.source` 번호는 1 가족 앨범, 2 내 폰, **3 흔한 사진**. 출제자가 사진을 내 폰 사진으로 바꾸면 `rec_id` 는 보내지 않는다.
- **보낼 때 서버가 다시 확인한다**: 가족 사진 행이면 그 사진이 아직 `photo` 상태인지(업로더가 타임라인에서 빼 `excluded` 가 됐으면 409), 같은 가족이 이 `rec_id` 로 최근 14일 안에 이미 보냈는지(공통 행도 같다).

**한도·캐시·AI 호출**
- AI 호출은 내용 질문을 만들 때만 한다. 기능 이름 `play_photo_rec` [내 결정], 값은 이게 뭐게와 같게 시작(쿨다운 5초·사용자 하루 3회·가족 하루 5회), 별도 한도. AI 동의가 꺼졌거나 한도를 다 쓴 가족도 월·일정 문제와 공통 사진은 정상으로 나온다(동의·한도가 없어도 3개가 채워진다) [내 결정].
- 구성은 저장·캐시하지 않는다(위 4번). `ai_guard` 캐시는 AI 동의가 꺼진 가족을 403으로 막아 구성 고정에 못 쓰므로 `ai_guard` 는 AI 호출(내용 질문 만들기)에만 쓴다. 만드는 중에 다른 가족 구성원이 열면 `preparing`, 같은 호출 중복 방지는 `ai_guard` 방식. 내용 질문은 사진당 호출 1번이라 동시 호출 후 한 요청 안에서 끝낸다.
- 서버 검증: JSON 형식, 보기 2~4개, 정답이 보기 중 정확히 하나, 확대 위치가 0~1, 질문 20자. 실패한 사진은 한 번 더 시도하고 그래도 안 되면 그 카드를 빼고 다른 후보로 채운다.

**서버 API** (`GET /play/photo/recommendations` [내 결정: 이름]): `{state, items:[{id, kind, source, image_url, question, options, answer(내는 사람에게만), box_x, box_y, zoom}]}`. 모든 실패·한도는 200으로 상태로 돌려준다(골든벨과 같음).

**앱**: 탐정단 만들기 화면에 "가비 추천 / 직접 내기" 전환. 카드에 사진 미리보기(확대 위치 상자)·질문·보기·출처 알약("가족 사진"/"가비가 고른 사진")·`< n / N >`·"이 문제로 쓰기"(질문·보기를 채우고 고칠 수 있음). 가족 앨범 고르기를 서버 연결 시 숨기던 부분은 이 추천과 별개로 둔다. 상태 문구는 다른 추천과 같은 말투이고 후보가 하나도 없으면 "가족 사진이 더 모이면 가비가 가족 사진으로 문제를 만들어요". 내가 올린 확인 전 사진이 있으면 확인 화면으로 가는 안내를 붙인다 [내 결정]. 서버 주소가 없으면 기존 시안.

## 7. 제약
- 서버 환경: 새 테이블 하나와 `play_photos.rec_id` 칸(expand 마이그레이션). 공용 DB 반영은 DB 담당자. **팀원의 `chat_photo_checks`·이력 표(`d7a41c9e5b02` 등)가 먼저 적용돼 있어야** 후보 조회가 된다(없으면 `family_chat` 이 503). 브랜치는 최신 `release/1.3` 에서 시작하고 이름·커밋 메시지는 사용자가 정한다.
- 외부 AI는 동의한 가족에게만, 사진은 EXIF 제거한 1024px 로만 보낸다.
- 하루 기준은 한국 시간 자정.

## 8. 위험
- 예전 사진이 후보에서 빠져 출시 초기에는 공통 사진 비중이 크다(사진 확인 화면 안내가 늘리는 방법).
- 일정 맞추기는 일정 제목이 "가족 모임"처럼 일반적이면 문제가 약하다. 촬영일이 일정과 안 맞는 사진은 건너뛴다.
- AI 내용 질문이 틀린 정답을 낼 수 있다(1차는 서버 구조 검사만, 보내기 전 출제자 확인이 마지막 방어선).
- 공통 사진의 저작권·출처(시드 50장도 해당): 쓰는 사진의 라이선스를 목록으로 기록한다(사진 사이트는 나중에 확인).
- 정답 노출: 추천 카드에 정답이 들어 있어 문제를 풀기 전에 추천 탭을 연 가족은 정답을 알 수 있다(골든벨 추천·이게 뭐게 추천과 같은 구조, 사용자가 받아들임). 사용자 id 시드로 줄이지만 후보 사진이 3장 이하이면 효과가 없다. 골든벨·이게 뭐게를 포함한 정답 숨김은 별도로 논의한다.
- 사진 담당 팀원의 AI 설명 저장 방식이 있다면 내용 질문 재료로 재사용할 수 있다(미확인).

## 9. 구현자에게 맡기는 것
`source` 값 번호, 월 보기의 오답 월 고르기, 일정 보기 선택 규칙, 후보 사진 정렬(최근순/무작위)과 카드 종류 분배, 확대 배율 기본값, 내용 질문 프롬프트와 모델(Haiku 5.5 기준 비용·시간은 구현 뒤 실측), `usable=false` 처리, 시드 스크립트 형식, 한도 값 조정, 앱 화면 세부, 테스트 구성(가짜 LLM, `test_quiz_rec` 와 비슷하게)과 폰 확인.
