# 기능: 일정 에이전트

## 목적
사용자가 메인(개인) 채팅이나 가족 채팅에서 일정 관련 말을 하면 일정 에이전트가 답하고 처리한다. 일정 화면의 "먼저 권해드려요" 카드도 같은 에이전트가 만든다. 일반 질문(날씨, 식당 추천 등)은 메인 에이전트가 직접 답하고 일정 에이전트의 범위가 아니다.

## 용어
- 메인 에이전트 = 사용자 요청을 받아 분류하고 일정 요청을 일정 에이전트에 넘기는 오케스트레이터(다른 담당자가 만든다).
- 일정 요청 = 일정 질의응답, 추천, 등록, 수정, 삭제, 확인 체크.
- 채널 = 호출한 채팅의 종류(개인 | 가족). 읽을 수 있는 데이터가 채널로 정해진다.
- 일정의 형태·누구·주제·공유 등 용어는 [일정](schedule.md) 문서를 따른다.

## 화면
- 이 기능은 새 화면을 만들지 않는다. 사용자가 일정 에이전트를 만나는 경로는 두 가지다.
  - 메인·가족 채팅: 메인이 일정 에이전트를 호출한다. 채팅 화면은 메인 담당자가 만들고, 일정 쪽은 카드 데이터 형식과 카드 컴포넌트를 제공한다.
  - 일정 화면의 먼저 권해드려요 카드(일정 체크, 일정 추천): 앱이 일정 에이전트를 직접 호출하며 메인을 거치지 않는다.
- 일정 앱 안의 채팅 화면(하단 시트, 전용 화면, 기록)은 에이전트 연동 확인 뒤 제거한다. 그전까지는 확인용으로만 둔다.
- 채팅 카드: 일정 목록(약속·할 일 미니 카드), 등록 완료, 수정 확인(이전 → 새 값), 삭제 확인(공유 안내), 추천. 수정·삭제는 채팅 안 확인 카드로 한 번 더 확인한 뒤 실행한다.

## 기능
- 일정 질의응답: "이번 주 일정 알려줘", "빈 시간 찾아줘" 같은 질문에 문장과 미니 카드로 답한다.
- 일정 추천: 읽은 데이터에서 추가할 일정을 제안한다. 채팅에서는 추천 카드로 보여 주고, 카드를 눌러 대화창에 입력하는 방식은 정해지면 반영한다.
- 일정 등록: 사용자가 "등록해줘"라고 하면 바로 등록한다(요청이 곧 승인). 날짜·제목만 있으면 시간·장소·누구·메모를 더 넣을지 한 번만 묻고, "그냥 등록해"면 그대로 등록한다. 처음부터 다 말했으면 묻지 않는다. 등록 뒤 채팅에 등록 정보 카드(값 없는 항목은 숨김, 상세 보기·취소)를 보여 준다.
- 일정 수정·삭제: 확인 카드로 한 번 더 확인한다. 삭제는 공유한 분 화면에서도 사라진다고 안내하고, 수정은 바뀌는 값을 "이전 → 새 값"으로 보여 준다. 대상이 여럿이면 어느 것인지 먼저 묻는다. 만든 사람이 아니면 수정·삭제할 수 없다.
- 일정 체크: 오늘 내 약속·할 일 중 확인하지 않은 것을 물어 확인·완료를 돕는다(먼저 권해드려요 확인 카드).
- 읽는 데이터: 일정(약속·할 일·부탁), 정산, 돌봄, 개인(메인) 채팅, 가족(소통) 채팅.
  - 개인 채널에서 호출되면 위 5종을 읽는다.
  - 가족 채널에서 호출되면 개인 채팅은 읽지 않는다.
  - 서버에서는 과거 1년·미래 1년까지 조회하고, LLM에는 질문에 해당하는 구간만 보낸다.
  - 각 기능의 service/repository를 서버 안에서 호출해 읽는다(DB 직접 연결 아님). 호출 전에 `ensure_group_member`를 확인하고 그룹은 서버가 정한다.
  - 외부 LLM으로 보내기 전에 개인정보를 가린다(ADR 0007 방식 재사용 여부는 팀 확인).

## API
- 에이전트 진입 함수: 사용자, 그룹, 채널, 입력 문장(또는 카드 요청 종류)을 받아 문장, 카드 목록, `pending_action`을 돌려준다. 메인이 생기면 메인이 이 함수를 호출하고, 그전에는 일정 라우터가 호출한다.
- 확인 실행: 수정·삭제 확인 카드의 버튼을 누르면 앱이 `pending_action`을 그대로 돌려보내고, 서버가 실행한다. 서버는 상태를 저장하지 않는다(stateless). 실행 직전에 그룹 구성원과 만든 사람을 다시 검사한다.
- 카드 호출: 일정 체크·추천 카드는 앱이 직접 호출한다.
- 서버 `schedule`에 일정 수정(update)을 추가한다.
- 입구(메인이 생기기 전까지): `POST /schedule/agent` — 요청 `{text, channel("personal"|"family")}`, 응답 `{intent, text, cards[{type, data}], pending_action}`. 사용자와 그룹은 로그인 정보로 정한다.
- 요청 종류와 답은 한 번의 LLM 호출로 함께 받는다(질문 1회 = 호출 1회). 코드가 돌려받은 `intent` 로 종류별 처리를 정하고 결과(대상 일정 id 등)를 검증한다. 일정 목록은 개인정보를 가린 뒤 보낸다. 가리는 함수는 `ai_assistant` 기능 폴더의 `app/features/ai_assistant/ingest/masking.py` 에 있는 `mask_text` 하나를 가져다 쓴다(`features/schedule/agent/chat.py`). 이 함수의 위치나 이름을 바꾸면 일정 쪽도 고쳐야 한다.
- 지금 처리하는 종류는 질의(`query`: 문장과 `event_list` 카드)뿐이고, 나머지 종류는 "아직 처리할 수 없어요"를 돌려준다.
- 나머지 엔드포인트(확인 실행 등)와 필드 이름은 구현 단계에서 정한다.
- LLM 호출은 `app/shared/llm` 래퍼로만 한다. 래퍼에 선택 인자 `model` 하나를 추가하며 안 주면 기존 동작이다. tool use는 쓰지 않는다. 일정 전용 프롬프트와 규칙은 `features/schedule/agent/`에 둔다.

## 데이터
- 새 테이블은 만들지 않는다(수정·삭제 확인을 stateless로 처리하기 때문).
- 서버 일정 모델(제목, 시작, 메모, 상태, 출처, 만든 사람)은 앱 모델(형태, 장소, 누구, 주제, 공유, 종일, 확인 여부)보다 필드가 적다. 에이전트는 일정 접근을 repository 뒤에 두고 서버에 있는 필드로 먼저 동작시키며, 모델 확장은 별도로 합의한다.

## 완료 조건
- 개인·가족 채널에서 호출했을 때 읽는 데이터가 위 규칙대로 달라진다.
- 일정 질의응답·추천·등록·수정·삭제 흐름이 동작하고, 수정·삭제는 확인 카드를 거쳐서만 실행된다.
- 만든 사람이 아니면 수정·삭제가 거부되고, 변조한 `pending_action`으로도 권한 밖의 일은 실행되지 않는다.
- LLM 호출이 실패하거나 키가 없을 때(`LLMUnavailable`) 규칙 기반 대체 동작 또는 안내 문구로 답한다.
- `model` 인자를 주지 않은 기존 호출은 동작이 바뀌지 않는다.
- 서버 테스트 통과, 앱 `npm run lint` 통과.

## 미정
- 일정 요청과 일반 요청을 가르는 기준(예: "내일 점심 식당 추천해줘")과 메인↔일정 에이전트 입출력 형식(메인 담당자와 협의).
- 모델 구성(용도별로 어떤 모델을 쓸지), 호출 한도·비용 관리.
- 개인정보를 외부 LLM으로 보내는 것에 대한 팀 확인과 마스킹 재사용 여부.
- 서버 일정 모델 확장 범위와 시점.
- 팀 AI 비서(PR #22·#42)가 후속으로 남긴 "일정·지출·돌봄 검색"과의 분담.
- 채팅 안 추천 카드를 눌러 대화창에 입력하는 방식.
- 먼저 권해드려요 추천을 미리 만들어 저장하는 구조(호출 비용), 카드 노출 개수·순서.
