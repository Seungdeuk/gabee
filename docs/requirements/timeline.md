# 기능: 가족 사진 타임라인·추억(가족 공동 앨범)

> 상태: **확정(2026-11-12 결정 반영)**. 구현은 PR 단위로 별도 승인을 받는다. 결정 기록은 맨 아래 "결정 기록", 아직 확인이 필요한 기술·탈퇴 정책은 "확인 필요 항목"에 따로 모았다.
> 관련: `family-library.md`(문서함·사진 판별), `family-chat.md`(사진 보내기·앨범 묶음), `weekly-news.md`(주간 뉴스, 타임라인과 독립), ADR 0014·0015, 로드맵 T05·T38~T43.

## 목적
가족 구성원이 가족 채팅방에 평소처럼 사진을 올리면, **다시 올리지 않아도** 가족 모두가 함께 보는 **가족 공동 앨범**에 날짜별로 쌓이고, 가족이 함께 댓글·추억·성장 기록을 남겨 회상할 수 있게 한다. 단순한 사진 목록이 아니라 미테네(Mitene)처럼 "가족이 같이 쓰는 앨범"이 목표다. AI 기능(이야기·검색·에이전트)은 그 위에 단계적으로 붙인다.

## 사용자 요구 (2026-11-10 사용자 요청)
1. 사진 **촬영일** 기준으로 연·월·날짜별 자동 정리
2. 가족 채팅방에 공유한 사진을 **재업로드 없이** 타임라인에 표시
3. 가족별 사진 댓글과 공동 추억 이벤트
4. 가족이 직접 입력하는 성장 기록
5. AI 가비가 사진·댓글·관련 일정에 **근거하여** 추억 이야기 생성
6. E5-small·pgvector 를 활용한 자연어 추억 검색
7. 장기적으로 가족 추억 영상 제작
8. ~~주간 가족 뉴스와 타임라인 추억 연결~~ — **이번 범위 제외.** 주간 뉴스(T26)와 타임라인은 독립이다(2026-11-12). 필요하면 추후 별도 승인.

## 화면 (시안 없음, 기존 앱 UI 컴포넌트 활용 — Q20)
- 기존 `AlbumGrid`·`MediaGrid`·`AlbumViewer`·`AuthImage`·`ReactionRow` 와 AI 확인 카드를 재사용한다. 새 시각 요소를 만들지 않는다.
- 진입: 마이 > **타임라인**(지금 "준비 중", `features/more/menuItems.js`).
- 타임라인 목록: 연·월 머리글 → 날짜 → 묶음(1장/2장 나란히/3장 이상 격자, 기존 앨범 말풍선 규칙과 같게). 월별 대표 사진. 위로 갈수록 최근. 촬영일이 없는 사진은 상세에 작게 "보낸 날 기준"을 표시한다(Q2).
- 사진 보기: 기존 사진 뷰어 재사용, "원본 메시지로 가기"(채팅방에서 그 메시지로 이동), 반응(기존 메시지 반응), 댓글.
- 추억 이벤트: 만들기(사진 고르기 → 제목·설명·날짜) → 보기(사진 묶음·댓글·AI 이야기).
- 성장 기록(출시 후): 대상(가족 구성원 또는 이름표) → 날짜·종류·값·메모·사진(선택).
- **확인 필요 목록(업로더 본인만)**: 판별이 애매하거나 실패한 내 사진(아래 "표시 조건").
- 추억 검색(후속), AI 이야기(2차), 영상(후속).
- "N년 전 오늘"·즐겨찾기·가족여행 일지는 후속 후보(2026-11-06 메모의 후속 목록).

## 자동 수집 규칙 (타임라인)
- **대상**: 가족 전체방(`chat_rooms.kind = family`, 옛 `room_id` 없는 메시지 포함)의 사진 첨부(`message_attachments.kind = image`)만.
- **제외**: 1:1 방 사진, 메인 AI 채팅(서버에 저장되지 않음), 가족 문서함에 등록된 사진(문서로 판별됐거나 "문서로 저장"한 사진 — Q5), 지운 메시지의 사진(첨부가 지워짐), 업로더가 "타임라인에서 뺀" 사진(2026-11-16 결정: 올린 사람만 뺄 수 있고 `excluded`(수동) 상태가 되며 채팅 원본은 그대로, 올린 사람이 안내 확인을 거쳐 다시 넣을 수 있다).
- **재업로드 없음**: 채팅에 저장된 1600px 사본과 400px 썸네일을 그대로 쓴다. 새 파일을 만들지 않는다.
- **묶음 유지**: 같은 `batch_id` 는 한 묶음으로 보인다. 묶음 안 촬영일이 다르면 가장 이른 날짜에 묶음 전체를 둔다(Q4).
- **날짜**: 촬영일이 있으면 촬영일, 없으면 **보낸 날(한국 시간)**. 이미 올라간 사진은 모두 보낸 날 기준이다(복구 불가, Q2). 새 사진의 촬영일은 iOS·Android 실기기에서 확인한 뒤에만 신뢰한다(웹은 촬영일 출처가 없어 보낸 날 기준).
- **시간대(Q3)**: 사진에 시간대 정보가 있으면 그것을 쓰고, 없으면 한국 시간으로 본다.

### 표시 조건 (문서 판별 결과 기준, D-2·D-8)
- 타임라인에는 **판별이 끝나 일반 사진으로 확인된 사진만** 보인다. 판별 대기·판별 실패·애매함·문서로 확정(등록됨)된 사진은 가족에게 보이지 않는다.
- 판별 결과는 사진마다 저장한다(일반 확인 / 문서 / 애매 / 실패). 저장돼 있지 않으면 **대기**로 보고 숨긴다. 판별 결과를 읽지 못하면(저장소 오류·판별 모듈 미등록) 빈 목록이 아니라 오류(503)를 돌려준다(fail-closed).
- 업로드 직후 판별이 끝나기 전에는 타임라인에 보이지 않을 수 있다(알려진 한계). 채팅방에서는 평소처럼 바로 보인다.
- **애매·실패 사진(D-8)**: 가족 타임라인에서는 숨기고 **업로더 본인에게만** "확인 필요" 목록으로 보여 준다. 업로더는 명시적으로 **일반 사진으로 표시** 또는 **문서로 저장**을 고를 수 있다.
- **문서로 확정된 사진은 한 번의 클릭으로 일반 사진이 되지 않는다.** 수동 분류는 다음을 지킨다.
  - 권한 검증: 그 사진의 업로더 본인만 할 수 있다(가족 그룹 멤버십·방 접근도 함께 확인).
  - 확인 안내: 바꾸면 무엇이 달라지는지(문서함에서 빠지고 가족 타임라인에 보인다 등)를 보여 주고 다시 한 번 확인받는다. 문서에서 일반으로 바꿀 때는 이유 선택이나 입력 같은 추가 단계를 둔다.
  - 변경 이력: 누가·언제·무엇에서 무엇으로(이전 상태→새 상태)·이유를 남긴다. 이력에는 사진 내용을 담지 않는다.
  - 세부 설계(이력 표, 문서함 항목 처리, 되돌리기)는 T05-b0 상세 설계에서 확정한다.
- **기존 사진 보강(D-9, 별도 PR)**: 기존 사진은 판별 결과가 없어 처음에는 모두 숨는다. 로컬 OCR 은 **문서 의심 여부를 보조적으로 확인하는 데만** 쓰고, "글자가 검출되지 않았다"는 이유만으로 일반 사진으로 자동 확정하지 않는다. 일반 사진임이 신뢰성 있게 확인되지 않은 사진은 업로더 확인 대상으로 남긴다. 자동 재판별은 별도 PR 로 분리하며 그 PR 에서 오탐·미탐 평가를 한다.
  - 평가 방법(제안): 합성 이미지(문서·일반 사진·메뉴판·간판·성분표 등)와 개발 중 확인한 샘플로 평가셋을 만들고(실제 가족 사진은 쓰지 않는다), 문서를 일반으로 잘못 확정하는 **미탐을 0건**에 두는 것을 하드 게이트로, 일반 사진을 문서 의심으로 돌리는 **오탐**(업로더 확인이 늘어나는 비용)은 허용 비율을 정해 관리한다.
- **판별 누락 복구(D-10)**: 판별 결과가 없는 사진은 **별도 작업**으로 주기적으로 다시 판별한다. 푸시 예약 스케줄러에 묶지 않는다. 재시도 횟수 제한, 같은 사진의 중복 실행 방지, 실패 상태 관리, 서버 재시작 복구, 여러 프로세스에서의 동작을 고려해 T05-b0 상세 설계에서 정한다.
- 신규 사진에서 어떤 판별 결과를 "일반 확인"으로 인정하는지(로컬 OCR 의 글자 없음만으로 충분한지 등)는 T05-b0 상세 설계에서 정한다(확인 필요).

### 촬영일·메타데이터 규칙 (Q1·Q3)
- 서버는 업로드 사진에서 **촬영 시각 태그(DateTimeOriginal, OffsetTimeOriginal)만** 읽는다. GPS(위치)·기기 모델·제조사·소프트웨어·설명 태그는 읽지도 저장하지도 않는다. 저장되는 사진 사본과 썸네일에는 메타데이터가 없다(현재 동작 유지).
- 앱은 촬영 시각을 얻으려고 `exif: true` 로 사진을 받지만 **`DateTimeOriginal` 한 값만 꺼내 서버로 보낸다.** 위치를 포함한 나머지 EXIF 는 즉시 버리고 로그·저장·전송하지 않는다.
- 서버가 읽은 값이 있으면 그것을 쓰고, 없을 때만 앱이 보낸 값을 쓴다. 범위(1990-01-01 ~ 현재+1일) 밖이거나 형식이 틀린 값은 버리고 보낸 날 기준으로 둔다(업로드는 막지 않는다). 값이 너무 길면(40자 초과) 요청 형식 오류(422)다.
- 시험: GPS·기기 태그가 든 사진을 올려도 DB·응답·저장 파일에 촬영 시각 외 메타데이터가 없음을 확인한다.

## 추억 이벤트·댓글·성장 기록 (T40)
- **추억 이벤트**: 가족 누구나 **가족방 사진**을 여러 장(묶음·날짜를 넘어) 골라 하나의 추억으로 묶는다. **사진 없는 텍스트 단독 이벤트는 만들 수 없다(Q6).** 제목·설명·날짜·대표 사진을 만들고 고칠 수 있다. 업로드 묶음(`batch_id`, 자동)과는 다른 단위다.
- **댓글**: 사진 한 장 또는 추억 이벤트에 가족이 댓글을 단다. 채팅방에는 올라가지 않는다. 수정·삭제는 **작성자만**(Q10). 반응은 기존 메시지 반응을 그대로 쓴다.
- **성장 기록(출시 후, Q12)**: 가족이 직접 입력한다(대상·날짜·종류·값·메모·사진 선택). 대상은 구성원 또는 **이름표(구성원이 아닌 아이 포함)** 다. **AI 처리(이야기·검색 색인·에이전트)에서 기본 제외**한다(Q11).
- **빈 이벤트(D-3)**: 이벤트의 모든 사진이 지워지면 이벤트는 남기되 "사진이 모두 삭제됐어요"로 표시한다. 삭제된 사진의 이미지·원문, 그 사진에 달린 댓글은 보이지 않는다. 제목·설명은 이벤트 작성자의 글이므로 남는다.
- **나간 가족(Q18)**: 구성원이 가족을 나가거나 탈퇴해도 그 사람이 만든 이벤트·댓글은 가족 공유 기록으로 남고 작성자 이름 자리에 "나간 가족"으로 표시한다. 계정 탈퇴 때 사용자 데이터를 정리하는 경로는 확인 전까지 보류한다(D-7, 확인 필요).
- **이전 결정과의 관계**: 2026-11-06 에 "별도 업로드/추억 직접 만들기는 폐기"로 정했다. 이 결정은 **사진과 연결된 이벤트에 한해 번복**했다(2026-11-12, Q6).

## AI 추억 이야기 (T41, 2차 기능)
- **요청할 때만** 만든다(자동 생성 없음). 한 번 만든 이야기는 저장하고, 다시 볼 때는 AI 를 부르지 않는다.
- **제안 → 확인 → 생성**: AI 채팅에서 이야기를 요청하면 가비는 **확인 카드**로 제안만 한다(서명 토큰 10분·1회용). 사용자가 확인하면 서버가 가족 AI 동의·한도·권한을 확인하고 한 번만 생성한다. 에이전트가 생성 도구를 반복 호출하는 구조가 아니다. 가족 채팅방에 자동으로 올리지 않고, 이야기는 **가족 타임라인 안에서만** 공유한다(Q13·Q14).
- **근거**: 추억 이벤트의 제목·설명·댓글, 같은 기간의 **가족 공유 일정**. 개인 일정·개인 AI 대화·1:1 대화·금액·건강 기록·성장 기록(Q11)은 쓰지 않는다. **사진 파일과 사진 내용은 외부 AI 로 보내지 않는다.**
- **근거 없는 추측 금지**: 근거에 없는 사건·인물·감정·장소를 쓰지 않는다. 설명이 없는 사진은 "사진 N장"으로만 언급하고 사진 속 활동을 추측하지 않는다(2026-11-06 원칙). 문장마다 근거(어느 이벤트·댓글·일정)를 연결해 저장한다. 근거가 연결되지 않는 문장은 보여 주지 않는다.
- **외부 전송·한도(Q19)**: 가족이 AI 사용에 동의한 경우만, 이름·연락처는 가명화해 보낸다. 제안 상한은 **구성원당 하루 3회, 가족당 하루 10회**이고 설정으로 조정할 수 있게 둔다(실제 모델 비용을 확인한 뒤 재검토).

### 재생성과 버전 (D-11)
- 기본으로 **최근 3개 이야기 버전**을 보관한다. 이전 버전은 덮어쓰지 않는다.
- 사용자가 수정한 버전은 자동으로 삭제하지 않는다.
- 이전 버전 복원은 **AI 호출 0회**이며 생성 한도를 차감하지 않는다. 재조회도 한도를 차감하지 않는다.
- **사용자가 명시적으로 재생성을 요청한 경우에만** 하루 한도를 1회 차감한다. 재생성 전에는 확인 카드로 한도와 "기존 이야기는 보관돼요"를 알린다.
- 버전마다 근거(문장별 근거 연결)와 수정 이력을 관리한다.
- 수정본이 여러 개일 때의 보관 한도와 저장 공간 정책은 구현 전에 추가로 검토한다(확인 필요).

### 근거 삭제와 이야기 (D-12)
- 근거 자료(사진·댓글·이벤트)가 삭제되면 **삭제된 정보를 반영한 이야기 문장을 그대로 유지하지 않는다.**
  - 삭제된 자료에만 근거한 문장은 숨기거나 무효화한다.
  - 남아 있는 근거만으로 충분히 뒷받침되는 문장은 유지할 수 있다.
  - 삭제된 사진·댓글의 **원문·이미지·인용 내용은 어디에서도 보이지 않는다**(이야기 문장, 근거 표시, 이전 버전 포함).
  - 사용자에게 "근거 일부가 삭제됐어요"를 안내한다.
  - 재생성은 사용자가 직접 요청할 때만 실행한다(자동 재생성 없음).
- 같은 삭제 정책을 **이전 이야기 버전과 검색 색인**에도 적용한다. 삭제된 원본의 정보가 AI 생성 문장·색인을 통해 계속 노출되지 않아야 한다.
- 구현 방식(문장 단위 무효화 기준, 버전 일괄 처리, 색인 정리 시점)은 T41 상세 설계에서 정한다.

### 생성 신뢰성 (D-4)
- 이야기 생성은 `pending` 줄을 먼저 차지한 뒤 서버가 요청 안에서 한 번 생성하고, 앱은 폴링으로 결과를 확인한다. 기존 주간 뉴스의 생성 패턴(동시 요청 방지, 오래된 `pending` 회수, 실패 시 놓기)을 따르며 별도 작업 큐는 두지 않는다.
- 실패하면 `failed` 로 저장하고 확인 토큰·한도를 되돌려 "다시 시도"할 수 있게 한다. 사용자가 앱을 닫아도 서버는 끝까지 처리해 저장한다. 서버가 재시작되면 오래된 `pending` 을 회수한다.
- **요청 취소·타임아웃 때의 실제 동작은 T41 구현 전에 검증한다(확인 필요).** 실패한 생성이 하루 한도에 포함되는지, 프록시·앱의 요청 타임아웃과 LLM 타임아웃의 관계도 그때 확인한다.

## AI 사진 설명 (T42, 장기 후보 — 구현하지 않음)
- 2026-11-06 "사진 내용은 AI 가 읽지 않는다" 결정을 **유지**한다(2026-11-12). Claude Vision 을 이용한 자동 사진 설명·태그를 만들지 않는다. 이야기·검색은 촬영일, 가족이 쓴 제목·설명·댓글, 허용된 가족 공유 기록만 쓴다.
- 장기 확장 후보로만 남긴다. 다시 검토할 때 동의 정책·외부 전송·비용·개인정보 고지(T31)를 따로 본다. 일반 사진(얼굴·집·아이)이 외부 AI 로 나가는 새 경로이기 때문이다. 이전 질문(Q7·Q8·Q9)은 보류.

## 추억 검색 (T38)
- **검색 대상**: 추억 이벤트 제목·설명, 가족 댓글, AI 이야기. 날짜·올린 사람 조건. 삭제된 대상은 색인에서도 지운다(D-12).
- **사진 자체는 글자 검색으로 찾을 수 없다**: 글이 붙은 사진만 내용으로 찾히고, 나머지는 날짜·올린 사람으로만 찾는다.
- **1단계**: 글자 일치(AI 0회, 이벤트·댓글 기능 직후). **2단계**: 기존 E5-small·pgvector 의미 검색 재사용(문서함과 섞지 않는 별도 색인, RAG 팀원 합의와 T12 해소 뒤).
- **역할 경계**: 임베딩 모델 선택·학습, 조각 나누기, 순위 매기기, 검색 품질 평가는 **RAG 담당 팀원 영역**이다. 이 기능은 어떤 글을 색인할지, 권한(가족 그룹)·삭제 동기화, 화면·API 를 정한다.

## Memory Agent (T39)
- 추억 검색·조회는 Tool Calling 으로 하는 읽기 전용 하위 에이전트(`ask_memories`)가 맡는다. 이야기 생성은 위 "제안 → 확인 → 생성"이고 생성 도구를 에이전트가 반복 호출하지 않는다.
- 1:1 방에서는 비활성이다(D-5). 도구 결과는 가명화해서 모델에 전달한다. 가족 그룹 권한과 AI 동의를 확인한다.
- 주간 뉴스를 읽는 도구는 넣지 않는다(T26 독립). 필요하면 별도 승인.

## 추억 영상 (T43, 후속)
- 사진 고르기·시간순·AI 제목/자막(스토리보드)·재생.
- 지금 영상 렌더링·저장·배포 기반이 없다. 1단계는 앱에서 사진 슬라이드쇼로 재생하는 안을 검토한다(Q17, 미정).
- 가족이 찍은 동영상 올리기(T10)와는 다른 기능이다.

## 주간 가족 뉴스와의 관계
주간 뉴스(T26)와 타임라인은 **독립 기능**이다(2026-11-12). 뉴스는 타임라인 사진·추억 이벤트·성장 기록을 읽지 않고, 타임라인은 뉴스를 읽지 않는다. 연동이 필요해지면 별도 승인 후 요구사항을 따로 쓴다.

## API (초안 — 이름·필드는 확정 전, `openapi.json` 이 기준)
- 타임라인: 월별 요약(월·사진 수·대표 사진), 월/날짜 범위 목록(사진·묶음·날짜·촬영일 여부·원본 메시지 id). 판별 결과가 일반 확인인 사진만.
- 사진 판별: 내 "확인 필요" 목록, 일반 사진으로 표시·문서로 저장(업로더만, 확인 단계·변경 이력).
- 추억 이벤트: 만들기·고치기·지우기·사진 넣기/빼기·목록·상세.
- 댓글: 사진·이벤트에 달기·고치기·지우기(작성자만).
- 성장 기록(출시 후): 넣기·고치기·지우기·목록.
- 이야기(2차): 제안·생성(확인 토큰)·조회·수정·버전 목록·복원·재생성.
- 모든 API 는 가족 그룹을 요청에서 받지 않고 로그인한 사용자의 가족 멤버십으로만 정한다. 다른 가족 데이터는 존재도 알리지 않는다(404).

## 데이터 (초안 — DB 변경은 Alembic 으로만, 모두 추가(expand))
- 사진 첨부에 촬영 시각 칸 1개(비어 있을 수 있음, Q1).
- 사진 판별 결과 표(ai_assistant 소유) + 수동 분류 변경 이력 — 상세는 T05-b0 설계.
- `family_memory`: 추억 이벤트, 이벤트-사진 연결, 댓글, (출시 후) 성장 기록, (2차) 이야기(버전·근거·수정 이력), (후속) 검색 색인.
- 삭제 정책: 사진(메시지)을 지우면 판별 결과·이벤트 연결·사진 댓글을 함께 지운다. 이야기 문장의 근거 처리는 "근거 삭제와 이야기"(D-12). 가족을 지우면 모두 지운다. 1:1 방 데이터는 처음부터 없다.
- 이벤트-사진 연결을 `message_attachments` 에 대한 FK CASCADE 로 할지(기능 간 표 참조)는 DB 담당자와 확인한다(D-6, 확인 필요).
- 지우거나 이름을 바꾸는 위험 변경은 없다. 공용 DB 반영은 DB 담당자 통합 절차를 따른다.

## 개인정보·권한·삭제 정책
- 가족 그룹 단위로만 보이고, 가족 구성원만 읽고 쓴다.
- 위치·기기 정보는 저장하지 않는다(촬영 시각만, "촬영일·메타데이터 규칙").
- 외부 AI 로 나가는 것: 이야기(가명화한 글, 가족 AI 동의 시)뿐이다. **사진 파일·사진 내용은 보내지 않는다.** 타임라인·댓글·성장 기록 자체는 외부로 나가지 않는다.
- 로그에 사진 내용·댓글·성장 기록 값·촬영 시각 값을 남기지 않는다.
- 구성원이 가족을 나갈 때 기록은 유지하고 "나간 가족"으로 표시한다(Q18). 계정 탈퇴 정리 경로는 확인 필요(D-7).

## 완료 조건 (단계 1·2 기준)
- 가족방 사진이 연·월·날짜·묶음으로 보이고, 촬영일이 있으면 촬영일·없으면 보낸 날로 정리된다.
- 판별이 끝나지 않았거나 일반 사진이 아닌 사진은 타임라인에 나오지 않는다. 판별 결과 조회가 실패하면 오류가 난다(빈 목록이 아니다).
- 문서로 확정된 사진은 확인 단계·권한 검증·변경 이력 없이 일반 사진이 되지 않는다.
- 1:1 사진·문서 사진·지운 사진이 나오지 않는다. 다른 가족 데이터에 접근할 수 없다(시험).
- GPS·기기 정보가 응답·DB·저장 파일 어디에도 없다(시험).
- 추억 이벤트에 가족방 사진만 넣을 수 있고, 사진을 지우면 이벤트 연결·사진 댓글이 정리된다. 가족 삭제 시 함께 지워진다(시험). 빈 이벤트에서 삭제된 사진의 내용이 보이지 않는다.
- 화면은 실기기(iOS·Android)·웹 확인이 필요하다.

## 확인 필요 항목 (기술·탈퇴 정책 등, 아직 정해지지 않은 것)
- iOS·Android 실기기에서 `exif: true` 로 촬영 시각(`DateTimeOriginal`)과 시간대가 오는지, 압축·편집 옵션에서 보존되는지, 웹 업로드의 촬영일 출처.
- 새 `taken_at` 칸이 없는 DB 에 새 코드가 먼저 배포될 때의 동작과 배포 순서(T05-a 구현 때 확인).
- 이벤트-사진 연결의 기능 간 FK CASCADE(D-6)와 `created_by` 의 탈퇴 시 처리, 계정 탈퇴 정리 경로(D-7).
- 신규 사진에서 "일반 확인"으로 인정하는 판별 결과 기준, 판별 결과 표·수동 분류 변경 이력·재시도 작업의 상세(T05-b0 설계).
- 기존 사진 자동 재판별의 오탐·미탐 허용 기준(별도 PR).
- 수정본이 여러 개일 때 이야기 보관 한도와 저장 공간 정책(T41 구현 전).
- 이야기 생성의 요청 취소·타임아웃·실패 시 한도 포함 여부(T41 구현 전).
- 일정의 '가족 공유 일정' 판정 기준, 의미 검색 색인 위치·모델(Q16, RAG 팀원 합의).
