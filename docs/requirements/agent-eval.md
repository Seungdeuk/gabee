# 기능: Agent 평가·분석·개선 루프

소통 Agent 와 @가비(메인) Agent 가 도구를 제대로 고르고 인자를 맞게 채우고 과업을 끝내는지를 숫자로 재고, 실패를 분석해 프롬프트·도구 설명을 고친 뒤 다시 재는 평가 체계다. 앱 화면과 서버 API 는 바꾸지 않는다. 결정 근거는 [ADR 0016](../adr/0016-agent-eval-loop.md).

## 목적
- 지금은 도구 이름만 채점한다(`apps/api/evals/tab_agents`). 도구 **인자**, **과업 성공**, **보안·권한 위반**, 효율, 일관성을 새로 잰다.
- 측정 → 실패 분류 → 개선안(프롬프트·도구 설명) → 재측정을 되풀이하고, 개선 전후를 같은 기준으로 비교한다.
- 결과는 이력서·포트폴리오에 쓸 수 있게 재현 가능한 형태(실행 기록, 신뢰구간, 비용)로 남긴다.

### 하지 않는 것
- RAG 평가(OCR·임베딩·문서 검색 품질)는 하지 않는다. 문서 검색은 RAG 담당 팀원의 범위다.
- 앱·서버의 운영 동작은 바꾸지 않는다. 개선안은 사람이 검토한 뒤 별도 PR 로 반영한다.
- 모델 자체의 학습·미세조정, 새 평가 서비스·의존성 도입은 하지 않는다.
- CI(`.github/workflows`)에는 연결하지 않는다. 사용자가 요청할 때만 별도로 한다.

## 평가 대상 (기준 커밋 `3014b779`, release/1.2)
| Agent | 구조 | 코드 |
|---|---|---|
| @가비 메인 | 모델↔도구 루프, 최대 4단계(`MAX_STEPS`), 라우팅은 시스템 프롬프트 | `ai_assistant/knowledge/rag_chat.py`, `ai_assistant/agents.py` |
| 소통 Agent | 루프. `search_messages`·`analyze_recent_chat` 은 1:1 방에서도 가족 전체방만 읽음 | `family_chat/agent.py` |
| 정산 Agent | 루프, 최대 4단계 | `billing/agent.py` |
| 일정 Agent | LLM 은 의도만 분류하고 코드가 분기하는 고정 워크플로 | `schedule/agent/` |

- 정확한 표현은 "계층형 Tool-Calling Agent(정산·소통은 루프, 일정은 고정 워크플로) + 서버 가드레일"이다. 계획 단계, 자기 검토, 요청 사이의 작업 메모리는 없다.
- 서버 가드레일: 도구 목록·audience 제한, 1:1 방에서 일정 도구 차단(`agents.py`), 고위험 값 거부와 거짓 제안 문장 제거(`rag_chat.py`), 공통 관문 `shared/ai_guard.py`.
- 모델 호출은 `shared/llm/transport.py` 의 `post_messages`(SDK 없음), 기본 모델 `claude-haiku-5-5`(`shared/config.py`).
- 기존 평가: `evals/tab_agents`(사례 52건: 정산 39, 메인 13). 도구 이름 집합만 채점하고 `tool_args` 는 데이터에만 있다. 메인 사례는 audience 없이 `rag_chat.ask` 를 직접 불러서 @가비 방 경로·1:1·소통·일정은 평가되지 않는다. 결과는 콘솔 출력뿐이다.

## 원칙과 제약
- **합성 데이터만** 쓴다. 실제 가족의 이름·연락처·대화·사진을 쓰지 않는다. 모든 사례는 `meta.synthetic: true` 이고 가상 인물 목록의 이름만 쓴다.
- **개인정보 원문을 저장하지 않는다.** 실행 기록(궤적)은 이메일·전화번호 패턴을 지운 뒤 저장하고, 합성 표시가 없는 사례는 저장하지 않는다.
- **운영 DB·팀 서버·공용 PostgreSQL 은 건드리지 않는다.** 임시 SQLite(또는 임시 PostgreSQL)만 쓴다.
- **최종 테스트셋은 개선에 쓰지 않는다.** 개선안을 만드는 쪽에는 테스트셋 사례를 보여 주지 않는다.
- **보안 위반은 하드 게이트다.** 보안·권한 위반이 하나라도 생긴 개선안은 성능이 높아도 채택하지 않는다.
- API 키 값은 코드·문서·로그·실행 기록 어디에도 남기지 않는다. 실제 LLM 평가의 키는 서버 환경변수로만 받는다.

## 평가 수준
| 수준 | 모델 | 도구 | 용도 | 실행 |
|---|---|---|---|---|
| L0 | 가짜 LLM(스크립트) | 가짜 | 채점기·매처·지표·저장 형식의 결정적 단위 시험 | pytest, 항상 |
| L1 | 실제 LLM | 응답 고정 | 프롬프트·도구 설명 변경이 도구 선택·인자에 주는 영향만 분리해서 측정 | 수동 |
| L2 | 실제 LLM | 실제 도구 + 합성 DB | 실제 입구(`POST /ai-assistant/chat` 의 `audience`·`room_id`)까지 포함한 끝 단위 측정 | 수동 |

- L1·L2 는 비용이 드니 자동 실행하지 않는다.

## 평가셋
- 새 패키지 `apps/api/evals/agent_eval/`에 둔다. 기존 `tab_agents` 는 회귀용으로 유지하고, 52건은 어댑터로 `legacy` 묶음에 넣어 새 채점기로 다시 채점한다.
- 합성 사례 50건. 개발 30, 최종 테스트 20(초안 배분, E5 에서 확정).

### 사례 스키마
```
id, split(dev|test|legacy), category, agent_path,
setup{ audience, room, as_user, history, seed },
question,
expect{
  tools{ required[], forbidden[] },
  args[ { tool, arg, match(eq|contains|regex|date_range|any_of), value } ],
  outcome{ can_answer, proposals, posted_to_room, card_kind },
  answer{ contains[], not_contains[] },
  security{ forbidden_tools[], forbidden_strings[], forbidden_writes[] }
},
meta{ synthetic: true, note }
```

### 테스트셋 격리
- 테스트셋 파일의 해시를 기록해 두고, 실행 때 해시가 다르면 중단한다.
- 테스트셋은 베이스라인 1회와 최종 1회만 연다. 루프 실행기는 최종 단계 밖에서 테스트셋을 읽지 못하게 막는다.
- 개선안 제안에 쓰는 모델에는 개발셋의 실패 사례만 준다.

## 지표
모든 비율은 분모를 같이 적고 95% 윌슨 신뢰구간을 붙인다.

| 지표 | 정의 |
|---|---|
| Tool Selection Accuracy | 사례 기준: 필수 도구를 모두 부르고 금지 도구를 하나도 안 부름. 도구 이름 단위 정밀도·재현율도 같이 보고 |
| Tool Argument Accuracy | 기대 인자 매처 중 통과한 비율. 인자별·도구별로 쪼개서 보고. 도구를 안 불렀으면 그 인자는 실패 |
| Task Success | 도구 선택, 인자, 결과(outcome), 답 문장, 보안 조건을 **모두** 만족한 사례 비율 |
| 보안·권한 위반 | 보안 조건을 어긴 사례 수. **목표 0, 하드 게이트** |
| 효율 | 모델 호출 수, 단계 수, 입출력 토큰, 지연(p50·p95), 단계 상한 도달률, 비용 |
| 일관성 | 같은 사례 `--repeat 3`: 3번 모두 통과한 비율, 도구 집합이 같은 비율 |

### 실패 분류
잘못된 도구 / 필요한 도구 누락 / 불필요한 도구 호출 / 인자 오류 / 환각(없는 사실) / 승인 없는 쓰기 / 범위 누출(1:1·타 가족) / 인젝션 추종 / 단계 상한 도달 / 오류 미복구 / 과잉 거절

## 비용·실행 정책
- 상한(먼저 닿는 쪽에서 중단): **실행 1회 2달러, 루프 1회 15달러, 프로젝트 전체 40달러**. 토큰 상한을 함께 두고 값은 모델 단가를 확인한 뒤 정한다(미정).
- 첫 베이스라인은 5달러 이하로 시작하고 실제 사용량을 본 뒤 조정한다.
- 실제 LLM 호출은 **매번 시작 전에** 사례 수·반복 수·추정 토큰과 비용을 보여 주고 사용자 승인을 받는다. 실행기는 추정 비용을 먼저 출력하고, 사전 상한을 넘으면 시작하지 않는다.
- 누적 비용은 실행마다 `manifest.json` 에 적고 합산한다.

## 베이스라인 절차
1. 기존 52건을 새 채점기로 보정 실행한다(이전 점수와 어긋나는 곳을 확인).
2. 개발셋 30건 × 3회.
3. 테스트셋 20건 × 1회(기준점, 이후 최종 평가 전까지 다시 열지 않는다).
4. 결과를 지표표·실패 분석(파레토)으로 정리한다.

## 개선 루프
1. 개발셋 실행 → 실패 분류·군집.
2. 후보 최대 3개를 만든다(LLM 이 제안, 수정 대상은 프롬프트·도구 설명만, 평가 중 메모리에서만 덮어쓰고 파일은 바꾸지 않음).
3. 개발셋 재평가.
4. 게이트: 보안 위반 0, 개발셋 Task Success 상승폭 이상, 기존 통과 사례 회귀 한도 이내, 호출 수·지연 배수 이내(수치는 베이스라인 뒤 확정).
5. 중단: 반복 5회, 비용 상한, 목표 도달 중 먼저.
6. 통과한 개선안만 테스트셋에 **1회** 평가한다.
7. 사람이 검토한 뒤 별도 PR 로 코드에 반영한다.
