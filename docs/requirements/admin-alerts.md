# 기능: 관리자 알림

## 목적
관리자가 서비스 이상 신호를 놓치지 않게, 기준을 넘은 상태를 알림 목록으로 보여 준다. 감시는 숫자 비교로만 하고 AI 는 새 알림이 생겼을 때 요약에만 쓴다(요약은 2단계 이후).

이번 1단계는 **틀과 첫 규칙 하나(서버 오류율)**까지다.
- 알림 기록 표, 규칙 명단, 점검 주소, 목록 주소, 확인 주소를 만든다.
- 규칙은 다섯 개를 등록한다: 서버 오류율(1단계), 처음 보는 서버 오류, 답 안 한 문의, AI 사용 급증, 승인 대기 참가 요청.
- 화면(관리자 페이지 메뉴)은 2단계, 5분마다 자동 호출(GCP Cloud Scheduler)은 3단계다. 1단계 코드는 주소를 두드리면 동작하지만 아직 아무도 두드리지 않는다.
- AI 요약은 1단계에 넣지 않는다.

## 화면
- 이번 단계 없음. 2단계에서 관리자 페이지 "운영 업무" 묶음에 "알림" 메뉴를 추가한다.

## API
- `POST /internal/alerts/run` (점검 주소)
  - 헤더 `X-Alert-Token` 이 설정된 토큰과 같아야 한다. 없거나 다르면 403 `forbidden`. 설정이 비어 있으면 항상 403(기본값).
  - 설정 `ADMIN_ALERTS_ENABLED` 가 꺼져 있으면 아무 일도 하지 않고 `{"checked": 0, "created": 0, "enabled": false}` 를 돌려준다.
  - 응답: `{"enabled": true, "checked": 점검한 규칙 수, "created": 새로 만든 알림 수}`
- `GET /admin/alerts` (목록 주소, 관리자만)
  - 응답: `{"items": [알림...], "unacked": 확인 안 된 개수}`
  - 알림 한 줄: `{"key", "rule", "severity", "message", "menu", "created_at", "acked_at"}`
  - 정렬: 확인 안 된 것 먼저, 같은 안에서는 최근 것 먼저. 한 번에 최대 50개.
- `POST /admin/alerts/{key}/ack` (확인 주소, 관리자만)
  - 확인 시각과 확인한 사람(사용자 id 가 아니라 "운영자" 표시)을 기록한다. 이미 확인된 것이면 기록을 바꾸지 않고 200 을 돌려준다.
  - 없는 key 는 404 `not_found`.
- 모두 `shared/errors.py` 의 공통 오류 형식을 따른다.

## 데이터
- 새 표 `admin_alert_log` (테이블 추가만, 기존 표는 건드리지 않는다)
  - `key` (문자열 120, 기본키): 지문. 예 `server_error_rate:2026-11-17T14` (규칙 이름 + 구간)
  - `rule` (문자열 60): 규칙 이름
  - `severity` (문자열 8): `긴급` · `주의` · `보통`
  - `message` (문자열 200): 숫자만 든 문구. 이름·이메일·사용자 id·오류 본문을 넣지 않는다.
  - `menu` (문자열 60): 확인할 메뉴 이름
  - `created_at` (시각, 기본 현재 시각)
  - `acked_at` (시각, 비어 있을 수 있음)
  - `acked_by` (문자열 40, 비어 있을 수 있음): 확인한 운영자 표시
- 점검 기준은 기존 `ops_request_metrics` 표를 읽는다(구간별 요청 수, 5xx 수). 새로 저장하지 않는다.

## 규칙 1: 서버 오류율
- 보는 것: 최근 60분의 요청 수와 5xx 수 (`ops_request_metrics`)
- 기준: 요청 20건 이상이고 5xx 비율이 5% 이상 → `긴급`, 1% 이상 → `주의`. 둘 다 아니면 알림 없음.
- 지문: `server_error_rate:<현재 시각을 시(時) 단위로 자른 값>` → 다음 시간이 되면 다시 알릴 수 있다.
- 문구 예: `최근 60분 서버 오류 6.2% (요청 320건 중 5xx 20건, 기준 5%)`
- 확인할 메뉴: `서버 상태`
- 숫자 기준은 설정이 아니라 규칙 코드의 상수다. 운영하며 바꿀 때는 코드를 고치고 이 문서를 함께 고친다.

## 규칙 2: 처음 보는 서버 오류
- 보는 것: `ops_error_events` 표. 서버 오류(`kind = server_error`: 5xx와 처리되지 않은 예외)만 본다. 401/403 같은 인증 실패는 보지 않는다.
- 기준: 최근 24시간에 처음 나온 **(오류 종류, 경로) 조합**이 있으면 `주의`. 그 전에 같은 조합이 한 번이라도 있었으면 새것이 아니다.
  - 오류 표의 지문(fingerprint)에는 가린 메시지가 섞여 있어서, 같은 종류·같은 경로여도 메시지가 다르면 줄이 따로 생긴다. 그래서 줄이 아니라 (종류, 경로) 조합으로 묶어서 본다.
  - 처음 본 시각(`first_seen`)은 줄이 처음 생길 때만 정해지고 다시 나도 바뀌지 않는다.
- 지문: `new_error:<종류와 경로를 섞은 짧은 해시 16자>`. 시간이 들어 있지 않아서 한 조합은 한 번만 알린다.
- 한 번 점검에 최대 10개(횟수가 많은 것 먼저). 배포가 크게 깨졌을 때 알림이 쏟아지는 것을 막는다. 10개를 넘는 것은 서버 상태 화면의 오류 목록에서 본다.
- 문구 예: `처음 보는 서버 오류 KeyError · /notices (3회)`. 오류 메시지 본문과 trace id 는 쓰지 않는다. 200자를 넘으면 자른다.
- 확인할 메뉴: `서버 상태`
- 알아 둘 것: 점검이 24시간 넘게 멈춰 있었다면 그 사이에 처음 나온 오류는 알리지 못한다.

## 규칙 3: 답 안 한 문의
- 보는 것: `support_tickets` 표. 상태가 `new`(새 문의) 또는 `working`(처리 중)인 줄. `done`(답변 완료)은 보지 않는다.
- 기준: 등록한 지 6시간이 넘은 줄이 1건 이상이면 `주의`.
- 지문: `stale_support:<한국 시간 날짜>`. 하루에 한 번만 알린다(같은 날 문의가 더 늘어도 새 알림은 만들지 않는다).
- 문구 예: `6시간 넘게 답이 없는 문의 2건 (가장 오래된 것 9시간째)`. 문의 제목·내용·작성자·가족은 쓰지 않는다.
- 확인할 메뉴: `문의 및 신고`

## 규칙 4: AI 사용 급증
- 보는 것: `ai_usage_logs` 표. 상태가 `nested`·`rejected`인 표식 줄은 뺀다(서비스 관리자 화면의 AI 요청 수와 같은 기준).
- 기준: 오늘(한국 시간 자정부터) 요청이 50건 이상이고 최근 7일 하루 평균의 3배 이상이면 `주의`. 평균은 오늘 이전 7일(한국 시간 자정 기준)의 합을 7로 나눈 값이다.
- 평균이 0이면(처음 쓰는 날, 예전 기록 없음) 오늘 50건만 넘어도 알린다. 서비스 초기에는 불필요한 알림이 날 수 있다.
- 지문: `ai_usage_spike:<한국 시간 날짜>`. 하루에 한 번만 알린다.
- 문구 예: `오늘 AI 요청 180건, 최근 7일 하루 평균 40건의 4.5배`. 가족·사용자는 쓰지 않는다.
- 확인할 메뉴: `기능·AI › AI`
- 알아 둘 것: 이 표에는 시간만으로 찾는 인덱스가 없다((가족, 시간)·(사용자, 시간)뿐). 기록이 많이 쌓이면 5분마다 도는 조회가 느려질 수 있어, 그때 인덱스 추가 마이그레이션을 따로 만든다.

## 규칙 5: 승인 대기 참가 요청
- 보는 것: `join_requests` 표. 상태가 `pending`(승인 대기)인 줄.
- 기준: 요청한 지 24시간이 넘은 줄이 1건 이상이면 `주의`.
- 지문: `stale_join:<한국 시간 날짜>`. 하루에 한 번만 알린다.
- 문구 예: `24시간 넘게 승인 대기 중인 가족 참가 요청 3건 (가장 오래된 것 30시간째)`. 가족 이름·신청자는 쓰지 않는다.
- 확인할 메뉴: `사용자 › 가족`

## 설정
- `ADMIN_ALERTS_ENABLED` (기본 `false`)
- `ADMIN_ALERTS_TOKEN` (기본 빈 값). `.env.example` 에 이름만 적는다. 실제 값은 서버 환경변수에만 둔다.

## 완료 조건
- 토큰이 없거나 틀리면 점검 주소가 403, 설정이 꺼져 있으면 아무 일도 하지 않는다.
- 같은 구간에 점검을 여러 번 불러도 알림 줄은 하나다(고유 키).
- 확인 주소를 두 번 불러도 결과가 같다.
- 관리자가 아니면 목록·확인 주소가 403 이다.
- 목록 응답에 이름·이메일·사용자 id·오류 본문이 없다.
- 규칙 기준선(20건 미만, 1%·5% 경계)을 시험한다.
- 처음 보는 서버 오류: 한 번만 알린다, 24시간 전에 있던 조합은 새것이 아니다, 메시지만 다른 줄은 한 조합으로 센다, 인증 실패는 무시한다, 한 번에 10개까지, 긴 이름도 기록표 칸에 들어간다, 문구에 오류 메시지·trace id 가 없다.
- 답 안 한 문의: 5시간 59분은 울리지 않고 6시간 넘으면 울린다, `new`·`working`만 센다(`done` 제외), 같은 날 다시 점검해도 한 번만, 문구에 제목·내용이 없다.
- AI 사용 급증: 50건 미만은 울리지 않는다, 평균의 3배 미만은 울리지 않는다, `nested`·`rejected` 줄은 세지 않는다, 평균이 0이어도 50건 이상이면 울린다.
- 승인 대기 참가 요청: 24시간 미만은 울리지 않는다, `pending`만 센다(승인·거절 제외), 같은 날 한 번만.
- 점검한 규칙 수는 5다.
- 표 추가는 Alembic 리비전 하나로만 하고, 점검 시 `alembic heads` 가 1개여야 한다.

## 미정
- 2단계 메뉴 이름을 "알림"으로 할지 "알림 센터"로 할지.
- 3단계 GCP Cloud Scheduler 설정을 누가 하는지(배포 담당자 허락 필요).
- 1% 주의 기준을 둘지(1단계 기본값으로 둠, 운영 후 조정).
- 규칙 3~5의 기준 숫자(6시간, 3배·50건, 24시간)는 제안값이다. 운영하며 조정하고, 바꿀 때는 `service_admin/alert_rules.py`의 상수와 이 문서를 함께 고친다.
- 문의 미응답에 `working`(처리 중)을 포함할지(기본: 포함).
