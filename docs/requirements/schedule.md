# 기능: 일정

## 목적
가족이 약속과 할 일을 한 곳에서 보고, 등록하고, 서로 확인한다. 일정 에이전트가 빠뜨린 것을 먼저 권해 준다.

## 용어
- 탭 이름과 총칭은 "일정", 형태는 "약속"(그날 그 시간에 일어나는 것)과 "할 일"(체크하면 끝나는 것). 약속의 체크는 "확인했어요", 할 일의 체크는 "완료했어요".
- 누구 = 나 말고 관련된 사람. 이름표(제목 앞)로 보이고 보낸·만든 사람이 아님. 안 고르면 내 일정(이름표 없음). 엄마+아빠는 "부모님"으로 합쳐 표시(저장은 개별).
- 주제 = 하나, 기본 선택 없음, 고르지 않으면 분류 없음. 기본 주제는 경조사, 나머지는 사용자가 만들고 색을 고름.
- 공유 = 보여줄 가족 구성원(계정 있는 사람만). 안 고르면 나만.
- 화면 글자에서는 "부탁"을 쓰지 않는다. "함께"는 영역·상태, "같이"는 동작.

## 화면
- 메인: 주간 스트립(+ 아이콘 → 달력), 오늘·내일 카드(체크 수 2/3), 일정·할 일 추가하기, 함께하기(같이하기), 먼저 권해드려요 카드, 채팅 입력.
- 달력: [달력 | 목록], 필터 두 줄(누구, 주제), 월 달력(점: 약속 복숭아 / 할 일 초록, 날짜당 최대 3개), 선택 날짜 목록.
- 등록: 형태 [약속 | 할 일]만 고르고 입력 항목은 같음. 제목(필수), 누구·주제·공유, 날짜(필수)·시간·장소, 메모. 날짜·시간은 시트로 선택. 저장하면 진입했던 화면으로 돌아감.
- 상세: 보기·수정·삭제. 수정·삭제는 만든 사람만. 삭제는 가운데 확인 팝업.
- 같이: 보내기, 받기, 현황(받은 | 보낸), 보낸 것 상세.
- 채팅: 하단 시트, 채팅 전용 화면, 기록.
- 화면별 상세 규칙은 프로젝트 위키 `schedule-*` 문서를 따른다.

## API
- 서버 일정은 사람마다 자기 줄(`user_id`)을 가진다. 앱은 우선 mock 데이터로 만들고, 서버 연동은 별도로 합의한다.
- `POST /schedule/events`: 제목과 시각(`start_date` + 선택 `start_time`·`end_time`, 또는 옛 방식 `starts_at`) 외에 형태 `kind`(1 약속·2 할 일), `place`, 누구 `who_ids`, `memo`(옛 이름 `note`), 공유 대상 `share_with`(가족 구성원 id 목록)를 받는다. 공유 대상을 고르지 않으면 나만 갖고, 고르면 그 사람마다 복사본이 생긴다. 구성원이 아닌 사람이 있으면 400 `invalid_share_target`.
- 복사본은 만들어진 뒤로는 받은 사람의 일정이다(`origin_id` 는 출처 표시일 뿐). 원본을 고치거나 지워도 복사본은 그대로이고, 복사본의 확인·삭제는 받은 사람이 자기 줄에서 한다.
- `GET /schedule/events`: 내 줄만 준다(삭제된 것 제외). 주인이 없는 옛 일정(`user_id` 없음)은 그룹 전체가 본다.
- `POST /schedule/events/{id}/confirm`: 내 줄만 확인한다.
- `PUT /schedule/events/{id}/checked`: 요청 `{checked: true|false}`. 내 줄의 확인(약속)·완료(할 일) 표시를 정한다. 같은 값을 다시 보내도 그대로이고, 내 줄이 아니거나 지워진 일정은 404. 체크는 각자 자기 줄에서 하고(공유받은 복사본은 따로), 일정을 고친 것이 아니라서 `edited_at` 은 바뀌지 않는다.
- `DELETE /schedule/events/{id}`: 그 줄의 주인만 지운다(삭제 시각 `deleted_at` 만 채움). 주인이 아니면 403 `not_owner`, 내 줄이 아니면 404.
- `PATCH /schedule/events/{id}`: 그 줄의 주인만 고친다(아니면 403 `not_owner`, 내 줄이 아니거나 지워진 것은 404). 바꿀 값만 보낸다: `title`, `start_date`, `start_time`, `end_time`, `kind`, `place`, `memo`, `who_ids`. 보내지 않은 값은 그대로이고, 시간(`start_time`·`end_time`)은 `null` 로 보내면 지운다(시간 없음, 시작이 없어지면 끝도 없어진다). 끝나는 시간이 시작보다 늦지 않으면 400 `invalid_time`, 보낸 값이 하나도 없으면 400 `nothing_to_update`. 고친 시각 `edited_at` 을 남기고 옛 컬럼(`starts_at`·`note`)도 맞춘다. 공유 대상은 고칠 수 없다. 원본을 고쳐도 복사본은 그대로이고, 복사본은 받은 사람이 자기 줄에서 고친다.
- `GET /schedule/events/{id}/sharing`: 읽기 전용, 저장 없이 그때그때 계산한다. 응답 `{shared_by, shared_with}`. 복사본이면 `shared_by` 는 원본 주인(원본이 지워졌어도), 아니면 `null`. `shared_with` 는 원본에서 나온 모든 복사본 주인의 id(받은 사람이 자기 복사본을 지웠어도 남고, 나도 받은 사람이면 포함). 공유 안 한 일정은 `[]`. 내 줄이 아니거나 없으면 404.
- 주제는 사람마다 자기 것이다. 이름(`name`, 30자)과 색(`color`, 지금은 `rose`·`amber`)을 가진다. 기본 주제 "경조사"는 사람마다 처음 목록을 읽을 때 만들고, 지운 뒤에는 다시 만들지 않는다. 같은 사람의 지우지 않은 주제끼리는 이름이 겹칠 수 없다.
  - `GET /schedule/topics`: 내 주제 목록(지운 것 제외). `POST /schedule/topics`: `{name, color}` 로 만든다. 이름이 겹치면 409 `topic_exists`.
  - `DELETE /schedule/topics/{id}`: 내 주제만 지운다(`deleted_at` 만 채움). 그 주제를 붙였던 내 일정은 `topic_id` 를 비운다.
  - 일정 `POST`·`PATCH` 는 `topic_id` 를 받고 일정 응답에도 `topic_id` 가 있다. `PATCH` 에서 `null` 이면 주제를 지운다. 없거나 지웠거나 남의 주제면 400 `invalid_topic`. 공유 복사본에는 주제를 붙이지 않는다.
- 옛 컬럼(`starts_at`·`note`·`created_by`·`status`)은 당분간 새 컬럼과 함께 채운다. 제거는 별도 PR(담당자 승인 후).
- 에이전트(`POST /schedule/agent`)도 호출한 사람의 일정만 읽는다.
- `GET /schedule/suggestions`: 응답 `{suggestions: [{id, title, kind, start_date, place}], exhausted}`. 추천은 참고용이고 사람마다 하루 최대 3묶음(LLM 3회, 한 묶음 = 같은 `created_at` 의 제안 최대 5개)까지 만든다. 오늘(서버 로컬 날짜) 만든 대기 제안이 있으면 AI 를 부르지 않고 그것을 돌려주고, 없을 때만 새로 만든다. 오늘 3묶음을 다 만들었으면 빈 목록과 `exhausted: true` 를 준다(다음 날 다시 만든다). 모델에는 내 일정(지난 2주~앞으로 60일)의 제목·날짜·시간만 보내고(개인정보는 가림, 가족 이름은 보내지 않음), 결과는 오늘~60일 안의 날짜만 받고 이미 있는 일정·제안과 같은 것은 버린다. AI 를 부를 때만 동의(403 `ai_not_enabled`)와 카드 한도(429)를 본다. 채팅의 `recommend` 의도도 같은 공급을 써서 `suggestion` 카드로 답한다.
- `POST /schedule/events` 에 `suggestion_id` 를 보내면 그 제안(내 대기 제안만, 아니면 400 `invalid_suggestion`)으로 등록한 것으로 보고, 일정에 연결하며 제안을 확정한다(같은 트랜잭션). 공유 복사본에는 연결하지 않는다.
- 같이해요(부탁). 보낸 사람은 `events_requests.user_id`, 받는 사람은 `events_request_recipients` 줄들이다. 응답 `RequestOut` = `{id, from_id, title, start_date, start_time, end_time, place, memo, created_at, canceled, recipients: [{user_id, status: waiting|accepted|declined}], my_event_id}`. 받는 사람 목록은 보낸 사람·받는 사람 누구나 전부 보고(어렵겠어요 포함), `my_event_id` 는 호출한 사람이 수락해서 만든 지워지지 않은 일정 id 다. 그룹 밖 사람은 보지 못한다(404).
  - `POST /schedule/requests`: `{title, start_date, start_time, end_time, place, memo, to_ids}` → 201. 받는 사람은 1~20명(중복은 하나로), 나는 뺀다, 모두 같은 가족 구성원이어야 한다(아니면 400 `invalid_recipients`). 시간 규칙은 일정과 같다(시작 없이 끝 불가, 끝이 시작보다 늦지 않으면 400 `invalid_time`).
  - `GET /schedule/requests`: 내가 보냈거나 내가 받는 사람인 부탁, 만든 시각 내림차순(같으면 id).
  - `POST /schedule/requests/{id}/answer`: `{answer: accepted|declined, kind: 1|2|null}`, 받는 사람 본인만(아니면 404). 수락이면 `kind` 필수(400 `kind_required`). 수락하면 받는 사람 본인의 일정만 만든다: `user_id`·`created_by` 는 수락한 사람, `source: "request"`, `who_ids` 는 `[보낸 사람]`, 제목·날짜·시간·장소·메모는 부탁 그대로이고 보낸 사람에게는 일정을 만들지 않는다. 종일(00:00~23:59) 부탁을 할 일로 수락하면 시간은 비운다. 이미 답한 사람이 다시 답하려면 부탁 날짜가 지나지 않아야 한다(400 `answer_locked`, 첫 답은 날짜와 무관). 다른 `kind` 로 다시 수락하면 이전에 만든 일정을 소프트 삭제하고 새로 만들고, 어렵겠어요로 바꾸면 그 일정을 소프트 삭제한다. 취소된 부탁에는 답할 수 없다(400 `request_canceled`).
  - `POST /schedule/requests/{id}/cancel`: 보낸 사람만(받는 사람이면 403 `not_owner`). 수락한 사람이 있으면 400 `already_accepted`(앱의 "답을 기다리는 동안만"과 같다). 이미 취소한 것은 그대로 200. `canceled_at` 만 채우고 이미 만들어진 일정은 지우지 않는다.

## 데이터
- 항목: 형태, 제목, 날짜(필수), 시작·종료 시간(선택), 종일, 장소(직접 입력), 메모, 누구(여러 명), 주제, 공유 대상, 만든 사람, 확인·완료 여부.
- 목록 순서: 약속 먼저(종일 → 시간순), 그다음 할 일(시간순, 시간 없는 것은 마지막).
- 누구가 비어 있으면 필터·에이전트에서는 만든 사람 본인으로 본다(저장 값은 공백).

## 완료 조건
- 앱: mock 데이터로 위 화면의 흐름이 동작하고 `npm run lint` 통과.
- 서버 연동은 서버 변경 합의 후.

## 미정
- 확인·완료 상태를 사람별로 둘지, 공유받은 사람의 수정 권한, 삭제 후 되돌리기, 반복 일정의 수정·삭제 범위.
- 할 일에도 종일을 넣을지(장소는 약속과 같이 넣기로 함), 반복·알림·첨부, 장소 지도 서비스.
- 기한이 지났는데 완료하지 않은 할 일의 표시 방식.
- 같이: 자동 마감 시점·재알림, 다른 시간 제안, 현황 진입 위치.
- 채팅: 기록 삭제·보관 기간, 대화에서 바로 체크 처리 여부, 빠른 질문 칩 구성, 시트→전체 화면 전환 시점.
- 먼저 권해드려요 카드 노출 개수·순서, 제안을 미리 만들어 저장하는 구조(호출 비용).
- 약속·할 일·주제 색(디자인 토큰 미정의).
- 메인 오케스트레이터와의 입출력 형식, 일정 에이전트 설계.
