# 기능: 운영 관리자 페이지 + AI Operations Agent (admin)

> 상태: **초안 (2026-11-02, 운영자 인증 결정 반영)**. 구현하지 않았다. "미정" 항목은 확인받기 전에 임의로 정하지 않는다.
> 작성 근거: 유님의 요청서·결정(2026-11-02)과 저장소 확인. 저장소에서 확인한 사실은 "확인됨", 요청서·구두 설명만 있는 것은 "미확인"으로 표시한다. 운영자 인증은 아래 "운영자 인증" 절에서 확정/제안/미정으로 나눠 적는다.

## 목적
운영자가 서버·인프라·API 상태를 한 곳에서 보고, 오류를 추적·처리하고, 자연어로 운영 데이터를 물어 장애를 분석할 수 있다.

**범위 밖 (다른 담당자가 개발 중이라 만들지 않는다):** 사용자·가족 그룹·테스터 관리, 가입 승인, 가족 데이터 열람. 이 문서의 모든 화면·API·Agent는 **가족의 개인 데이터(가계, 사진, 위치, 돌봄, 채팅·AI 대화 원문, 이름·이메일)에 접근하지 않는다.** 필요해지면 이 문서를 고친 뒤 별도로 확인받는다.

**역할 경계(확정 8차, 유님 설명):** 서비스 관리자 페이지 = 사용자가 가비를 어떻게 이용하는지, 서비스가 어떤 상태인지 관리. 운영 관리자 페이지(이 문서) = 가비를 구성하는 서버와 시스템이 잘 작동하는지 관리. 경계가 겹치는 지표의 소속은 "확정 8차" 표(제안, 미정) 참고.

## 운영자 인증

### 확정 (유님이 정함, 2026-11-02)
1. 운영 관리자 페이지의 운영자는 유님 1명이다.
2. 운영자 식별 기준은 **사용자 id**이다.
3. 인증은 **기존 JWT 로그인을 재사용**한다.
4. 서비스 관리자 페이지(주님)도 식별 기준을 사용자 id로 맞춘다.
5. 공통 검증 함수 PR은 유님이 먼저 올린다.
6. 허용 목록 변경은 유님이 환경변수를 바꿔서 한다.
7. 운영 관리자 화면은 **별도 웹**으로 제작한다 (앱 마이 탭 안이 아님).
8. 경로·폴더는 운영 관리자와 서비스 관리자를 분리하는 방향이다 (구체 이름은 아래 제안).
9. 허용 목록은 id로 우선 둔다.
10. **주님이 동의했다** (유님 전달, 2026-11-02). 동의 대상은 이 절에 적힌 운영자 인증 구성(아래 "제안")이다. 주님 본인의 확인 기록은 저장소에 없다(미확인). 동의한 구성의 개별 항목을 바꾸게 되면 주님과 다시 맞춘다.

### 유님 설명 기준 (저장소로 확인하지 못함 — 미확인)
- 주님은 서비스 관리자 페이지를 맡았고 아직 개발을 시작하지 않았다.
- 운영자 인증 조율은 위 확정 10(주님 동의)으로 끝났다. 협업 전달용 문서는 dev-docs `wiki/howto/gabee-operator-auth-handoff.md`.
- `gabee.cloud` 도메인은 가비아에서 구매했고 Cloudflare에 연결되어 있다.
- GCP 계정의 소유자는 주님이고 관리는 유님이 하고 있다. scope 분리의 목적은 "주님이 인프라를 못 건드리게 하는 것"이 아니라 코드와 서버 판단에서 두 scope가 섞이지 않게 하는 것이다. 팀 역할 위키의 "주님: 인프라 계정에서 변경"이 가리키는 변경은 확인하지 못했다(미확인).

### 확정 2차 (유님이 "위 최선안으로 확정"이라고 함, 2026-11-02)
아래 항목은 확정이다. 항목 안에 "미정"·"미확인"이라고 쓴 부분(서브도메인, Cloudflare Access, 서비스 관리자 쪽 폴더 이름 등)은 확정에 포함되지 않는다. 요구사항 문서 확인 전에는 구현하지 않는다.
- **공통 검증 함수**: `shared/auth.py`에 `require_operator(scope)`를 한 곳에만 둔다. 이유: 검증 로직이 두 벌이면 한쪽만 고쳐져 보안 구멍이 생길 수 있고, 정책 변경과 테스트가 한 번으로 끝나며, 나중에 허용 목록을 DB로 옮겨도 호출부를 안 바꿔도 된다.
- **JWT만 인정**: 같은 파일에 JWT 전용 `bearer_user`가 이미 있다(확인됨: 2026-11-02, 파일 읽기). `require_operator`는 이를 기반으로 하고, 익명 계정용 레거시 `X-Gyeot-Token`은 받지 않는다.
- **scope**: `ops_admin`(운영 관리자), `service_admin`(서비스 관리자). 서로 자동 포함하지 않는다. 이유: 최소 권한, 서비스 관리자는 가족 데이터에 더 가까움, 계정 유출 시 영향 범위 제한. 한 사람이 둘 다 맡으면 두 목록에 같은 id를 넣는다.
- **허용 목록 변수**: `<SCOPE>_ADMIN_USER_IDS` 형식 (`OPS_ADMIN_USER_IDS`, `SERVICE_ADMIN_USER_IDS`), 쉼표 구분(앞뒤 공백 제거, 빈 항목 무시, 정확히 일치할 때만 통과), 비어 있거나 설정이 없으면 아무도 허용하지 않음(fail-closed). `config.py`와 `.env.example`에 추가하고, 실제 id 값은 문서·커밋·seed에 넣지 않는다.
- **가족 역할과 무관**: `group_members.role`(owner/admin)이어도 허용 목록에 없으면 403. 이유: 가족 그룹은 누구나 만들 수 있어서, 가족 역할을 운영자 권한으로 인정하면 가족을 만드는 것만으로 권한 상승이 된다.
- **경로·폴더**: 운영 관리자 `app/features/ops_admin/` + `/admin/ops/*`, 서비스 관리자 `app/features/service_admin/` + `/admin/service/*`(후자의 이름은 주님이 정함). 서로의 내부 파일을 import하지 않는다.
- **별도 웹 폴더**: `apps/ops-admin/` (`apps/invite-page`처럼 `apps/` 아래). 새 앱 폴더이므로 구현 전에 계획을 보여주고 확인받는다.
- **허용 목록 저장**: 1차는 환경변수. 로컬은 `.env`에 로컬 계정 id, 운영은 Cloud Run 환경변수 또는 Secret Manager에 운영 계정 id. DB 테이블(`operators`)은 운영자가 늘거나 권한 단계가 필요할 때 로컬 → Alembic 마이그레이션 → 통합 절차로 추가한다. DB 방식의 주의점: 마이그레이션은 구조만 옮기고 데이터는 옮기지 않음, 마이그레이션 파일·seed에 실제 사용자 id를 넣지 않음, 공용 DB 반영은 Pull Agent 수동 실행으로만, 첫 운영자를 넣는 절차가 따로 필요.
- **서브도메인**: `ops.gabee.cloud` 같은 서브도메인을 DNS 레코드로 붙이는 방안. 이름과 웹 호스팅 위치(Cloudflare Pages / Cloud Run)는 미정.
- **Cloudflare Access**: 웹 화면 보호용 보조 수단이다. 최종 판단은 항상 JWT + 허용 목록이 한다. Cloud Run 주소로 API를 직접 호출할 수 있는지와 Access 무료 사용 범위는 미확인.
- **허용 목록은 호출 시점에 읽기**: `require_operator`가 `settings`에서 호출 때마다 읽는다(모듈 로드 시 굳히지 않음). 이유: 테스트에서 값을 바꾸기 쉽다.
- **공통 함수 PR 리뷰**: 확정 4차에서 변경 — 유님이 직접 리뷰하고 별도 리뷰어는 두지 않는다(아래 "확정 4차"). 이전 내용: 작성자(유님)가 아닌 사람이 리뷰, 지정은 유님.
- **감사 로그**: 쓰기 기능이 들어가는 2단계에 함께 넣는다(보관 기간은 미정).
- **허용 목록 DB 이전 시점**: 운영자가 늘거나 권한 단계가 필요해질 때.
- **테스트 기준(구현 시)**: 토큰 없음 401 / 허용 목록 비어 있음 403 / 목록에 없는 사용자 403 / 가족 owner·admin이어도 목록에 없으면 403 / `ops_admin` id로 `service_admin` 접근 403 / 레거시 토큰 거부.

### 작업 범위 규칙 (확정, 2026-11-02)
1. `shared/auth.py`, `shared/config.py`, `.env.example`의 운영자 관련 부분은 공통 함수 PR이 병합되기 전까지 주님이 수정하지 않는다. 필요한 변경은 유님에게 요청한다.
2. 아래 PR은 유님이 권한·데이터 범위를 리뷰한다: 서비스 관리자 페이지가 보여주는 데이터 종류가 정해지거나 바뀌는 PR, 접근 권한을 거는 방식이 정해지거나 바뀌는 PR.
3. 그 밖의 일반 화면·로직 작업은 `CONTRIBUTING.md`의 기존 규칙(작성자가 아닌 1명 리뷰)대로 한다.
4. 공통 함수 PR 병합 후에는 각자 자기 scope와 폴더에서 개발한다.
5. 브랜치는 `release/1.2`에서 `feature/<이름>-<주제>`로 만들고 PR의 base는 `release/1.2`다. 요구사항 문서가 정해지기 전에는 구현하지 않고, 새 엔드포인트에는 테스트를 최소 1개 함께 쓴다.
※ 확정 6차: 서비스 관리자·운영 관리자 PR의 리뷰는 규칙 2·3 대신 유님이 한다(해석, 아래 "확정 6차" 참고).
상세 전달본: dev-docs `wiki/howto/gabee-operator-auth-handoff.md`.

### 추가 제안: 허용 목록 변경 절차와 권한 코드 세부 (2026-11-02, A·B는 제안, C의 1~6번은 확정 3차에서 확정)
이번 요청도 "확정 범위"에 적힌 항목이 없어 아래는 **전부 제안**이다. 위에서 이미 확정으로 올린 같은 이름의 항목은 유님 확인 전에는 상태를 바꾸지 않았고, 달라지는 부분만 마지막 목록에 모았다.

#### A. 허용 목록 변경 절차 (제안)
- 허용 목록 변수는 이미 분리돼 있다: `OPS_ADMIN_USER_IDS`, `SERVICE_ADMIN_USER_IDS`.
- 서비스 관리자 쪽 목록도 **1차에는 유님이 환경변수로 변경**한다. 주님의 변경 요청은 드물 것이고 목록은 사용자 id 몇 개뿐이라 부담이 작다. (일반 규칙 "허용 목록 변경은 유님이 환경변수로"는 확정 6번과 같다.)
- 각자 따로 환경변수를 설정하는 안은 1차에는 쓰지 않는다. 이유: 환경변수는 같은 Cloud Run 서비스에 있어 편집 권한이 서비스 단위일 가능성이 크고(**미확인**), yaml로 한꺼번에 덮어쓰면 서로의 변수를 지울 수 있으며, 변경마다 새 리비전이 생기고, 변경 이력 추적이 어렵다. (yaml 등록과 리비전 관련 기록: 위키 `troubleshooting/gabee-gcp-env-registration`)
- 변경 요청이 잦아지거나 주님에게 인프라 권한을 줘야 하는 상황이 오면 시크릿 분리(Secret Manager) 또는 DB 이전을 **그때 정한다(미정)**. 사용자 id는 코드·Git·문서에 남기지 않고 메신저 등으로 전달한다.

#### B. 유님 설명 기준 (저장소로 확인하지 못함 — 미확인)
- GCP 계정의 소유자는 주님이고, 관리는 유님이 하고 있다.
- 따라서 scope 분리의 목적은 "주님이 인프라를 못 건드리게 하는 것"이 아니라, **코드와 서버 판단에서 `ops_admin`과 `service_admin`이 섞이지 않게 하는 것**이다.
- 팀 역할 위키의 "주님: 인프라 계정에서 변경"이 어떤 변경을 가리키는지는 확인하지 못했다(미확인).

#### 확정 4차 (유님 답변, 2026-11-02)
유님의 답을 다음과 같이 해석해 반영했다.
- **확정 — 공통 함수 PR은 유님이 직접 리뷰한다. 공통 PR의 별도 리뷰어는 두지 않는다.** 이는 확정 2차·3차의 "작성자(유님)가 아닌 사람이 리뷰, 지정은 유님"을 **대체**한다. 이 결정은 `CONTRIBUTING.md`의 "리뷰어는 작성자 본인이 아닌 사람", "CI 통과 + 팀원 1명 리뷰 승인"에 대한 **예외**다. 팀이 이 예외에 합의했는지는 미확인이다. 리뷰 체크 5가지(scope 섞임 / 비어 있을 때 차단 / 가족 역할 미사용 / 레거시 토큰 거부 / 값이 코드·`.env.example`에 없음)는 유지한다.

- 팀장 리뷰 가능 여부(미확인)는 더 이상 필요하지 않다.

#### 확정 11차 (유님: "위 권장안으로 결정", 2026-11-02) — 1번 PR(`require_operator`) 설계 4가지
1. **테스터 동의 검사는 작은 헬퍼 함수로 뽑아 `current_user`와 `require_operator`가 함께 쓴다.** 이유: 조건이 한 곳에만 있어 나중에 어긋나지 않는다. 주의: 기존 `current_user` 코드를 고치므로 동의 검사 동작이 그대로인지 기존 테스트로 확인한다.
2. **검사 순서는 `bearer_user` 인증 → 허용 목록 확인 → 테스터 동의 검사**(허용 목록 먼저). 이유: 운영자가 아닌 사람은 동의 여부와 상관없이 항상 같은 403을 받는다.
3. **운영자가 아닐 때의 오류 코드는 `operator_required`(HTTP 403)**. 허용 목록의 내용·크기는 응답에 드러내지 않는다.
4. **알 수 없는 scope는 `require_operator(scope)`를 만들 때 바로 `ValueError`로 처리한다**(요청이 올 때가 아님). 이유: 오타를 서버 시작 시점에 발견한다.
- 기존 확정과의 관계: 충돌 없음. 확정 4차(테스터 동의 검사 포함)와 확정 2차·3차(한 곳 배치, 호출 시점 읽기, 403 비노출)를 구체화한 것이다.
- 1번 PR의 나머지 계획(변경 파일 4개, 테스트 안)은 **승인 대기**이고 구현은 시작하지 않았다.

#### 확정 12차 (유님 답변, 2026-11-02)
- **최선안 표는 확정 5차를 유지한다(표 전체 확정).** 요청서의 빈 "확정 범위" 칸은 표의 확정 상태에 영향을 주지 않는다.
- **3번 PR 이후 항목은 3번 PR 착수 전에 다시 묻는다**: 지표·오류 보관 기간, 집계 구간, 심각도 기준, 오류 담당자 표기(사용자 id 또는 라벨), 웹 차트 방식(외부 스크립트 금지 전제), ADR 번호. 그때까지 임의로 정하지 않는다.

### 미정 (임의로 정하지 않는다)
위 "최선안 표"에 제안값이 있는 항목도 확정 전까지는 미정으로 둔다.
- (정리됨) 서비스 관리자 쪽 허용 목록 변경은 유님이 환경변수로 한다 — 확정 5차
- 서비스 관리자의 경로·폴더 이름, 별도 웹 기술(순수 HTML / React), 호스팅 위치
- 서브도메인 사용 여부와 이름, Cloudflare Access 사용 여부
- **감사 로그**: 운영자가 누가·언제·어떤 운영 API를 호출하거나 무엇을 바꿨는지 남기는 기록(개인정보·응답 내용은 저장하지 않음, 새 테이블이라 Alembic 필요). 2단계에 함께 넣는 것은 위에서 확정했고, 보관 기간만 미정.
- 별도 도메인 사용 시 서버 CORS 설정을 좁힐지 (코드상 기본값은 `*`로 보임, 운영 설정은 미확인)

## 화면 (관리자 웹, 별도 웹으로 확정 — 기술·폴더·호스팅은 "최선안 표"에서 확정 5차로 확정)
이동: 운영 대시보드 ↔ 인프라 ↔ 오류·로그 ↔ API 상태 ↔ 배포·DB ↔ AI 운영 Agent

1. **운영 대시보드**: 전체 상태, 서비스별 상태 카드, 요청 수·성공률·실패율·평균 응답 시간, 시간별 요청·오류 추이, 서비스별 응답 시간, 최근 오류·배포·장애
2. **인프라**: Cloudflare Workers / Cloud Run / FastAPI / Supabase(PostgreSQL)별 상태·요청 수·응답 시간·오류율·인스턴스·DB 연결, 최근 인프라 이벤트
3. **오류·로그**: 필터(기간·오류 유형·API·심각도) 목록, 상세(시간, 유형, 메시지, endpoint, status, 횟수, Trace ID, 처리 상태, 담당자, 조치 내용), 처리 상태 변경
4. **API 상태**: Workers·FastAPI·Supabase·Claude API별 연결 상태·응답 시간·호출 수·성공/실패·오류율, Claude 토큰 사용량(비용은 추정)
5. **배포·DB**: 배포 일시·버전·성공 여부·담당자·배포 후 오류 변화, DB 연결·쿼리 오류·응답 시간·백업(지원되는 경우). **DB 수정 기능 없음**
6. **AI 운영 Agent**: 자연어 질문 → 아래 형식으로 응답

### 승인된 목업 구성 (유님 "진행", 2026-11-03)
원본: `dev-docs/raw/2026-11-03-ops-screen-structure.md`. 목업(비공개, 가짜 수치): https://claude.ai/artifact/GbYsH7RVuDNU6LW6KsUKGM. 확정은 **"승인된 목업 구성"까지**이고, 위 6개 목록을 대체하지 않는다(세부가 다른 곳은 아래 "목록과 다른 점" 참고).

공통 원칙
- 목업 띠와 "샘플" 표기로 가짜 값을 구분한다. 수집하지 않는 지표는 숫자 없이 "수집 안 함"/"확인 전"으로 둔다.
- 사용자·가족 id, 대화 내용을 보이지 않는다. API는 경로 패턴으로만 집계한다.
- 화면에서 바꿀 수 있는 것: 오류 처리 상태·담당자·조치 메모, 배포 기록 수동 추가. DB·서버 설정 변경은 없다.

화면(6개, 왼쪽 메뉴로 이동)
1. 운영 대시보드: 요청 수·성공률·실패·평균 응답, 시간별 추이, 서비스별 상태(출처 표시), 최근 오류·배포
2. 인프라: FastAPI·DB 상태(저장소 안 수집), Cloud Run·Cloudflare는 "수집 안 함"(2단계), 최근 인프라 이벤트(빈 상태 포함)
3. 오류·로그: 필터(기간·유형·API·심각도·상태), 묶음 목록(횟수), 상세(Trace ID 등), 상태·담당·메모 저장
4. API 상태: 경로 패턴별 요청·성공률·오류율·응답·마지막 확인, Claude 사용량(비용은 단가 설정 후 추정), 인증 실패율(비율만)
5. 배포·DB: 수동 배포 이력, DB 연결·스키마 준비·응답 시간·쿼리 오류, 백업은 수집 안 함, 읽기 전용
6. AI 운영 Agent: 질문 → 요약/확인된 사실/추정/추가 확인/권장 조치, 사용한 조회 표시, 읽기·분석만

목록과 다른 점(유님 확인 필요 — 위 기존 목록은 고치지 않았음)
- 2번: 기존은 Cloudflare Workers/Cloud Run별 상태·인스턴스까지 적었으나, 목업은 1단계에서 "수집 안 함".
  - **갱신(유님 "진행", 2026-11-03)**: Cloud Run 인스턴스 상태는 1단계로 당기는 방향으로 승인. 단 실제 연결은 "인스턴스 상태를 1단계로 당기는 검토"의 확인 항목 1~3이 끝난 뒤이고, 그 전에는 "확인 전"으로 표시. Cloudflare는 확인 항목 5 전까지 "수집 안 함" 유지. (확정 13차에 따라 목업 자체는 인스턴스를 반영하지 않고 진행)
- 4번: 기존은 Workers·FastAPI·Supabase·Claude별 연결 상태, 목업은 경로 패턴별 집계 + Claude 사용량 + 인증 실패율.
- 1번: 기존의 "서비스별 응답 시간"·"장애", 5번의 "배포 후 오류 변화"는 목업 요약에 없음. 5번 "백업(지원되는 경우)"은 목업에서 "수집 안 함".

미정 유지: 차트 방식(외부 스크립트 금지 전제), 글꼴, `apps/ops-admin/` 계획 확인(폴더 생성 전).

### 인스턴스 상태를 1단계로 당기는 검토 (2026-11-03, 유님 요청 — 전부 제안·미확인, 기존 확정은 아직 바꾸지 않음)
기존 확정 9차는 Cloud Run·Cloudflare 지표를 "수집 안 함(2단계)"으로 두었다. 이 절은 1단계로 당길 수 있는지 보는 **검토안**이고, 유님이 아래 "바뀌는 문서 항목"을 확인하기 전에는 다른 절을 고치지 않는다.

#### 1. 확인 항목과 순서 (결과는 모두 미확인, 유님이 알려 주면 기록)
| 순서 | 확인할 것 | 방법(제안) | 현재 상태 | 이 결과로 갈리는 것 |
|---|---|---|---|---|
| 1 | 부여된 역할 이름과 범위(프로젝트 Owner인지, IAM 관리만인지) | GCP 콘솔 IAM 화면의 본인 행(역할 목록), 또는 IAM 관리 권한이 있다면 프로젝트 IAM 정책 조회 | **미확인** | 서비스 계정을 만들고 역할을 줄 수 있는지(2번 설계안의 전제) |
| 2 | Cloud Run 서비스 이름·리전·CPU 할당 방식(요청 중에만/항상)·최소·최대 인스턴스 | Cloud Run 콘솔의 서비스 상세(현재 리비전 설정) | **미확인** | 지표 해석(CPU 할당이 "요청 중에만"이면 요청 밖 CPU는 의미가 달라짐), 요청 계측 집계를 요청 중에 flush해야 하는지(기존 미확인 항목) |
| 3 | Cloud Monitoring·Cloud Logging·Cloud Run 조회 API 사용 설정 여부 | 콘솔 "API 및 서비스 > 사용 설정된 API"에서 Monitoring API, Cloud Run Admin API(조회용), Logging API 확인 | **미확인** | 꺼져 있으면 켜는 일이 프로젝트 변경이라 소유자(주님)와 먼저 합의 |
| 4 | "GCP 소유자는 주님" 합의를 바꿔도 되는지 | 유님이 주님께 직접 확인하고 답을 알려 줌(Claude는 주님 의견을 추정하지 않음) | **미확인**(주님 의견 없음) | 합의가 유지되면 서비스 계정 생성·API 활성화는 주님과 같이 진행 |
| 5 | Cloudflare 지표용 API 토큰을 유님이 만들 수 있는지 | Cloudflare 대시보드 > 내 프로필 > API 토큰에서 "읽기 전용"(분석 읽기) 템플릿이 만들어지는지. 계정 소유자가 다르면 계정 멤버 권한 확인 | **미확인** | Cloudflare 지표를 1단계에 넣을지 (아래 3번 표는 GCP 쪽 지표만 다룸) |

권장 순서: 1 → 2 → 3(조회만, 변경 없음) → 4(사람 확인) → 5. 1~3은 화면을 보는 것뿐이라 바로 가능하고, 4가 정해지기 전에는 API 활성화·서비스 계정 생성 같은 **쓰기 작업을 하지 않는다**.

#### 2. 읽기 전용 서비스 계정 설계안 (제안)
- **계정**: 이 용도 전용 서비스 계정 1개(예: `ops-admin-reader`, 이름은 미정). 사람 계정과 섞지 않는다.
- **역할(최소, 조회 전용·쓰기 없음)** — 후보이며 실제 역할 이름과 필요 권한은 구현 전에 GCP 문서로 다시 확인한다(미확인):
  - `roles/monitoring.viewer`: Cloud Monitoring 지표 조회(인스턴스 수·CPU·메모리·지연)
  - `roles/run.viewer`: Cloud Run 서비스·리비전 설정 조회(최소·최대 인스턴스, 리비전 목록)
  - Cloud Logging 조회 역할(`roles/logging.viewer`)은 **1단계에서 주지 않는다**. 요청·오류 로그에 가족 식별자나 요청 내용이 섞여 있을 수 있어 가림 규칙이 먼저 필요하다(오류 로그 연동은 기존대로 2단계).
  - 프로젝트 전체가 아니라 가능하면 **해당 프로젝트 범위에서 위 두 역할만**. Owner/Editor/IAM 관리 역할은 주지 않는다.
- **키 보관**: 서비스 계정 키(JSON)를 쓰는 경우 Secret Manager에만 두고, 서버는 그 비밀을 읽어서 쓴다. 코드·`.env.example`·문서·커밋·로그에 값을 넣지 않는다(`.env.example`에는 시크릿 **이름**만 비워 둔 주석). 서버가 Secret Manager 값을 읽는 계정(`secretAccessor`)은 **그 비밀 하나에만** 준다.
- **키 없는 대안(검토 필요)**: API가 도는 Cloud Run 서비스의 실행 계정에 위 조회 역할을 붙이면 키 파일이 필요 없다. 다만 그러면 API 서버 전체가 GCP 조회 권한을 갖게 되어 확정 9차("읽기 전용 서비스 계정·토큰을 Secret Manager 보관")와 다르다. 어느 쪽으로 할지는 **미정**이고 유님이 정한다.
  - (2026-11-03 공식 문서 확인, 근거는 아래 5장) 키 없는 방식은 **확인됨**: Cloud Run 서비스 ID(서비스 계정)에 역할을 붙이면 클라이언트 라이브러리가 ADC로 메타데이터 서버에서 토큰을 받는다. 역할 후보 `roles/monitoring.viewer`(`monitoring.timeSeries.list` 포함)와 `roles/run.viewer`는 **쓰기 권한이 없음이 확인됨**(단 둘 다 지표·서비스 설정 외 읽기도 포함하므로 "조회 전용"이지 "최소"는 아님). 주의: 서비스 ID는 서버 전체가 공유하고, 현재 서비스 계정이 기본 Compute Engine 계정(Editor일 수 있음)인지 **미확인**이며, 로컬 개발 PC의 ADC 로그인이 있으면 개인 계정이 쓰일 수 있고, 나중에 키 방식으로 바꿀 때 `GOOGLE_APPLICATION_CREDENTIALS`는 문서가 권하지 않는다(5-3).
- **유님 관리자 계정은 서버에 넣지 않는다**(요청 사항). 서버가 쓰는 것은 위 서비스 계정뿐이다.
- **로컬 개발**: GCP에 연결하지 않는다. 키가 없으면 해당 지표는 "수집 안 함"으로 표시(기존 원칙 그대로).
- **키 관리**: 만든 사람·날짜·교체 주기는 정하지 않았다(미정). 키 유출 의심 시 키를 폐기하고 새로 만든다는 절차만 제안한다.
- **어댑터 위치(제안)**: `app/features/ops_admin/`의 읽기 전용 어댑터. 호출 실패·권한 없음·API 꺼짐은 오류가 아니라 "수집 안 함/확인 전"으로 표시한다. 외부 SDK·의존성 추가가 필요하면 먼저 제안하고 확인받는다(의존성 임의 추가 금지).

#### 3. 인스턴스 상태 지표 후보 (제안, 출처 구분)

표기: **확인됨**은 공식 문서에서 본 것이다. **미확인**은 못 찾았거나 문서마다 다르거나 기억에 의존해야 하는 것이다. 문서 주소는 `cloud.google.com`에서 `docs.cloud.google.com`으로 옮겨져 있었다(301). 아래 "문서 이름"은 그 사이트의 제목이다.

**5-1. Cloud Run 지표 (Cloud Monitoring)** — 확인됨: 2026-11-03, "Google Cloud metrics: Cloud Run 지표 목록"(Monitoring API 지표 페이지의 `run.googleapis.com` 절), "Cloud Run 모니터링" 문서의 핵심 지표 표
| 항목 | 지표 이름(`run.googleapis.com/` 뒤) | 종류·값 형식 | 단위 | 라벨 | 상태 |
|---|---|---|---|---|---|
| 인스턴스 수(활성/유휴) | `container/instance_count` | GAUGE, INT64 | `1` | `state`(active/idle) | GA |
| CPU 사용률 | `container/cpu/utilizations` | DELTA, DISTRIBUTION | `10^2.%` | 없음 | GA |
| 메모리 사용률 | `container/memory/utilizations` | DELTA, DISTRIBUTION | `10^2.%` | 없음 | GA |
| 요청 수 | `request_count` | DELTA, INT64 | `1` | `response_code`, `response_code_class`, `route`(항상 빈 값) | GA |
| 요청 지연 | `request_latencies` | DELTA, DISTRIBUTION | ms | 위와 같음 | GA |

- **샘플링 주기·반영 지연(확인됨)**: 위 지표 목록의 Cloud Run 지표는 "60초마다 샘플링, 샘플링 뒤 최대 120초까지 보이지 않을 수 있음"으로 적혀 있다. 그래서 화면 값은 최대 몇 분 늦을 수 있다고 표시해야 한다.
- **보관 기간**: Monitoring 할당량·한도 문서에는 24개월(사용자 지정·외부·에이전트·Prometheus/OTLP·워크로드 지표, Compute Engine·GKE·Cloud Storage·BigQuery·Cloud SQL·부하 분산기 대부분)과 6주("그 밖의 모든 지표 유형")만 있다. Cloud Run은 24개월 목록에 이름이 없지만 "그 밖"이라고 명시한 문장도 못 봤다 → **미확인**(6주로 추정, 단정하지 않음).
- **재시작 횟수**: 지표 목록에서 재시작·충돌·인스턴스 시작 횟수를 직접 주는 지표를 **찾지 못함(미확인)**. 관련 지표로 `container/instance_count_with_readiness`(BETA, 상태 UNKNOWN/HEALTHY/UNHEALTHY), `service_health_count`(BETA), `container/startup_latencies`(BETA)가 있으나 "재시작"을 뜻한다고 문서가 말하지 않는다. 대체는 3번 표의 "인스턴스 수 변화로 추정" 또는 앱이 시작할 때 `ops_*`에 한 줄 기록(저장소 안 수집)이다.
- **미확인**: CPU·메모리 사용률 분포를 어떻게 계산하는지(문서에서 설명을 못 찾음), 지표 리소스 종류의 정확한 이름(목록에는 "revision"으로 표기됨).

**5-2. 최소 IAM 역할** — 확인됨: 2026-11-03, "Access control for Cloud Monitoring"(Monitoring 접근 제어), "Cloud Run IAM roles"(Cloud Run IAM 역할 참조)
| 역할 | 확인된 내용 | 쓰기 권한 | 비고 |
|---|---|---|---|
| `roles/monitoring.viewer` | `monitoring.timeSeries.list` 포함(지표 조회에 필요). 문서 설명: "모든 모니터링 데이터와 설정을 읽는(get, list) 권한" | **없음**(나열된 권한이 전부 get/list) | 지표 외에 대시보드·알림 정책·업타임 체크·SLO·그룹·알림 채널 읽기와 `resourcemanager.projects.get/list`도 포함 → 지표만 읽는 데는 **충분하지만 최소는 아님** |

CPU 할당 방식은 `template.containers[].resources.cpuIdle`("요청 중에만 CPU를 할당할지, 기본값 true")이다. 리비전 수준 `template.scaling`의 하위 필드는 이 조사에서 확인하지 못했다(미확인).

**5-3. 키 없는 방식(Cloud Run 실행 계정에 역할 부여)** — 확인됨: 2026-11-03, "Cloud Run 서비스 ID(Service identity)", "Application Default Credentials 동작 방식"
- **방법**: 서비스 ID는 리비전을 배포할 때 지정한 서비스 계정이다. 지정하지 않으면 Compute Engine 기본 서비스 계정(`PROJECT_NUMBER-compute@developer.gserviceaccount.com` 형식)을 쓴다. 문서는 사용자 관리 서비스 계정을 만들어 필요한 권한만 주는 것을 권장한다.
- **키 없는 인증**: 클라이언트 라이브러리는 ADC로 인스턴스 메타데이터 서버에서 서비스 ID의 OAuth 토큰을 받는다(키 파일 불필요). 직접 호출할 때는 메타데이터 서버의 `/service-accounts/default/token` 경로에서 액세스 토큰을 받는다(경로는 문서 확인, 호스트 주소는 이번에 확인하지 못함). ADC 탐색 순서: ① `GOOGLE_APPLICATION_CREDENTIALS`가 가리키는 파일 ② `gcloud auth application-default login`이 만든 로컬 파일 ③ 연결된 서비스 계정(메타데이터 서버).
- **서버 전체가 갖는 권한 범위**: 서비스 ID는 그 서비스의 모든 인스턴스가 쓰는 하나의 ID라서, 조회 역할을 붙이면 **API 서버의 모든 코드**(가족 기능 포함)가 같은 조회 권한을 갖는다(문서의 서비스 ID 설명에서 읽히는 해석). 그래서 어댑터를 `ops_admin` 안에만 두고 조회 외 권한을 붙이지 않는 것은 코드 규율이지 GCP가 막아 주는 것이 아니다.
- **주의 1 — 현재 서비스 계정 확인 필요(미확인)**: 문서는 기본 서비스 계정이 조직 정책에 따라 프로젝트 **Editor 역할**을 자동으로 받았을 수 있다고 경고하고, 그 경우 덜 넓은 역할로 바꾸라고 권한다. 지금 API가 어떤 계정으로 도는지 모르므로(확인 항목 추가: 아래 6번), 조회 역할을 붙이기 전에 먼저 본다. 기본 계정이 Editor라면 조회 역할 추가는 의미가 없고 계정 정리가 먼저다.
- **주의 2 — 로컬 개발**: ADC는 로컬 파일(②)도 쓰므로, 개발 PC에 `gcloud auth application-default login`이 되어 있으면 서버가 개인 계정 자격으로 GCP를 읽을 수 있다. 2번 설계안의 "유님 관리자 계정은 서버에 넣지 않는다", "로컬 개발은 GCP에 연결하지 않는다"와 어긋날 수 있다. 제안: 어댑터를 명시적 설정으로만 켜고(기본 꺼짐, 이름 미정) 로컬에서는 자격 증명 조회 자체를 하지 않는다.
- **주의 3 — 나중에 키 방식으로 바꿀 때**: Cloud Run 문서는 서비스 ID를 쓰는 서비스에 `GOOGLE_APPLICATION_CREDENTIALS`를 설정하지 말라고 한다. 키 방식으로 전환한다면 환경변수 방식이 아니라 Secret Manager 값을 읽어 명시적 자격 증명으로 쓰는 설계가 되어야 한다(전환 방식은 유님이 정함, 미정).

**5-4. 사용 설정이 필요한 API** — 확인됨: 2026-11-03, "Cloud Monitoring API 사용 설정", Cloud Run Admin API REST 참조
- Cloud Monitoring API: 서비스 이름 `monitoring.googleapis.com`. 문서는 "사용하기 전에 사용 설정해야 한다"고 한다. **기본으로 켜져 있는지는 문서에서 못 찾음(미확인)**.
- Cloud Run Admin API: REST 호스트가 `run.googleapis.com`(`https://run.googleapis.com/v2/...`)이다. 서비스 이름 문서를 따로 확인하지는 않았다. Cloud Run이 이미 배포돼 있어 켜져 있을 가능성이 높지만 **미확인**.
- Cloud Logging API는 1단계에서 읽지 않으므로 켜지 않는다.
- **켜는 권한(확인됨)**: `serviceusage.services.enable`. 프로젝트를 만든 Owner(`roles/owner`) 또는 `roles/serviceusage.serviceUsageAdmin`에 있다.
- 소유자(주님)와 합의가 필요한지는 **GCP 문서의 사항이 아니라 팀 합의의 사항**이다. 확정 13차: 소유자 합의는 필요할 때 유님이 요청한다.

**5-5. 호출 방법·의존성·제한·비용**
- **REST 지표 조회(확인됨: "projects.timeSeries.list" 참조)**: `GET https://monitoring.googleapis.com/v3/{name}/timeSeries`, `name`은 `projects/[PROJECT_ID_OR_NUMBER]`. `filter`(필수)는 **지표 유형 하나만** 지정해야 한다. `view`는 필수. `pageSize`는 비어 있거나 100,000을 넘으면 100,000으로 처리한다. OAuth 스코프는 `cloud-platform`, `monitoring`, `monitoring.read` 중 하나. 응답이 200MB를 넘으면 `RESOURCE_EXHAUSTED`(HTTP 429). 정렬 기간·`perSeriesAligner` 값의 의미와 최소 정렬 기간은 해당 페이지에서 읽지 못했다(**미확인**).
- **REST 서비스 조회(확인됨: "services.get" 참조)**: `GET https://run.googleapis.com/v2/{name}`, 스코프 `cloud-platform`.
- **토큰 얻는 법(확인됨)**: Cloud Run에서는 메타데이터 서버에서 서비스 ID의 액세스 토큰을 받는다(5-3).
- **의존성(확인됨)**: 서버 `pyproject.toml`에 `httpx>=0.27`이 **이미 있다**. 그래서 메타데이터 토큰 + `httpx`로 REST를 부르면 **새 의존성 없이** 가능하다(토큰 만료·재발급 처리는 우리 코드). 공식 라이브러리를 쓰면 Python 패키지 `google-cloud-monitoring`(문서 확인, ADC 지원 확인)이 추가된다. 그 하위 의존성 목록과 Cloud Run Admin용 패키지 이름은 확인하지 못했다(**미확인**). 제안: 1단계는 `httpx` + 메타데이터 토큰으로 하고, 라이브러리 도입은 유님이 확인한 뒤에 정한다(의존성 임의 추가 금지).
- **호출 횟수 제한**: Monitoring 할당량 문서에 `timeSeries.list`의 분당·초당 한도 숫자가 **없다**. 문서는 할당량 대시보드(콘솔)에서 보라고 한다(**미확인**).
- **비용(부분 확인)**: 가격 페이지 본문은 가져오지 못했고(본문 잘림), 검색 결과 요약 기준으로 2025-10-02부터 쓰기 API 호출은 무료, 읽기 API 호출은 **반환된 시계열 100만 개당 $0.50, 결제 계정당 첫 100만 개 무료**로 읽힌다. 콘솔에서의 읽기는 무료. 옛 문서에는 호출 수 기준 모델이 남아 있어 구현 전에 가격 페이지를 다시 본다. Cloud Run 시스템 지표 자체의 비용은 확인하지 못했다(**미확인**). 제안: 필터·집계로 반환 시계열 수를 줄이고, 샘플링 주기(60초)보다 짧게 부르지 않는 캐시를 둔다.

**5-6. Cloud Run CPU 할당 방식** — 확인됨: 2026-11-03, "Cloud Run 결제 설정(CPU 할당)", "컨테이너 런타임 계약"
- 요청 기반(기본, `cpuIdle` 기본값 true): "CPU는 요청을 처리하는 동안에만 할당된다". 인스턴스 기반: "인스턴스 수명 전체에 CPU가 할당된다", "요청 처리 밖에서도 CPU를 할당한다".
- 인스턴스 수명: 최소 인스턴스가 없으면 요청 처리 후 15분 넘게 유휴로 두지 않는다. 유휴 인스턴스는 최소 인스턴스여도 언제든 종료될 수 있다. 종료 시 SIGTERM을 보내고 10초 뒤 SIGKILL(2세대는 SIGTERM 처리기 설치를 권고, 1세대는 처리하지 않으면 즉시 종료).
- **미확인**: ① CPU 사용률 지표가 두 방식에서 어떻게 달라지는지(Monitoring 문서에서 못 찾음). ② 요청 기반에서 요청이 없을 때 백그라운드 작업(요청 계측 flush)이 "제한된다"는 직접 문장은 못 찾았다. 인스턴스 기반과의 대비 문장만 있다. 따라서 "요청 밖에서 flush가 보장되지 않는다"는 해석은 확인이 아니라 **추정**이다.
- 설계 시사점(제안, 미검증): 요청 계측은 요청 처리 중에 일정 간격으로 flush하고, 종료 때 SIGTERM 처리기에서 마지막으로 한 번 flush(10초 안)하는 안을 검토한다. 현재 서비스의 CPU 할당 방식은 확인 항목 2번 결과를 기다린다.

## 데이터 (제안 — 확정 전, 새 테이블은 모두 Alembic 리비전)
- `ops_request_metrics`: 시간 구간별 집계(경로 패턴, 메서드, 상태코드 구분, 요청 수, 지연 합·최대). **요청 건별 저장이나 본문·쿼리·헤더 저장은 하지 않는다.**
- `ops_error_events`: 시각, 유형, 가린 메시지, endpoint 패턴, status, 횟수, trace id, 심각도, 처리 상태, 담당(운영자 식별자), 조치 메모. 메시지·스택은 개인정보 가림 후 저장, 사용자·그룹 id는 저장하지 않는다.
- `ops_incidents`, `ops_deployments`: 장애·배포 기록
- `ops_audit_logs`: 운영자가 무엇을 조회·변경했는지(누가, 언제, 어떤 API). 응답 내용은 저장하지 않는다.
- `ops_docs`, `ops_doc_chunks`: 운영 문서와 pgvector 조각(기존 임베딩 모델 384차원 재사용 여부는 미정)
- 요청 계측은 요청마다 DB에 쓰지 않고 프로세스 메모리에 모아 주기적으로 반영하는 방식을 제안한다(멀티 워커 정합성은 설계 시 확인).
- 삭제·이름·타입 변경은 없다. 새 테이블 추가만이라 `destructive-approved`는 필요 없다. 공용 DB에는 직접 적용하지 않고 격리 PostgreSQL에서만 검증한다.

## AI Operations Agent
- 하나의 Agent + 조회 Tool로 시작하고, 필요할 때 전문 Agent로 나눈다.
- Tool(전부 **읽기 전용**): 인프라 상태, API 지표, 오류 검색·요약, 배포 전후 비교, 운영 지식 검색.
- LLM은 Tool이 돌려준 데이터를 분석·설명할 뿐 수치를 만들지 않는다. 호출은 `shared/llm` 래퍼로만 한다.
- 응답 형식: ① 질문 요약 ② 조회한 데이터·출처·조회 시각 ③ 확인된 문제 ④ 가능한 원인(추정) ⑤ 추가 확인 항목 ⑥ 권장 대응. **조회 결과와 추정을 구분**하고 근거 없는 원인을 단정하지 않는다.
- 서버 재시작·DB 변경·배포 같은 위험 작업은 Agent가 실행하지 않는다. 필요하면 권장 대응에 적기만 한다(승인 후 실행은 후속 단계에서 별도 설계).
- Agent에 보내는 데이터는 집계·가린 오류 메시지뿐이고, 가족 데이터·원문은 보내지 않는다.

## RAG (4단계)
문서 등록 → 청킹 → 임베딩 → pgvector 저장 → 유사 검색 → Claude 답변. 대상은 인프라 구성, API 명세, 배포 가이드, 운영 매뉴얼, 장애 대응 기록, 오류 해결 사례. 실시간 로그는 RAG가 아니라 API/DB로 조회하고, 반복해서 쓸 만한 사례만 정리해 지식베이스에 추가한다. 가족 대화·개인정보가 든 문서는 등록하지 않는다(등록 전 가림 처리).

| 3 | API·DB 설계 | `/admin/ops/*` 명세, `ops_*` 테이블, 운영자 권한 규칙 | 스키마·엔드포인트 확정, `permissions.md`·`db.md` 초안, ADR 1건(번호는 `git fetch` 후 최대 번호 + 1) | 운영자 인증 미정(감사 로그), 로그 보관 기간 | 운영자 인증은 일부 확정(위 절), 나머지 제안·확정 전 |
| 4 | 화면 구성 | 6개 화면(대시보드·인프라·오류·API·배포/DB·Agent) | 별도 웹 목업, "수집 안 함"·빈 상태 포함 | 웹 폴더·기술·호스팅, 서브도메인 | 위치는 별도 웹으로 확정, 나머지 시작 전 |
| 5 | 실제 데이터 연동 | 요청 계측(1-b), 오류 수집(1-c), 외부 플랫폼 읽기 어댑터, 배포·장애 기록 | 지표마다 수집 가능한 것만 연결, 개인정보 가림 테스트 | 2~3단계 결정 | 시작 전 |
| 6 | Agent·LLM | 조회 Tool 5종 + 단일 Agent, 6단계 응답 형식, 일일 요약 | `shared/llm` 래퍼 사용, 호출 한도, 출처·조회 시각 표시, 평가 사례 | Agent 한도·모델·기록 저장 여부 | 시작 전 |
| 7 | RAG | 운영 문서 수집→검색→답변, 장애 사례 정리 | `ops_docs`·`ops_doc_chunks`, 문서 가림 처리 | RAG 원본 문서·등록 방법 | 시작 전 |

단계 1~3은 구현 없이 문서로 끝나고, 4단계부터 코드가 생긴다. 4단계 전에 3단계 결정(특히 화면 위치·운영자 식별)이 필요하다.

## 완료 조건
- 운영자가 아닌 사용자와 토큰 없는 요청은 `/admin/ops/*`에서 401/403이다(테스트).
- 어떤 응답·로그·Agent 입력에도 가족 개인정보가 없다(테스트로 확인).
- 수집하지 않는 지표는 수치 대신 "수집 안 함"으로 보인다.
- Agent 응답에 출처와 조회 시각이 있고, 조회 결과와 추정이 구분된다.
- 새 테이블은 단일 Alembic head, 격리 PostgreSQL 전체 upgrade, 스키마 일치 검증을 통과한다.
- `openapi.json`과 `docs/contracts/db.md`, `docs/features/ops-admin.md`를 갱신한다.

## 미정 (Claude는 아래를 임의로 정하지 않고 확인받는다)
운영자 인증 관련 미정은 위 "운영자 인증 > 미정" 절에 있다(서비스 관리자 폴더·웹 기술, 서브도메인·Cloudflare Access, 감사 로그, 허용 목록 DB화 시점, CORS). 그 밖의 미정:
1. **외부 연동 권한**: Cloud Run·Cloudflare·Supabase·GCP 지표를 읽을 API 토큰/서비스 계정을 쓸 수 있는가, 어디에 보관하는가. 없으면 해당 항목은 수집 안 함으로 둔다. 실제 구성(AWS 이전 계획 포함) 확인 필요.
2. **Claude API 상태 확인 방식**: 실제 호출 프로브는 비용이 든다. 호출 결과 기반 집계만 쓸지, 주기적 최소 호출을 둘지. 비용 계산용 단가 출처.
3. **운영 로그 보관 기간**, 가족에게 "운영자가 조회했음"을 알릴 필요 여부(감사 로그 결정과 함께).
4. **오류 저장 방식**: 앱(클라이언트) 오류까지 받을지, 서버 오류만 받을지. Sentry·Cloud Logging 같은 외부 도구 사용 여부.
5. **배포 이력**: GitHub Actions 결과를 가져올지, 수동 입력할지, Cloud Run 리비전에서 읽을지. 배포 담당자 정보 출처.
6. **알림**: 운영 알림 채널(앱 푸시, 메일, 메신저), 임계값.
7. **Agent 한도**: 운영자별 하루 호출 한도, 사용 모델(기본 `claude-haiku-5-5` 유지 여부), 질문·답변 기록 저장 여부.
8. **운영 문서 RAG 원본**: 어떤 문서를 넣을지, 등록 방법(파일 업로드 / 저장소 `docs/` 동기화), 기존 임베딩 모델 재사용 여부.
9. **위험 작업 승인 절차**: 재시작·배포 등을 후속 단계에서 지원할 때의 승인 방식(지금은 범위 밖).
10. **운영자 권한 단계**(보기/변경 분리): 운영자 1명이라 1차는 단일 scope(`ops_admin`)로 두는 것이 제안이며, 분리 여부는 미정.
11. **`permissions.md`에 "서비스 운영자" 절을 쓸지**: 유님에게 먼저 묻는다(아직 쓰지 않음).

## W2 서버 연결, CSP, CORS (2026-11-04, 유님 "이어서 진행")
> 확정 18차로 호스팅이 Cloud Run 같은 서비스로 바뀌었다. 아래 Cloudflare Pages `_headers`·`CORS_ORIGINS` 항목은 배포 방식이 정해진 뒤 다시 본다(같은 출처가 되면 CORS 변경이 필요 없을 수 있음 — 미검증).
**구현됨(로컬 커밋, 푸시 전)**
- 서버: `feature/hojenn-ops-read-api`(worktree `gabee-ops-api`) — `GET /admin/ops/summary`, `GET /admin/ops/apis`(읽기 전용, `require_operator("ops_admin")`, 기간 1h/24h/7d, `metrics_enabled` 포함, p95 없음). 요청 계측 브랜치 위에 쌓았고 `release/1.2`를 병합했다. 병합으로 Alembic head가 둘이 되어 요청 지표 리비전의 `down_revision`을 옮겼다(내용 불변).
- 웹: `feature/hojenn-ops-admin-web` `47736c4` — 서버 모드(JWT 로그인 → 운영자 확인 → 대시보드·API 상태에 실제 지표). 인프라·오류 로그·배포/DB는 저장 테이블·API가 없어 샘플을 섞지 않고 "미연결"로 표시. 배포본은 샘플 계정 파일이 없어 항상 서버 모드.
- 검증(이 PC): 로컬 SQLite + 실제 uvicorn으로 로그인·403·지표 조회·경로 패턴 집계(원본 주소 `unmatched`로 묶임)를 curl로 확인, 가짜 DOM 통합 시험 12개 통과, 샘플 모드 시험 41개 통과. **실제 브라우저·모바일·다크 모드, 실제 PostgreSQL, 운영 서버(api.gabee.cloud) 연결은 미확인.**

**CSP (확정 방향, 적용은 배포 때)** — *재검토 대상: 확정 18차로 호스팅이 바뀌어 아래 Pages `_headers`·`api.gabee.cloud` 기준 항목과 CORS 는 배포 방식 확정 뒤 다시 본다(문장은 기록으로 남김).*
- meta: `connect-src`를 `'self'`, 로컬 개발 주소, `https://api.gabee.cloud`로 제한(기존 `https:` 전체 허용 제거).
- 배포본: Cloudflare Pages `_headers`로 `connect-src 'self' https://api.gabee.cloud`, `frame-ancestors 'none'`, `nosniff`, `no-referrer` 적용. meta와 헤더는 함께 적용되어 더 좁은 쪽이 이긴다. Pages 동작은 **아직 배포하지 않아 미확인**.
- 남은 완화: `style-src 'unsafe-inline'`(화면 코드가 style 속성을 씀). 제거하려면 인라인 스타일을 클래스로 옮기는 별도 작업이 필요.

**CORS (제안, 운영 변경은 운영 담당자 몫)**
- 근거: 첨부 문서(2026-11-04 curl) — `api.gabee.cloud`는 임의 출처에 `*` 응답. 코드는 이미 `CORS_ORIGINS`로 좁힐 수 있어 **코드 변경 없음**.
- 이 PC에서 `CORS_ORIGINS`를 특정 출처로 둔 로컬 서버로 확인: 허용 출처는 `access-control-allow-origin`이 그대로 오고, 그 밖의 출처 preflight는 400.
- 제안 값: `https://ops.gabee.cloud`(+ 운영에서 앱 웹을 쓰면 그 출처). 적용·되돌리기 절차는 첨부 문서 5장(변경 전후 `curl -X OPTIONS`, 문제 시 `*`로 복귀)을 따른다. **운영 `CORS_ORIGINS` 현재 값, Cloud Run 여부, Expo 웹 운영 출처는 미확인.**
- 주의: 이 설정은 API 전체에 공통이라 브라우저로 API를 부르는 다른 클라이언트에 영향을 준다.

## 확정 18차 — 운영 웹 호스팅을 기존 Cloud Run 서비스에 얹는 것으로 변경 (유님 "기존에 Cloud Run 서비스에 얹어", 2026-11-03 결정 · 2026-11-04 기록, 적용 확인 2026-11-04)
근거: dev-docs `wiki/decisions/gabee-admin-page-2026-11.md` 34장. 유님이 "별도 정적 호스팅(추천) vs 같은 서비스"의 장단점을 듣고 직접 고른 결정이다.

**변경**: 확정 5차 "최선안 표"의 호스팅(Cloudflare Pages)을 **대체**한다. 운영 웹(`apps/ops-admin/`의 정적 파일)은 기존 앱 서비스(Cloud Run)와 같은 서비스에 함께 배포하고, 서브도메인(`ops.gabee.cloud` 제안)을 그 서비스에 붙인다.

**유지**: 별도 웹 폴더 `apps/ops-admin/`, 순수 HTML+JS(TypeScript 금지), 최종 인증 판단은 JWT + 허용 목록(Cloudflare Access는 보조), 경로 `/admin/ops/*`.

**알려 준 장단점**: 장점 = 배포 대상이 하나, 같은 출처라 CORS 불필요. 단점 = ① 운영 화면만 고쳐도 API 전체 재배포 ② `apps/api/Dockerfile`이 `apps/api` 안의 파일만 복사하므로 `apps/ops-admin/`을 이미지에 넣으려면 빌드 방식 변경 필요 ③ Cloudflare Access는 호스트 이름 단위라 `*.run.app`·기존 도메인으로도 화면 파일에 접근 가능(화면 파일에 비밀은 없고 데이터는 JWT·허용 목록이 막지만 한 겹 약해짐).

**참고(확인함)**: `release/1.2`의 `main.py`는 서비스 관리자 화면을 같은 서비스에서 정적 파일로 내려준다(`app/features/admin/static`을 `/admin/ui`로 마운트). 운영 웹을 같은 방식으로 얹을 때 경로 충돌은 확인하지 못했다(`/admin/ops/*` API와 `/admin/ui`는 달라 보이지만 미검증).

**미정 (구현 전 설계·확인 필요, 임의로 정하지 않는다)**
1. 정적 파일을 서버가 내려주는 방식과 경로(접두사 또는 호스트 이름 기준). 서비스 관리자 `/admin/ui` 방식을 따를지.
2. 이미지에 `apps/ops-admin/`을 넣는 방법(Dockerfile 빌드 방식 변경 또는 복사 방법). `Dockerfile`·`deploy/`·`.github/workflows/`는 요청 없이 수정하지 않는 영역이라 유님 요청과 계획 확인 후에만 건드린다.
3. 서브도메인 호스트로 들어온 요청이 가족용 API 전체에도 닿는 문제. 호스트별로 경로를 제한할지(제안: 운영 호스트는 `/admin/ops/*`와 화면 파일만 허용).
4. Cloud Run 기본 주소·기존 도메인으로 운영 화면에 접근되는 것을 막을지(**미확인**: 앱 서비스가 Cloudflare를 거치는지, Cloud Run 도메인 매핑이 가능한지).
5. 운영 웹 변경이 API 배포와 묶이므로 운영 웹 변경은 API 배포 일정(deploy/kang 기준)에 맞춘다.

**로컬 확인으로 알게 된 사실 (2026-11-05, 근거: dev-docs `wiki/decisions/gabee-admin-page-2026-11.md` 35장)**
- 현재 서버 경로와 운영 웹 정적 파일 경로(`/`, `/css`, `/js`, `/index.html` 등)는 **충돌하지 않는다**(1번 관련).
- 폴더를 통째로 마운트하면 `_headers`, `README.md`, `*.example.js` 까지 밖으로 노출된다 → 마운트 범위나 제외 규칙이 필요(1번 관련).
- `js/config.js` 는 빈 `apiBase`(같은 출처 상대 경로)를 지원하지 않는다 → 같은 출처로 가려면 코드 변경이 필요(별도 PR).
- 보안 헤더(`frame-ancestors`, `nosniff`, `no-referrer`)는 Pages `_headers` 대신 FastAPI 쪽에서 붙여야 하며 **아직 구현되지 않았다**.
- 빌드 컨텍스트가 `./apps/api` 라서 `apps/ops-admin/` 은 지금 이미지에 **들어가지 않는다**(2번 관련).

**이미 병합된 것에 미치는 영향 (제안, 미검증)**: `apps/ops-admin/_headers`(Pages 전용)는 같은 서비스 배포에서는 쓰이지 않는다. 같은 출처가 되면 `connect-src 'self'`만으로 충분해지고 운영 `CORS_ORIGINS` 변경은 필요 없을 수 있다. 정리는 배포 방식이 정해진 뒤 별도 PR로 한다.

## 서비스 관리자와의 경계 (2026-11-05, 유님과 논의 · 근거: `docs/features/admin.md`, `app/features/admin/router.py` 를 읽은 결과, 실제 화면은 열어 보지 않음)

운영 관리자(`ops_admin`)와 서비스 관리자(`service_admin`, 담당 kang, `/admin/ui`)는 권한을 서로 포함하지 않는다. **→ 권한은 확정 19차로 하나(`admin`)로 합쳐짐(문장은 기록으로 남김).** 서비스 쪽은 회원·가족 그룹·기능(최근 7일 사용 수)·AI 이용·문의 및 신고를, 운영 쪽은 요청 지표·API 경로·오류 이벤트(·인프라)를 본다. 개인 데이터는 서비스 쪽에만 둔다.

| 찾으려는 것 | 가는 곳 |
|---|---|
| 사용자가 신고·문의했다 | 서비스 관리자 (문의 및 신고) |
| 서버가 느리다·5xx 가 많다·새 오류 | 운영 관리자 (대시보드, 로그/오류) |
| 특정 회원·가족 문제 | 서비스 관리자 (회원, 가족 그룹) |
| AI 사용량·비용 | 서비스 관리자 (AI 이용) |
| 인스턴스·배포·원문 로그 | GCP 콘솔 |

- 운영 쪽에 **만들지 않는 것**: 회원·가족 화면(개인 데이터), AI 사용량 화면(서비스 쪽과 중복), GCP 콘솔과 같은 인프라 상세 화면.
- 겹침이 작은 항목: 기능별 사용량(서비스: DB 행 수 / 운영: 경로별 요청 수)은 단위와 목적이 달라 둘 다 둔다. 문의 및 신고와 오류 이벤트는 같은 문제의 두 면이므로 연결(링크)만 검토한다.
- 나중에 검토: 로그인·첫 화면·메뉴를 하나로 묶고 권한은 그대로 나누는 통합 셸. **→ 확정 19차로 대체됨(권한도 하나로 합침).** 서비스 화면 쪽 변경(서로 가는 링크 등)은 담당(kang)과 상의한다.

## 확정 19차 — 권한을 통합관리자 하나로 바꾸고, 통합관리자 페이지는 kang 이 작성 (kang 결정, 2026-11-06 · 유님 확인 필요)

**변경**: 확정 2차의 scope 2개(`ops_admin`·`service_admin`, 서로 자동 포함하지 않음)와 허용 목록 2개(`OPS_ADMIN_USER_IDS`·`SERVICE_ADMIN_USER_IDS`)를 **대체**한다.
- scope 는 `admin` 하나, 허용 목록은 `ADMIN_USER_IDS` 하나다. 서비스 관리(`/admin/service/*`)와 운영 관리(`/admin/ops/*`) API 가 모두 `require_operator("admin")` 을 거친다.
- 서비스 관리자 화면과 운영 관리자 화면은 로그인 하나, 메뉴 하나(홈·서비스·운영·설정)로 합친다. 통합관리자 페이지는 kang 이 작성한다.

**유지**: `shared/auth.py` 한 곳의 `require_operator(scope)`, 사용자 id 기준, JWT 재사용, fail-closed(목록이 비면 아무도 통과 못 함), 가족 역할과 무관, 403 `operator_required`, 테스터 동의 검사 순서. 알 수 없는 scope(예전 이름 포함)는 의존성을 만들 때 `ValueError`.

**이유**: 관리자가 서비스·운영을 함께 보고, 로그인·메뉴를 하나로 합치기로 했다. 확정 2차가 scope 를 나눈 이유(최소 권한, 계정 유출 시 영향 범위)는 목록을 꼭 필요한 사람으로 짧게 두는 것으로 대신한다.

**배포 순서(중요)**: ① 운영 서버(Cloud Run) 환경변수에 `ADMIN_USER_IDS` 를 먼저 넣는다 → ② 코드 배포 → ③ 예전 `OPS_ADMIN_USER_IDS`·`SERVICE_ADMIN_USER_IDS` 를 지운다. ①을 빼고 배포하면 목록이 비어 아무도 관리자 화면에 들어가지 못한다(예전 이름은 더 읽지 않는다).

**미정**: `apps/ops-admin/` 원본을 계속 둘지(통합 페이지의 '운영' 탭은 `service_admin/static/ops/` 복사본을 쓴다), 운영 서버 API 담당.
