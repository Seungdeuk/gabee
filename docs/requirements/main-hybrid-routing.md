# 기능: 메인 Agent 하이브리드 라우팅 (서버 1차 판정 + 모델 2차 선택)

@가비(메인) Agent 가 출처가 하나로 정해진 질문에서 다른 담당 Agent 까지 함께 부르는 과잉 라우팅을 줄인다. 라우팅의 **범위 조건**은 서버의 결정론적 규칙이 정하고, 모델은 허용된 담당 안에서만 고른다. 설계 근거는 `docs/features/agent-main-routing-followup-design.md`(`feature/seungdeuk-main-source-routing` 브랜치, #542 종료 메모)와 최종 평가 보고서 7절 1번이다.

## 목적
- 관측: 불필요한 이중 호출 6 → 12건(dev 36사례 × 3회). 대부분 첫 모델 호출에서 `ask_family_chat` 과 `ask_schedule` 을 동시에 부른 경우다. 프롬프트 수정(#535·#542)으로는 2/6 → 1/6 까지만 줄었다.
- 목표: 명시된 출처와 충돌하는 담당 호출을 서버가 막아 Tool Precision·호출 수·비용을 개선하되, 필요한 도구를 막아 Tool Recall 이 떨어지는 일은 없게 한다.

### 하지 않는 것
- 새 LLM 호출이나 분류 모델은 넣지 않는다. 규칙 기반(1안)만 구현하고, 경량 분류 모델(2안)은 `unclear` 비율을 본 뒤 따로 정한다.
- 탭 Agent(정산·소통·일정) 내부 동작과 권한 규칙은 바꾸지 않는다. 권한은 지금처럼 fail-closed 이다.
- 문서 도구(`search_knowledge`·`get_item`)·기억·공유·웹 도구는 제한하지 않는다. 대상은 `ask_*` 담당 도구뿐이다.
- 시스템 프롬프트 문장은 바꾸지 않는다(#542 판정 유지).
- 평가 사례·정답지·채점기는 바꾸지 않는다.

## 화면·API·데이터
- 화면: 없음. API: 없음(`POST /ai-assistant/chat` 응답 형태 그대로). DB: 변경 없음.
- 설정: `MAIN_ROUTING_MODE` = `off`(기본) | `shadow` | `enforce`. `.env.example` 에만 추가한다.

## 동작
### 1. 출처 판정 (결정론적, 비용 0)
- 입력: 이번 질문 문장, 채널(`audience`: me / room / direct).
- 출력: `sources ⊆ {chat_history, family_todo, schedule_tab, billing_ledger, knowledge_docs}`(명시된 출처들), 비어 있으면 `unclear`. 명시 출처가 둘 이상이면 복합(compound)이다.
- 규칙: 일반 표현 사전("일정 탭"·"캘린더"·"일정에 넣어", "채팅에서"·"대화에서"·"방에서 얘기한", "가족 할 일 목록"·"공동 할 일", "장부"·"지출 기록"·"정산", "올린 문서"·"영수증"·"안내문" 등)과 채널만 쓴다.
- 평가 사례 문장이나 특정 낱말(예: 장보기)을 하드코딩하지 않는다. 사전 단어는 평가 사례와 겹치지 않는 별도 일반화 시험 문장으로 검증한다.
- 이전 턴은 보지 않는다. 앞선 대화를 가리키는 말("그거", "아까", "첫 번째" 등)이 있으면 `unclear` 로 판정하고 막지 않는다.
- 어느 탭에 쓸지가 앞뒤 말에 달린 쓰기 표현("등록", "추가", "넣어", "잡혀" 등)이 있어도 `unclear` 다.
- 목록을 말하지 않은 할 일: 개인 채팅에서는 `unclear`(소통·일정 둘 다 보는 #535 규칙 유지), 가족방에서는 가족 공동 목록(family_todo)이다. "일정 탭의 할 일"·"내 할 일"은 schedule_tab 이다.
- 가족방에서 출처·일정·장부 표현이 없는 질문은 그 방 대화(chat_history)로 본다(설계 메모 6절, 2026-11-27 사용자 결정). 일정을 '일정'이라 말하지 않은 가족방 질문은 일정 Agent 를 못 쓰는 한계가 있다.

### 2. 허용 담당 집합
| 판정 | 허용되는 `ask_*` |
|---|---|
| `unclear` | 제한 없음(지금과 같음) |
| 명시 출처 하나 이상 | 명시된 출처의 담당만. chat_history·family_todo → `ask_family_chat`, schedule_tab → `ask_schedule`, billing_ledger → `ask_billing`, knowledge_docs → `ask_*` 없음(문서 도구만) |
| 복합(예: "채팅에서 정한 걸 일정에 넣어줘") | 언급된 출처 담당 각각 |

- 1:1 방(`direct`)에서 `ask_schedule` 을 막는 기존 규칙은 그대로 두고, 이 표보다 먼저 적용된다.
- 차단은 "명시된 출처와 충돌하는 담당"에만 적용한다. 라우팅은 fail-open 이다(판정이 애매하면 막지 않는다).

### 3. 모드
- `off`: 아무것도 바꾸지 않는다(병합 시 운영 동작 변화 0).
- `shadow`: 실제로 막지 않고 "막았을 호출"만 기록한다.
- `enforce`: 모델에 보내는 도구 목록에서 허용 밖 `ask_*` 를 빼고, 시스템 프롬프트 끝에 "이번 질문에서 쓸 수 있는 담당" 한 줄을 붙인다. 그래도 요청되면 실행하지 않고 "이 질문에는 이 담당을 쓰지 않습니다"를 오류 결과로 돌려준다.
- 기록: 평가 관찰(`eval_hook`)에 `blocked_tool`(모드, 도구 이름, 판정 출처, 규칙 id)을 남긴다. **질문 문장은 기록하지 않는다.** 운영 로그에는 남기지 않는다.

## 완료 조건
- L0: 판정 규칙 단위 시험(일반화 문장 포함), 허용 집합 표 시험, 세 모드 각각의 `_handle_calls`·도구 목록 시험, 1:1 기존 차단 유지 시험.
- `off` 에서 기존 `ai_assistant` 시험 전부 통과(동작 변화 0).
- Fake Runner 로 dev 36사례를 `shadow` 로 돌렸을 때 **정답 도구를 막았을 호출 0건**. 1건이라도 있으면 그 규칙을 고치거나 뺀다.
- PR 전에 FULL(`scripts/check_local.py --full`)과 `ruff check`·`ruff format --check` 를 통과한다.
- 실모델 국소 평가(`enforce`, 과잉 라우팅 사례와 반대 사례 × 3회)는 비용 승인을 받은 뒤 별도로 한다. 이 평가 전에는 운영에서 `enforce` 를 켜지 않는다.

## 미정
- 실모델 국소 평가의 사례 목록과 비용 한도(승인 필요, 예상 $0.1~0.3).
- 운영에서 `shadow` → `enforce` 로 바꾸는 시점과 담당자.
