# ACCOUNT 개인정보 보호 개선 과제: 경로 분석·설계·테스트 계획 (구현 전, 승인 대기)

작성일 2026-11-19. R9 연구와 독립된 보안 과제다. 이 문서는 분석·설계·계획이며 **운영 코드는 바꾸지 않았다.** 점검은 코드 읽기와 새로 쓴 합성 문장 실행만 썼고 실제 계좌번호·사용자 대화·외부 호출은 쓰지 않았다. `[V]` 코드·문서로 확인, `[I]` 추정.

## 1. 현재 ACCOUNT 보호 경로 (코드 기준)

### 1-1. 탐지 규칙의 범위 (`app/shared/privacy/detectors.py`) [V]
- 전처리는 이미 있다: 전각→반각, 여러 대시→`-`, 보이지 않는 문자 제거(글자 수 불변, 위치 복원).
- 계좌 후보: `\d{2,6}(-\d{2,8}){1,3}` 또는 `\d{10,14}`, 숫자 합계 **10~14자리**만. 전화 모양은 전화로 본다. 숫자 앞 14자·뒤 6자 안에 `주문·운송장·택배…`가 있으면 제외.
- 계좌 문맥(숫자 앞뒤 **20자** 안): 은행명+은행/계좌/입금… 또는 은행명이 바로 앞뒤(0.8), `계좌|예금주`(0.7), `입금|송금|이체`만(0.6). 하이픈이 있으면 +0.1. 문맥이 없으면 계좌로 보지 않는다.
- 정책: ACCOUNT=BLOCK, 점수 ≥ 0.7이면 차단. 점검에서 확인한 불일치: 약한 문맥(0.6) 주석은 "가리기만"이라 했지만 하이픈 번호는 0.7이 되어 차단된다.
- 새 합성 19건 점검(`apps/api/scripts/probe_account_rules.py`): **미탐 = 문맥 없는 하이픈 번호, 9자리, 공백 구분, 문맥이 20자보다 먼 경우, `주문번호` 근처, 15자리.** 문맥 없는 붙인 13자리는 RRN(0.45)으로 오인되어 우연히 가려진다. 한 문장 두 계좌는 둘 다 탐지.

### 1-3. 래퍼·활성화·승인
- **래퍼 최종 방어 없음** [V]: 모든 HTTP 요청은 `shared/llm/transport.post_messages` 를 거치지만 직렬화된 본문 검사나 "게이트웨이를 거쳤는지" 확인이 없다. 새 호출자가 원문을 그대로 보낼 수 있다.
- **`blocked_count`·`high_risk_count` 는 `prepare_text/json` 호출자 어디서도 사용하지 않는다** [V]: 값만 바꾸고 요청은 계속되며 사용자는 모른다. 값 탐지 자체가 없으면 어떤 토큰도 만들어지지 않는다.
- **`high_risk_guard`(점수 ≥0.45, RRN·CARD·ACCOUNT·SECRET)는 `POST /billing/agent/chat` 과 `POST /ai-assistant/knowledge/items` 에만** 붙어 있다 [V: `high_risk_guard.py` `_TARGETS`]. 탐색 에이전트가 메인 채팅에도 붙어 있다고 서술했으나 코드와 문서(`LLM_EGRESS_TEMP_GUARDS.md` 2026-11-04 현황, `_TARGETS` 주석)는 메인 채팅을 일부러 뺀 것으로 확인된다. 이 가드도 같은 `detect()` 를 쓰므로 §1-1 의 미탐은 가드에서도 그대로 통과한다.
- 활성화 [V]: 외부 호출 스위치는 `ANTHROPIC_API_KEY` 유무(`llm.available()`)다. 키가 비면 외부 호출이 없고 503 `llm_unavailable`. `.env` 는 읽지 않아 **운영에서 현재 켜져 있는지는 확인하지 못했다.** 가족 그룹별 AI 동의(`ai_group_settings.enabled`, 기본 꺼짐)가 없으면 403 `ai_not_enabled`. `DISABLED_AI_ROUTES` 로 경로별 503 차단이 가능하다.
- 사용자 승인 [V]: 가족 AI 켜기 때 동의 카드 1회만 있고 요청마다 확인은 없다. 문서 업로드·채팅 사진·에이전트 경로에는 전송 전 확인 UI가 없다[I: 모바일 폴더에서 찾지 못함]. 모바일에 `sensitive_content` 400 전용 처리는 없어 일반 오류로 보일 수 있다[I]. 동의 문구와 문서 사이에 "누가 켤 수 있는가" 불일치가 있다.
- `.env`·실데이터 미사용. 감사 로그는 호출 메타데이터만 보관하고 본문은 보관하지 않는다.

### 1-4. 결론
정책(ACCOUNT=BLOCK)은 맞고, 문제는 (1) 규칙 탐지 재현율, (2) 규칙 미탐 숫자가 래퍼 앞뒤 어디에서도 안전망 없이 외부로 나가는 구조, (3) 메인 채팅·OCR 이미지·정산 도구 결과·일정 제안류처럼 애초에 가림이 없거나 약한 경로다. 가장 큰 노출 경로는 메인 채팅(5)과 OCR 원본(6, 7)이다.

## 2. 개선 설계안

### 2-1. 3단계 분류 (확실 / 의심 / 일반 식별번호)
| 등급 | 정의(예) | 기본 동작 |
|---|---|---|
| **확실 계좌** | 하이픈·붙임 9~16자리 + 가까운 은행명/`계좌`/`예금주` 또는 은행 고유 자릿수 형식 | BLOCK(줄 제외 또는 요청 중단) |
| **의심 계좌** | 계좌 모양(§2-2 후보)이지만 문맥이 없거나 멀거나, 문맥이 충돌(`주문번호 계좌 …`), 길이가 범위 밖, 같은 메시지에 은행명·계좌 단어가 있고 번호가 따로 있음 | 값을 고정 토큰으로 치환(원문 비전송). 엄격 경로에서는 중단 |
| **일반 식별번호** | 주문·운송장·사업자·시리얼 문맥, 날짜·시각·금액, 전화·RRN·카드(체크섬 통과) | 기존 규칙대로(계좌 아님, 별도 종류) |
비대칭 원칙: 계좌 의심을 놓치는 비용(원문 전송)이 과차단 비용(재입력 요청)보다 크므로, **불확실하면 계좌 쪽으로 보수적으로** 처리하되 일반 식별번호 문맥이 분명하면 풀어 준다.

### 2-2. 처리 순서 (정규화 → 후보 → 제외/우선순위 → 문맥 점수 → 등급 → 동작)
1. **정규화**(위치 복원 유지): 기존 전각·대시·보이지 않는 문자 + `NFKC`/유니코드 숫자(아랍·원숫자 등)를 ASCII 숫자로. 숫자 사이 구분자 `공백·.·가운뎃점·/·_` 를 후보 안에서 무시.
2. **후보 생성**: 숫자 9~16자리(구분자 무시), 자릿수 분포가 계좌형(예: 3-3-6, 3-2-6, 4-2-7, 4-3-6, 3-4-4-2)이면 가산. 한 문장에 여러 개면 각각 독립 후보(서로 문맥을 공유하는 나열형 `국민 …, 농협 …` 포함).
3. **우선 판정**: 전화(체크섬 없음, 형식 엄격), RRN(생년월일·체크섬), 카드(Luhn)를 먼저 확정해 겹침을 제거. 날짜·시각·금액(쉼표·원 단위) 제외.
4. **일반 식별번호 문맥 제외**: 현행 `_NOT_PII_CONTEXT` 를 사전 고정. 단 **계좌 단서와 충돌하면 의심으로 남김**.
5. **문맥 점수**: 은행명·계좌 단어 창을 20자 → 40자로 넓히고, 같은 메시지 안 단어는 약한 가산, 직전 사용자 줄의 계좌 단서를 한 턴 이월(대화에서 "계좌 알려줘" → "110-123…" 패턴).
6. **등급·동작**: 위 표. 동작은 경로별 매트릭스(§3).
7. **래퍼 최종 방어**: `transport.post_messages` 직전에 직렬화 본문을 같은 탐지기로 한 번 더 검사하고 확실·의심 후보가 남아 있으면 요청을 중단(fail-closed, 값은 로그에 남기지 않음). 가명화를 안 거친 신규 호출자도 막는 안전망이다. 이미지·PDF 본문은 검사할 수 없어 OCR 경로는 별도 정책(§3)으로 다룬다.

| 안 | 조건 | 오탐 영향 | 사용자 안내 | 적용 범위 |
|---|---|---|---|---|
| A. 메인 채팅 입력의 긴 숫자 사전 차단 | 정규화 후 숫자 9자리 이상(전화·날짜·금액·주문 문맥·RRN 판정 제외)이 질문·앞 대화에 있으면 400 | 합성·뉴스 코퍼스 대략치: 합성 baseline 720문장 중 연속 9자리+ 66문장(이 중 탐지기가 설명하지 못하는 것 22), 합성 신규 4,749문장 0, KLUE 21,008문장 0. baseline 은 일부러 개인정보를 넣은 문장이라 **깨끗한 오탐률이 아니다** | "계좌·긴 번호처럼 보이는 숫자가 있어 보내지 않았어요. 번호를 빼고 다시 물어보세요" (현행 `sensitive_content` 문구 확장) | `/ai-assistant/chat`, `/knowledge/ask` 입력(질문·history) |
| B. 래퍼 직전 fail-closed 검사 | 요청 본문에 확실·의심 계좌 후보가 남으면 호출 중단 | A보다 좁고(계좌 모양+문맥 단서) 신규 경로까지 보호 | 일반 오류 문구로는 부족 → 전용 오류 코드·모바일 안내 필요 | 모든 텍스트 LLM 호출 |
| C. 위험 경로 일시 차단 | `DISABLED_AI_ROUTES` 로 OCR 전송·일정 제안 등 | 기능 중단(영향 큼) | 앱의 "일시 중단" 안내 | 선택 경로만, 최후 수단 |
| D. 동의·공지 강화 | 업로드·메인 채팅 화면에 "계좌번호·주민번호는 입력/업로드하지 마세요" 상시 안내 | 오탐 없음, 보호 효과는 약함 | 화면 상단 문구 | 앱 UI(코드 변경 필요) |
권고(승인 시): **B를 가장 좁은 규칙(확실+의심 계좌)으로 먼저**, 메인 채팅은 A 의 좁은 변형(길이 9+이고 은행 단서가 같은 메시지에 있을 때)부터, OCR은 §1-2의 6·7이 구조적이라 규칙 보완이 아니라 별도 결정(전송 전 확인·문서 유형별 제한)이 필요하다. 정확한 임계와 문구는 승인 후 합성 코퍼스 측정으로 정한다.

## 4. 테스트 설계 (합성 데이터만)

### 4-1. 기준선 보존
- 현재 서비스 규칙을 **동결**: 커밋 `87219658` 의 `detectors.py`·`policy.py`·`pseudonymizer.py` 를 `legacy` 사본(테스트 전용 모듈)으로 고정하고 해시 기록. 새 규칙과 같은 합성 세트·같은 하니스로 변경 전후를 나란히 측정한다.
- 합성 세트는 시드 고정 생성기 + 버전·SHA256 기록, 한 번 확정하면 수정하지 않는다(필요하면 새 버전).

### 4-2. 합성 세트 구성 (모든 번호는 가상)
- **양성(계좌)**: 형식(자릿수 9~16 × 하이픈 위치 × 공백·점·가운뎃점 구분 × 붙임) × 문맥(은행명 앞/뒤, `계좌`, `예금주`, 입금류, 없음, 20~60자 떨어짐, 앞 줄에 있음) × 표기(ASCII·전각·아랍 숫자·대시 변형·보이지 않는 문자) × 개수(1·2·3개, 한 줄 나열·여러 줄) × 은행(대표 은행명 전부).
- **음성(일반 식별번호)**: 주문번호·운송장·예약번호·사업자번호·시리얼·바코드·전화(국내·국제·유선)·RRN·카드(Luhn)·날짜·시각·금액·버전·좌표·IP·OTP·학번·청구번호, 그리고 계좌 단어와 섞인 충돌 문장(`주문번호 계좌 …`).
- 각 항목에 정답 등급(확실/의심/일반)과 기대 동작을 붙인다. 정답 부여는 생성 규칙에서 기계적으로 도출하고 경계 사례만 사람이 검수.

### 4-3. 지표와 합격 기준(제안, 승인 시 사전 등록)
1. **ACCOUNT 탐지 재현율**: 확실 ≥ 0.99, 의심 포함 전체 ≥ 0.95, 형식·문맥·표기 층별 최저 표시.
2. **일반 식별번호 오탐률**: 음성 범주별(주문·운송장·전화·RRN·카드·날짜·금액) 계좌 판정 ≤ 1%, 충돌 문장은 의심 판정 허용(과차단 비용 별도 보고).
3. **BLOCK 정상 동작**: 확실 계좌는 `apply`/`prepare_transcript` 에서 줄 제외, `apply_values` 에서 고정 토큰, 점수 경계(0.69/0.70) 시험.
4. **원문 잔존율**: 모든 가명화 출력에 원본 숫자열(구분자 제거 후)이 남은 건수 — 확실·의심 양성에서 **0건**이 기준.
5. **외부 호출 중단**: LLM 전송을 가짜 transport 로 대체(실제 HTTP 없음)하고 확실·의심 계좌가 든 요청에서 가짜 transport 가 **호출되지 않거나 본문에 원본이 없음**을 단언.
6. **경로별 회귀**: 가족채팅 4종, 가족채팅·정산·일정 에이전트, 메인 채팅, 문서 인제스트(`mask_text`·`find_pii` 응답 대체 시뮬레이션), `admin_knowledge` 에 같은 합성 입력을 흘려 경로 × 입력 매트릭스로 통과/차단/마스킹 결과를 표로 기록.
7. 기존 `test_detectors.py`·`test_hardening.py` 의 계좌 양성/음성 회귀 전부 통과 유지, 새 케이스는 별도 파일.

### 4-4. 실행 순서(승인 후)
기준선 동결 → 합성 세트 생성·해시 → 현재 규칙 측정(기준선 보고서) → 규칙 변경안 구현 → 같은 세트 재측정 → 경로별 통합 테스트 → 오탐 수용 판단은 사용자.

## 5. 이번 단계의 한계와 결정 필요 사항
- 운영 설정(키 유무·동의 상태)은 `.env` 를 읽지 않아 확인하지 못했다.
- 메인 채팅 가리지 않음(2026-11-04 결정)과 OCR 원본 전송은 정책 결정 사항이다. 개선안 적용 범위를 정해야 한다.
- 일반 식별번호 오탐 영향은 아직 깨끗한 합성 음성 코퍼스로 측정하지 않았다(§3 수치는 거친 참고치).
- 코드·정책 변경, 배포, 모델 변경은 하지 않았고 승인 후에 구현한다.
