# 0007. 업로드 → 전처리 → knowledge → 채팅 연결: 가린 글자만 외부 모델로, 원본은 서버에서 직접

## 결정

1. **업로드 흐름**: `POST /ai-assistant/files` 가 바로 `received` 로 응답하고, 읽기(OCR)·가리기·분류·사진 설명·knowledge 저장은 백그라운드에서 한다. 처리 상태는 `photos.status`, 저장된 knowledge 기록의 id 는 파일 id 와 같게 둬서 DB 구조를 바꾸지 않고 잇는다. 처리 중 서버가 꺼져 `received` 로 15분 넘게 남은 파일은 `failed` 로 알려 준다.
2. **개인정보 가리기 확대**: 외부 모델(Claude)로 나가는 글이므로 일반 문서(영수증·고지서·엑셀 등)도 주민번호 외에 카드·전화·이메일·계좌 번호, 라벨이 붙은 이름·주소를 가린다. 주민번호는 하이픈 없는 13자리, 공백·점·긴 대시 구분, 전각 숫자도 가린다. (전처리 담당자의 기존 정책 "일반 문서는 주민번호만"을 바꾼 것 — 담당자 확인 필요)
   - 한계: 라벨 없는 이름·주소, 고객번호·환자번호는 아직 새어 나간다. 영수증의 가게 전화번호도 가려진다.
3. **민감 기록(처방전·신분증·통장·가족관계증명서)도 가린 글자로 채팅 근거에 쓴다.** 설정 `CHAT_INCLUDE_SENSITIVE` 로 켜고 끈다(보안 점검 뒤 기본값을 false 로 바꿨다 — 켠 가족만 포함). 끄면 검색·`get_item`·`list_items` 에서 빠지며 지침도 "볼 수 없다고 안내"로 바뀐다. 가린 값(홍**, ******-*******)은 되살리지 않는다.
   - 외부 API 로 가린 글자가 전송·처리된다는 점은 그대로다. ingest 문서의 "어떤 모델에도 보내지 않는다" 문구와 어긋나므로 팀이 문구 또는 동의 절차를 정해야 한다.
   - 기록은 사용자별이 아니라 **가족 그룹 단위**로 저장·검색된다. 같은 가족이면 누구든 민감 기록의 가린 내용을 물을 수 있다. (사용자 확인: 지금 설계로 충분함)
4. **원본 꺼내주기**: 답변의 출처에서 "원본 보기"를 누르면 앱이 `GET /ai-assistant/files/{id}/original` 을 로그인 토큰 헤더와 함께 호출해 원본 바이트를 받는다. 원본은 Claude 를 거치지 않는다.
   - 서버는 요청자의 가족 그룹이 기록의 그룹과 같을 때만 준다(다른 가족·로그인 없음은 404/401). 저장 경로의 첫 칸이 요청 그룹과 다르면 읽지 않는다(`raw_store.get_for_group`).
   - 이미지·PDF 말고는 내려받기로만 응답하고 `nosniff`·`CSP: sandbox`·`no-store` 를 붙인다.
   - 서명 URL 방식은 쓰지 않았다(비밀키·만료 관리가 늘고 주소가 새면 유효시간 동안 노출). 필요하면 나중에 얹는다.
   - 앱은 지금 이미지만 앱 안에서 연다. PDF 등은 `expo-file-system`·`expo-sharing` 이 필요해 보류.

## 추가 결정 (2026-10-23): 앱에서 PDF 원본 보기, 같은 파일은 출처 하나, 읽어 낸 글 보기 개선

- **PDF 원본을 앱에서 보기**: 앱에 PDF 뷰어를 넣는 대신(`expo-file-system`·`expo-sharing` 추가가 필요) 서버가 쪽을 그림으로 그려서 준다. `GET /ai-assistant/files/{id}/original/pages`(쪽 수, 최대 100)와 `.../pages/{n}`(JPEG, 긴 변 1600px). 원본 보기와 같은 가족 그룹 확인을 거치고, 사진이 아닌 파일은 404. 앱은 쪽 그림을 위아래로 넘겨 본다. 새 의존성 없음(이미 쓰는 `pypdfium2`). 워드·엑셀·PPT 원본은 아직 앱에서 열 수 없고 "읽어 낸 글로 확인" 안내가 뜬다(변환 도구가 없음).
- **같은 파일은 출처 하나**: 같은 파일을 두 번 올리면 기록이 둘 생기는데, 검색 결과에서 같은 원본 경로(같은 해시)는 점수가 높은 하나만 Claude 에게 넘기고, 답의 출처 번호도 같은 원본이면 하나로 합친다(`[1][1]` 도 `[1]`). 기록 자체의 중복 저장 방지와 삭제는 아직 없다.
- **읽어 낸 글 보기**: 기록 상세에서 마크다운 원문 대신, 위에 요약(날짜·금액·장소 등)과 태그, 아래에 읽어 낸 글(표는 칸으로, 소제목은 굵게, 읽은 순서 번호는 숨김)을 보여 준다.

## 추가 결정 (2026-10-23): 기록 삭제, 읽는 중 표시와 걸린 시간

- **기록 삭제**: `DELETE /ai-assistant/knowledge/items/{id}` (204). 읽어 낸 글, 검색 조각, 올린 파일 정보(`photos`), 서버에 둔 원본과 화면용 사본을 함께 지우고 **되돌릴 수 없다**. 같은 가족 그룹만 지울 수 있고(다른 가족은 404), 원본을 지울 때도 저장 경로의 첫 칸이 요청 그룹인지 확인한다(`raw_store.delete_for_group`). 같은 파일을 두 번 올려 같은 원본을 가리키는 다른 기록이 남아 있으면 원본은 그대로 둔다. 앱은 기록 상세의 "이 기록 지우기"와 목록 길게 누르기에서 확인창을 거쳐 지운다. 가족 누구나 지울 수 있고 삭제 이력은 남기지 않는다.
- **읽는 중 표시**: 파일을 읽는 동안 가비가 튀고 점이 깜빡이는 표시와 지나간 시간("12초 지났어요 · 보통 5~30초 걸려요")을 보여 주고, 끝나면 답변에 "(걸린 시간 N초)"를 붙인다. 서버가 단계를 알려 주지 않으므로 가짜 진행 단계는 보이지 않고, 시간은 앱이 올린 시각부터 센 값이다.

## 추가 결정 (2026-10-23): 흐린 줄은 채팅에서 물어본다, 올리기 시트, 답변 만드는 중 표시

- **흐린 줄 표시와 되묻기**: 사진 글자 인식(OCR)에서 확신도가 0.8 미만인 줄(가장 흐린 것부터 최대 6줄)은 저장할 때 줄 끝에 `[불확실]` 을 붙인다. 이 줄이 있으면 파일 상태 응답(`GET /ai-assistant/files/{id}`)의 `doubts` 로 내려가고, 앱은 올린 직후 채팅에 줄마다 입력칸이 있는 카드("이 줄은 글자가 흐려서 확실하지 않아요")를 띄워 "모두 맞아요" 또는 "고쳐서 저장"을 고르게 한다. 확인하거나 고치면 `PATCH` 로 반영되고 `[불확실]` 표시와 확인 필요 상태가 사라진다. DB 컬럼 추가 없음(표시를 글 안에 두었다). 채팅 지침에도 "[불확실] 줄의 값은 단정하지 말 것"을 넣었다. 스캔 PDF·문서는 줄별 확신도가 없어 이 질문 대상이 아니고 기존 "확인 필요"만 뜬다.
- **이름 라벨 가리기 버그**: 일반 문서에서 "이름"처럼 라벨이 줄 끝에 있으면 다음 줄의 단어("합계")까지 이름으로 가리던 문제를 고쳤다. 라벨 값이 같은 줄에 있을 때만 가리고, 처방전·신분증·통장·증명서처럼 라벨 칸과 값 칸이 줄로 나뉘는 문서만 다음 줄까지 본다.
- **올리기 시트**: `+` 를 누르면 시스템 알림창 대신 아래에서 올라오는 둥근 시트에 앨범·카메라·파일 타일이 뜬다.
- **답변 만드는 중 표시**: 단계 표시의 점이 깜빡이고, 끝난 단계의 체크가 톡 튀어나오며, 지금까지 걸린 시간이 올라간다.

## 추가 결정 (2026-10-25): OCR 줄 방향 확인을 끄고 읽는다, 임베딩은 BM25 를 합치지 않는다

- **OCR**: 줄 방향 확인(cls) 모델이 짧은 줄을 거꾸로 뒤집어 읽어 줄이 통째로 빠지고 있었다("고객명 영희" → "후", 확신도 0.49 라서 버려짐). 가짜 문서 150장(깨끗함·약간 흐림·심하게 흐림·큰 폰 사진 속 작게·위아래 뒤집힘)으로 설정 9+6가지를 비교해, **방향 확인을 끄고 읽고 평균 확신도가 0.85 미만이면 (방향 확인 켜기 / 사진 180° 돌리기) 중 확신도 합이 큰 쪽을 쓰기**로 했다. 입력은 EXIF 회전만 반영하고 흑백·대비 보정은 뺐다(원본 색이 오류율이 낮음). 줄 회수 68.0% → 95.2%, 숫자 회수 83.6% → 99.2%, 글자 오류율 37.7% → 4.8%. 전체 흐름(시험 파일 34개) 질문 정답 28/39 → 36/39. 어두운 저화질 조건은 줄 회수 83.8% 로 아직 낮다.
  - 부작용: 이제 줄이 읽히므로 개인정보 원문이 남은 값이 4/40 → 7/40 으로 늘었다(라벨 없는 이름, 증권번호). 라벨 번호(증권·고객·환자·계약번호)와 라벨 없는 이름·주소 가리기를 더 해야 한다.
  - 시험 자료와 코드: 재현 묶음 `gabee_share/ocr_eval` (저장소 밖).
- **임베딩 + BM25**: 임베딩(e5-small 파인튜닝 ONNX) 단독이 가장 좋았다(질문 9,334개 R@3 97.9%). BM25 단독 81.9%, 합치기 RRF 1:1 92.5%, 임베딩 90%+BM25 10% 점수 합산 97.4% 로 어떤 방식도 임베딩 단독을 넘지 못했다. 서비스는 임베딩 단독을 유지한다. 실제 질문이 쌓이면 다시 본다. 재현 묶음 `gabee_share/embedding_eval`.
- **문서 분류의 qwen 대체**: 임베딩 + 로지스틱 분류기는 합성 데이터에서 100%(너무 쉬움), 사람이 쓴 샘플 51개에서 약 92%(qwen2.5vl:3b 약 80%), 실제 파이프라인 기록에서는 표 형식(엑셀·CSV)과 처음 보는 종류에서 약 78~80% 였다. 알려진 종류에는 쓸 수 있지만 95% 를 넘으려면 종류와 표 형식 학습 데이터를 늘려야 한다. 아직 서비스에 적용하지 않았다.


## 추가 결정 (2026-10-26): qwen 을 모두 걷어냈다 — 사진 설명은 사용자가 달고, 문서 분류는 작은 로컬 분류기가 한다

전처리 담당자와는 상의를 마쳤다(사용자 확인). 브랜치 `feature/kang-user-description-classifier`. **새 의존성은 없다.**

  - 이유: ① 한국어가 약하다 — 가벼운 후보(SigLIP2·한국어 CLIP·Florence-2-base·SmolVLM-256M)를 CPU 로 시험했을 때 한국어 질문으로 사진을 찾는 비율이 낮았다(SigLIP2 사진 벡터 28%, 영어 질문 91%). 영어 설명을 한국어로 옮기려던 번역 모델은 출력이 깨져 쓰지 못했다. ② 사진이 서버 밖(LLM API)으로 나가지 않는다. ③ 채팅 LLM 에 쓰기 도구를 더하지 않는다(읽기 도구 3개 그대로). ④ 사용자가 아는 정보(누구와·어디서)가 들어가고, 한국어 설명은 e5 로 바로 색인된다.

- **문서 분류**: 로컬 언어 모델(qwen)로 종류를 정하던 것을 **앱 임베딩(e5-small 파인튜닝) + 글자 TF-IDF → 로지스틱 회귀** 분류기로 바꿨다. 순서는 `규칙(처방전·고지서·영수증) → 분류기(확률 ≥ 0.7 확정) → Jev(키가 있을 때만) → 기타 문서 + 확인 필요`. 분류기는 `numpy` 만으로 읽는다(`ingest/doc_classifier.py`, scikit-learn 은 개발용 학습 스크립트 `scripts/train_doc_classifier.py` 에서만 쓰고 프로젝트 의존성에 넣지 않았다).
