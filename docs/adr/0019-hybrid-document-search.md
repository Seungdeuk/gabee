# 0019. 문서 검색은 임베딩 후보 안에서 글자 TF-IDF 를 계산해 순위를 섞는다(DB·의존성 변경 없음)

- 날짜: 2026-11-10
- 결정:
  - `knowledge/service.search` 는 임베딩 상위 `CHAT_HYBRID_CANDIDATES`(기본 100)개 조각을 가져온 뒤, 그 안에서 질문과 조각 글의 글자 2·3개 묶음 TF-IDF 코사인을 파이썬으로 계산하고 임베딩 순위와 RRF(k=60, 가중 `CHAT_HYBRID_TEXT_WEIGHT`=1)로 섞어 다시 정렬한다(`knowledge/hybrid.py`). 설정 `CHAT_HYBRID_SEARCH=false` 면 예전 동작이다.
  - 반환 `Hit.score` 는 계속 임베딩 코사인 유사도다(섞은 순서와 점수 순서가 다를 수 있다). 첫 호출 검색 강제(`chat_force_search_min_score`)는 `hybrid=False` 로 불러 섞지 않은 최고 유사도를 쓴다. 날짜·종류·민감·가족 필터와 `per_item` 은 후보를 가져오는 단계에서 그대로 적용된다.
- 이유:
  - 임베딩은 고유명사·숫자·낱말 일치에 약하다. 오프라인 실험(전체 조각 대상, API 비용 0)에서 글자 TF-IDF 를 섞으면 공개 PDF 정답 쪽 Hit@3 59.8→68.9%, 정답 문서 Hit@1 85.7→92.8%, 가족 v2 Hit@1 95.5→96.6%. TF-IDF 만 쓰면 가족 Hit@1 이 84.8% 로 떨어져서 반드시 섞는다.
  - 후보 100개 안에서만 계산해도 효과 대부분이 남는다(공개 PDF 정답 쪽 Hit@3 67.0%, 가족 v2 Hit@3 99.4%). 조각이 긴 공개 PDF 에서도 TF-IDF 계산이 약 14~32ms 다. 새 의존성·DB 확장·마이그레이션이 없다.
- 대안:
  - **전체 조각 대상 TF-IDF/BM25**(DB 전문 검색, pg_trgm, 색인): 효과는 조금 더 크지만(Hit@3 68.9% 대 67.0%) 확장 설치와 Alembic 리비전, 공용 DB 반영 절차가 필요하다. 지금은 보류, 조각이 크게 늘면 다시 검토한다.
  - **후보 200개**: 효과 차이가 0.5%p 이하인데 계산 시간이 두 배다(공개 PDF 약 27~70ms).
  - **재순위 모델**: 별도 실험(`rerank_public_hybrid.json`) 참고. 모델 파일·의존성이 늘어 이 결정에는 넣지 않았다.
- 결과·주의:
  - 후보 밖(임베딩 100위 밖)에 있는 글자 일치 조각은 못 건진다. 임베딩 모델을 바꾸면 후보 수·효과를 다시 잰다(`apps/api/eval/rag/hybrid_candidates_check.py`).
  - 같은 조각을 질문마다 다시 쪼개지 않도록 글 단위 LRU 캐시(4096개)를 쓴다.
