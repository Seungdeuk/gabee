# 0022. Agent 평가의 정책 3건(권장안) — 일정 쓰기 성공 평가는 평가 쪽 직접 경로를 1차로, val·test 본문은 저장소 밖 보관을, 가족 이름은 현행 기록 전용을 임시로 둔다

- 날짜: 2026-11-18
- 상태: **제안(권장안, 사용자 승인 대기)**. 2026-11-17 조사의 권장안을 정리한 것이고 **최종 정책이 아니다.** 사용자가 승인하기 전에는 이 문서를 병합하지 않고, 아래 구현도 시작하지 않는다.
- 이 문서가 바꾸는 것: **없다.** 운영 코드·평가 코드·시험·사례 정답지를 바꾸지 않는다. 지금 동작(일정 쓰기 사례는 `unsupported`, val·test 목록이 저장소에 있음, 가족 이름 원문은 기록만)은 승인과 구현이 끝나기 전까지 그대로 유효하다.
- 권장안:
  1. **일정 쓰기 성공 평가: 방안 A(평가 쪽 직접 경로)를 1차 구현 방향으로 둔다. 방안 B의 필요성은 후속 검증 항목으로 남긴다.**
     - 쓰기 사례만 일정 Agent(`handler.handle`)를 직접 불러 `schedule_outcome` 으로 완료·되묻기·거절을 가리고, 승인 카드가 나오는 사례는 확인 호출(`handler.confirm`, 앱이 누르는 `/schedule/agent/confirm` 과 같은 함수)까지 한다. 이때만 해당 사례에서 `write_guard` 를 끈다.
     - 성공은 **임시 SQLite 의 일정 행 전후 비교**(제목·날짜·시간·장소·공유 대상)로 판정한다. 공용·운영 DB 는 어떤 경우에도 쓰지 않는다(ADR 0009-local-first-db-workflow, 평가 DB 경계).
     - "승인 게이트"는 **운영이 실제로 쓰는 경로 그대로** 본다: 공유 대상이 있는 등록과 모든 수정·삭제는 확인 카드를 거친 뒤 확인 호출에서만 DB 가 바뀐다. 공유 대상이 없는 직접 등록과 일정 체크는 운영이 카드 없이 바로 쓰므로, 그 경로는 사용자가 요청한 사례(기대 `calls` 에 쓰기를 적은 것)에서만 허용하고 요청 없는 쓰기는 지금처럼 `unapproved_write` 로 실패시킨다. 이 경로를 운영에서 카드로 바꿀지는 평가 범위 밖이다(앱 담당과 협의).
     - 운영 응답에 결과 필드를 더하는 방안 C 는 운영 코드 변경이라 이번 권장안에 넣지 않는다.
     - **후속 검증 항목(방안 B의 필요성):** A 는 일정 Agent 를 직접 부르므로 **메인 모델의 도구 선택·질문 재작성·쓰기 의도 판단을 재지 못한다.** 실제 사용자 경로(메인 → `ask_schedule`)에서 모호한 요청이나 인젝션이 쓰기로 이어지는지는 A 로는 검증되지 않으므로, A 의 첫 결과가 나온 뒤 메인 경로를 유지한 채 일정 Agent 응답을 관찰 훅으로 붙이는 방안 B 가 필요한지 판단한다(필요하면 별도 계획·승인). B 가 필요하다고 판단되기 전까지 메인 경로의 쓰기 성공·쓰기 의도 평가는 미검증으로 문서에 남긴다.
  2. **val·test 관리: 사례 본문은 저장소에 커밋하지 않고 저장소 밖 비공개 위치에 두는 것(방안 A)을 권장한다. 적용 범위는 아래로 한정한다.**
     - **저장소 밖 보관 적용 범위:** 신규 **val(18)·test(18) 사례 본문**(E5c 산출물)과 2·3단계에서 더하는 val·test 본문. 저장소에는 id 목록·건수·본문 파일의 sha256 만 둔다. 실행은 기존 `--split-file` 과 `runs_guard`(예약·해시 기록)를 쓰고, 해시 고정과 "기존 분할 파일을 고치지 않고 새 파일을 더한다"(ADR 0016)는 유지한다.
     - **적용하지 않는 것:** 개발셋(dev 36)과 기존 legacy 52건 본문(개발 루프의 입력이라 저장소에 둔다), 이미 커밋된 `scenarios_val.json`·`scenarios_test.json`(질문 서명·기대 행동 설명, 사례 **본문이 아님**, git 이력에서 지울 수 없고 이력 재작성은 force push 라 사용자 지시가 따로 필요하다), 결과 폴더(`.gitignore` 로 제외).
     - **작성자·실행자 분리 적용 범위:** (a) **test 본문**은 본문을 쓰는 사람과 개선안(프롬프트·도구 설명)을 만드는 쪽(개발 세션의 Claude Code 와 개선 후보를 제안하는 LLM)을 분리하고, 본문은 최종 평가 실행기만 읽는다. (b) **val 본문**은 루프 실행기만 읽고 개선안을 만드는 LLM 에는 주지 않는다(ADR 0016 의 현행 규칙). (c) 개발셋은 분리하지 않는다. 분리의 구체적 방법(누가 쓰는지, 어디에 두는지, 백업)은 사용자가 정한다.
     - Claude Code 읽기 거부 규칙은 사용자가 개인 설정 `.claude/settings.local.json` 에 **직접** 넣는 권장 사항이다(Claude Code 는 설정 파일을 고치지 않는다). 규칙이 `cat` 같은 Bash 경로를 막지 못하므로 보조 수단이다. `.gitignore` 에 val·test 본문 파일 이름 패턴과 `results*/` 를 더하는 것은 구현 작업이다(`.github/workflows` 는 건드리지 않는다).
     - 권장하지 않음: 암호화 후 커밋(의존성 추가가 필요하고 `CLAUDE.md` 의 임의 의존성 추가 금지와 충돌하며, CI 시크릿 방식은 `.github/workflows` 수정 금지와 충돌), 별도 비공개 저장소(저장소 생성은 계정·권한 작업이라 필요할 때 사용자가 결정).
     - **E5c(val·test 본문 36건 작성) 전에 위 구현을 끝낸다.** 본문을 쓰고 나서 옮기면 이력에 남는다.
  3. **가족 이름(PERSON): 현행(사전 점검이 PERSON 원문을 기록만 하고 실패로 세지 않음)을 임시 상태로 유지한다.** 최종 정책이 아니다.
     - 임시 유지의 근거는 ADR 0014 다: 외부 AI API 로 사용자 입력이 나가는 것은 설계 제약으로 삼지 않고 공지로 알리며 보호의 초점은 우리 DB 에 저장되는 내용이다. 평가가 운영과 다른 기준으로 실패를 정하면 운영이 정한 적 없는 규칙을 평가가 만들게 된다. 경로별 기록(메인 의도된 예외·정산 알려진 갭·소통·일정 정책 미준수 기록)은 그대로다.
     - **후속 결정 사항(미결, 사용자가 정한다):** (a) **경로별 허용 목록(방안 ③)을 도입할지**: 가명화를 문서로 선언한 경로(일정 Agent·주간 뉴스·타임라인·문서 업로드의 `[가족:id]` 치환, ADR 0012)에서 가족 이름 원문이 전송 본문에 나오면 사전 점검을 실패시키는 안. 소통 Agent 는 **도구 결과 본문의 원문만** 실패로 하고 사용자 질문에 쓴 이름은 기록만 하는 세분안을 함께 검토한다(운영의 `agent_guard.prepare` 는 질문에 형식 값만 가린다). (b) **운영 문서와 운영 동작의 불일치를 어떻게 해소할지**: 일정·뉴스·타임라인 문서는 가명화를 선언하지만 정산·메인·소통 질문은 원문으로 나간다. 정산·메인·소통 질문을 가명화할지, 아니면 문서를 운영 동작에 맞출지는 앱 담당과 정할 운영 정책이며 평가 PR 범위를 넘는다. 이 두 가지가 정해지기 전에는 방안 ③ 구현을 시작하지 않는다.
- 이유:
  - 일정 쓰기는 평가에서 가장 위험한 동작이라 "보안 위반이 없다"와 "쓰기가 맞게 된다"를 따로 재야 한다. 그러나 메인 경로에서는 일정 Agent 응답이 보이지 않아 완료·되묻기·거절을 가릴 수 없다(`runner.SCHEDULE_WRITE_REASON`). 평가 쪽 직접 경로는 운영 코드를 바꾸지 않고 DB 결과로 성공을 확인할 수 있는 가장 작은 방법이다. 다만 메인 경로의 쓰기 의도는 재지 못하는 한계가 있어 후속 검증 항목을 남겼다.
  - 테스트셋이 개선 PR 을 쓰는 사람과 Claude 에게 보이면 평가가 무의미해진다(ADR 0016 결과 절의 한계). 코드가 막는 것은 실수 방지 수준이라, 본문을 저장소에 두지 않는 것이 구조적으로 가장 단순하고 규칙 충돌이 없다. 적용 범위를 val·test 본문으로 한정한 것은 개발셋이 개발 루프의 입력이기 때문이다.
  - 가족 이름 원문 전송은 운영의 현재 정책이고(ADR 0014) 평가가 그와 다르게 실패를 정하면 평가가 운영 정책을 앞지르게 된다. 그래서 현행을 임시로 유지하고 정책 결정이 먼저다.
- 대안:
  - 일정 쓰기: **B(메인 경로 유지 + `AgentResponse` 관찰 훅)** 는 실제 경로에 가깝지만 운영 함수에 의존하고 승인 버튼을 시뮬레이션해야 한다(위 후속 검증 항목). **C(운영 응답에 결과 필드)** 는 가장 안정적이지만 `ask.py`·`rag_chat.py` 등 운영 코드와 OpenAPI 를 바꾼다.
  - val·test: 암호화 커밋, 별도 비공개 저장소, 읽기 거부 규칙만 쓰기(강제력이 개인 설정에 달림).
  - PERSON: ① 전 경로 실패(메인·정산이 설계상 원문이라 상시 실패해 점검이 무의미), ③ 경로별 허용 목록(후속 결정 사항), ④ 사례별 허용 플래그(스키마·사례 정답지 변경이 큼).
- 결과(승인 후 별도 작업으로, 각각 시작 전에 계획을 보여 주고 승인받는다):
  - 순서 제안: ① val·test 저장소 밖 보관 구현(E5c 전제) → ② 일정 쓰기 직접 경로(사례 스키마의 기대 DB 상태·`unsupported_reason` 분기·가짜 모델 L2 시험, 약 300~500줄) → ③ 방안 B 필요성 판단 → ④ PERSON 은 후속 결정 사항이 정해진 뒤.
  - 충돌 점검: ADR 0014(외부 전송은 설계 제약 아님) — 가족 이름은 현행 기록 전용을 유지하므로 충돌하지 않는다. ADR 0016(테스트셋 해시 고정·분할 파일 새로 더하기) — 본문만 저장소 밖으로 옮기고 해시·목록은 유지한다. ADR 0012(문서 가족 이름 치환) — 방안 ③ 도입 여부를 정한 뒤 점검한다. ADR 0009-local-first-db-workflow — 임시 SQLite 만 쓴다. `CLAUDE.md` — `.github/workflows` 수정·의존성 임의 추가·설정 파일 수정을 하지 않는다.
  - 한계: 직접 호출 평가는 메인 모델의 쓰기 의도를 재지 못한다. val·test 본문을 저장소 밖에 두면 CI 에서 그 분할의 시험을 돌릴 수 없고 분실 위험이 있어 보관 위치와 백업을 사용자가 정해야 한다. 이미 커밋된 val·test 목록은 이력에 남는다. 가족 이름 처리의 운영 불일치는 해소되지 않았다.
