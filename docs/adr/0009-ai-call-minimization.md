# 0009. 가족 채팅 AI 는 사용자가 요청할 때만 부르고, 한도·캐시·동시 실행 표시는 PostgreSQL 에 둔다

- 날짜: 2026-10-23
- 결정:
  - AI(Anthropic) 호출은 **일반 메시지 전송에서 절대 일어나지 않는다**. 구성원이 분석·답장·주제 추천을 눌렀을 때만 부른다. 자동 분석은 기본 꺼짐이며, 켜더라도 메시지마다가 아니라 시간·새 메시지 수 기준으로 모아서 한다(설계만, 아직 구현하지 않음).
  - 모든 AI 기능은 공통 관문 `app/shared/ai_guard.py` 의 `run` 하나를 거친다. 순서는 **동의 → 결과 캐시 → 키 확인 → 쿨다운 → 사용자·가족 그룹 하루 한도 → 가족 그룹 동시 실행 칸 → 사용 기록 선기록 → 호출 1번 → 결과·기록 저장**이다.
  - 한도·캐시·동시 실행 상태는 **PostgreSQL 테이블**(`ai_group_settings`, `ai_usage_logs`, `ai_result_cache`, `ai_inflight`)에 둔다. Redis 는 쓰지 않는다.
  - 결과 캐시 키에 **분석 범위의 첫·마지막 메시지 id 와 개수**를 넣는다. 범위에 새 메시지가 들어오면 키가 달라져 결과가 자동으로 새로 만들어지고, 같은 범위면 TTL 동안 AI 를 부르지 않는다. 캐시는 가족 그룹별로 격리한다.
  - **실패는 재시도하지 않는다.** 호출이 실패하면 503 `llm_failed` 로 끝내고, 이미 선기록한 사용 기록은 한도에 그대로 센다. 자동 재시도 루프는 두지 않는다.
  - **동의 모델**: AI 기능은 가족 그룹 단위로 **기본 꺼짐**이다. 가족 소유자 또는 관리자가 켜고 끈다. 동의하지 않은 그룹은 AI 를 한 번도 부르지 않는다.
  - 한 번의 분석 요청에서 요약·중요 메시지·일정 후보·할 일 후보를 **구조화 출력 호출 1번**으로 받는다. AI 가 만든 날짜·시간·담당자·메시지 번호는 서버가 검증해서 대화에 없는 값을 버린다. 일정·할 일은 후보이며 사용자가 확인해야 등록된다.
- 이유:
  - 대화는 개인 정보이고 호출은 돈이 든다. 일반 채팅마다 AI 를 부르면 비용과 개인정보 전송이 대화 양에 비례해 늘어난다. 호출 시점을 사용자 요청으로 제한하면 두 문제를 함께 줄일 수 있다.
  - 여러 워커(uvicorn 여러 프로세스, 배포 중 두 버전)가 같은 가족 그룹의 한도와 동시 실행을 세야 한다. 프로세스 메모리에 두면 워커마다 한도가 따로 놀아 실제 한도를 넘는다. 이미 모든 서버 상태가 PostgreSQL 에 있으므로(공용 DB 는 gabee 가 공유), 같은 DB 에 두면 새 인프라 없이 일관성을 얻는다.
  - 동시 실행 칸을 DB 유니크 키(`group_id`, `slot`)로 잡으면 두 요청이 동시에 와도 한쪽만 칸을 얻는다. 죽은 요청은 `started_at` 으로 120초 뒤 치운다.
  - 캐시 키를 "요청 내용"이 아니라 "분석 범위의 끝 id"로 만들면, 메시지가 추가되는 순간 자동으로 무효화된다. 시간 기반 캐시만 쓰면 새 메시지가 있어도 옛 결과가 TTL 동안 나온다.
  - 실패 재시도를 없애면 장애 때 한 요청이 여러 번 과금되거나 한도를 빠르게 소진하지 않는다.
  - 동의 기본값을 꺼짐으로 두면 구성원이 모르는 사이 대화가 외부 AI 로 나가는 일이 없다.
- 대안:
  - **Redis 로 한도·캐시·락 관리**: 빠르고 TTL 기능이 있지만, 이 프로젝트의 배포·운영 구성(Docker Compose, 공용 PostgreSQL)에 새 서비스를 추가해야 한다. 한도 기록과 사용량 분석을 SQL 로 보기도 어렵다. 가족 규모의 트래픽에서는 PostgreSQL 로 충분하다고 판단했다.
  - **프로세스 메모리 캐시·락**: 워커가 하나일 때만 맞다. 여러 워커에서 한도가 우회되므로 채택하지 않았다.
  - **메시지 전송 시 자동 분석**: 전송 응답을 늦추고 호출 수가 메시지 수에 비례한다. 채택하지 않았다.
  - **시간 기반 캐시만 사용**: 새 메시지가 있어도 TTL 동안 옛 결과를 보여 준다. 채택하지 않았다.
  - **실패 시 지수 백오프 재시도**: 일시 장애에는 유용하지만, 이 단계에서는 비용·한도 소진 위험이 더 크다고 봤다. 필요하면 나중에 사용자의 명시적 "다시 시도" 버튼으로 처리한다.
- 결과:
  - 일반 메시지 전송은 AI 호출 0을 보장한다(`ai_service` 가 전송 경로를 건드리지 않는다).
  - 한도는 PostgreSQL 기준이라 여러 워커에서도 같은 값으로 적용된다. 한도 초과는 429 `ai_daily_limit_user`/`ai_daily_limit_group`, 쿨다운은 429 `ai_cooldown`(Retry-After), 동시 실행 초과는 409 `ai_busy`.
  - 사용 기록(`ai_usage_logs`)에는 기능, 호출 수, 토큰, 캐시 적중, 상태, 오류 종류, 모델만 남기고 **대화 원문·문서 원문·API 키는 남기지 않는다**.
  - 한계: 캐시 결과(요약 JSON)는 TTL 동안 DB 에 남는다(원문은 아님). 쿨다운·한도 판정은 DB 조회 기반이라 요청마다 몇 번의 쿼리가 든다. 동시 실행 칸이 죽은 요청으로 120초 동안 잡힐 수 있다.
  - 자동 분석의 "마지막 분석 범위"를 기억하려면 나중에 `ai_group_settings` 에 컬럼을 더하는 Alembic 리비전이 필요하다(요구사항 문서 참고).
  - SQLite(로컬 개발)에서도 같은 코드가 돌지만, 여러 프로세스 간 일관성은 PostgreSQL 에서만 보장된다.
