# 0017. 채팅 공유 카드는 서버가 읽어 만든 보낸 시점 스냅샷이고, 글자는 고정 문구로 둔다

- 상태: 유효
- 날짜: 2026-11-10

## 배경
채팅방에서 내 일정 한 건과 내 정산 몫을 가족(또는 1:1 상대)에게 카드로 보낼 수 있어야 한다(요구사항 `docs/requirements/family-chat.md` "채팅방 공유 카드").
일정은 사람마다 자기 줄이 있고, 정산은 월 단위로 계산되며 제3자의 이름·금액이 섞여 있어서, 무엇을 어떻게 담을지가 개인정보와 위조 방지의 문제다.

## 결정
1. **내용은 서버가 읽어 만든다.** 클라이언트는 종류와 대상(일정 id·월)만 보내고, 제목·금액은 받지 않는다. 데이터 주인 기능(schedule·billing)이 자기 안에서 "내가 포함됨"을 확인해 내용을 만들고, family_chat 은 `app/shared/chat_share.py` 등록 구조로 부르기만 한다(다른 기능 내부 import 금지 규칙, `room_assistant`·`chat_library` 와 같은 방향). 만드는 함수가 없으면 보내지 않는다(503).
2. **보낸 시점 스냅샷이다.** `message_shares.payload` 에 복사해 두고, 원본을 고쳐도 카드는 바뀌지 않는다. 메시지를 지우면 payload 도 지운다. 메모는 담지 않고, 정산은 내 몫만(1:1 방에서는 그 상대와의 줄만) 담는다.
3. **메시지 글자는 개인정보 없는 고정 문구**("일정을 공유했어요")다. 새 테이블(`message_shares`)은 `message_attachments` 를 재사용하지 않는다(파일 경로·크기 NOT NULL 과 사진·파일 모음 집계에 섞이기 때문).
4. **새 테이블은 하위 기능으로 분리해 점검한다**(`shared/schema.py` `SUB_FEATURE_PREFIXES`: `message_shares` → `chat_share`). 공용 DB 에 리비전이 반영되기 전에도 소통 전체가 503 이 되지 않고 공유 카드 API 만 막힌다. 방·가족 삭제(`group_purge`)도 DB 에 실제로 없는 테이블은 건너뛴다(없는 테이블 때문에 삭제가 500 이 되지 않게).

## 결과
- 금액이 가족(또는 1:1 상대)에게 보인다는 점을 앱 확인창이 알려야 한다. @가비 가 카드를 참고하는 부분은 이어지는 PR 에서 구현한다(최근 대화 맥락 `room_context` 에 카드 요약을 더한다. 사용자가 금액까지 @가비 에 보이는 것을 승인했다).
- 구버전 앱은 고정 문구 말풍선만 보인다.
- 1:1 방 정산 카드의 `remaining` 은 내 전체 잔액이 아니라 그 상대와의 줄 합계다(카드 안에서 줄과 맞고 제3자와의 관계를 드러내지 않는다).
- `message_shares` 의 외래키는 ON DELETE CASCADE 이고, 공유 API 는 일정·정산 기능의 스키마 준비 상태도 확인한다.
- 알려진 후속: 카드 `payload` 는 아직 느슨한 객체(`dict`)로만 계약에 나온다. kind 별 타입 모델로 바꾸는 것은 후속 PR(앱 영향 있음).
