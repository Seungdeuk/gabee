# 0009. 개발은 각자 로컬 DB로 하고, 공용 DB는 통합 확인용으로 운영한다

- 날짜: 2026-10-23
- 결정: 5인 팀의 DB 작업을 아래처럼 나눈다.
  - **개발·마이그레이션 작성은 각자의 로컬 DB**(`docker compose`의 개인 Docker DB)에서 한다.
  - **공용 DB(`192.168.0.44:5432/gabee`)는 통합 확인용**이다. 병합된 `main` 을 한데 모아 보는 곳이고, 개인 기능의 중간 상태를 올리지 않는다.
  - 공용 DB 스키마는 **통합 때 DB 담당자가 Pull Agent 를 수동으로 한 번 실행**해서 반영한다. 에이전트의 5분 주기 **자동 적용은 끈다**(`agent.env` 의 `GABEE_AGENT_ENABLED=false`). 설치·백업·검증 코드는 그대로 둔다.
  - PR 단계의 CI(`api-postgres`: 단일 head·전체 upgrade·스키마 일치)는 **유지**한다.
- 이유: 멘토링에서 "각자 로컬 DB로 개발하고 통합 테스트 때 병합"하라는 조언을 받았다. 자동 적용을 운영해 보니 5인 팀에 비해 부담이 컸다. 같은 날 배포 도구·`config.py`·`pyproject.toml` 변경으로 에이전트가 세 번 `held` 가 되어 공용 DB PC(학원 공용 PC)에 직접 접속해 `bless` 해야 했고, 위험 변경 승인은 문구만 확인해 실제 승인 여부를 검증하지 못했다. 공용 PC 의 공용 계정·같은 디스크 백업 문제도 있다. 개발 중간 상태가 공용 DB 에 계속 쌓이는 것보다, 로컬에서 자유롭게 개발하고 통합 시점에만 한 번 안전하게 반영하는 쪽이 단순하다.

## 흐름

1. **개발(각자)**: 최신 `main` 에서 브랜치 → 로컬 DB 에서 모델 수정·`alembic revision --autogenerate`·리뷰·`alembic upgrade head`. 로컬에는 가짜 데이터만 쓴다.
2. **PR**: CI 가 단일 head·전체 upgrade·스키마 일치를 검증한다. 병합 직전에 최신 `main` 을 받아 `alembic heads` 가 1개인지 다시 확인한다(충돌하면 나중에 병합되는 쪽이 `down_revision` 을 옮긴다).
3. **통합(DB 담당자)**: 통합할 `main` 을 정해 팀에 알리고, 공용 DB PC 에서 에이전트를 수동으로 실행한다(dry-run 확인 → 적용). 새 백업·복원 검증·리허설·사후 검증은 그대로 거친다.
4. 위험한 변경(삭제·이름/타입 변경 등)은 PR 리뷰에서 DB 담당자가 사전 승인하고, 통합 때 담당자가 다시 확인한다.

## 영향

- 공용 DB 는 통합 전까지 `main` 보다 뒤처진다. 그 DB 에 붙은 서버는 아직 없는 스키마가 필요한 기능만 `503`(스키마 게이트, [0006](0006-schema-gate-degraded-start.md))이다. 개발은 로컬 DB 라 영향이 없다.
- 에이전트는 설치된 채로 **꺼져 있다**. 작업 스케줄러는 5분마다 돌지만 `disabled` 로 끝난다. 자동 적용을 다시 켜려면 `GABEE_AGENT_ENABLED=true`.
- 수동 실행에서도 배포 도구·신뢰 파일이 검토 기준과 다르면 `held` 로 멈춘다. 이때 담당자가 변경을 검토하고 `bless` 한다. 통합 때만 필요해 부담이 줄지만, 담당자의 공용 PC 접근은 여전히 필요하다.
- 백업은 공용 PC 의 마이그레이션 직전 백업(DB 와 같은 디스크)과, 개인 PC 에서 따로 받는 일일 덤프로 보완한다. 정기 백업은 이 저장소의 자동화가 아니라 각자 설정이다.
- [0007](0007-shared-db-auto-migration.md)·[0008](0008-shared-db-pull-agent.md)의 자동 적용 부분은 **중지**됐고, 배포 단계(CI 검증·위험 검사·백업·복원 검증·리허설·적용·사후 검증)와 보안 모델은 수동 실행에도 그대로 쓴다.

## 남는 과제

- 위험 변경 승인(`destructive-approved: PR #번호`)은 지금도 문구 형식만 확인한다. 통합 때 담당자가 직접 확인하는 것으로 대신하며, GitHub PR 승인 검증은 필요해지면 구현한다.
- 공용 DB 를 학원 공용 PC 밖(개인 서버·관리형 DB)으로 옮길지는 별도로 논의한다.
