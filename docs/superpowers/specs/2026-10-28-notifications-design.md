# 알림함 설계 (notifications)

- 날짜: 2026-10-28
- 상태: 설계 승인됨(채팅), 구현 전. 이 문서 검토 후 구현 계획으로 넘어간다.

## 목표

메인 화면(첫 탭, AI 채팅)에서 **지난 사건 기록**을 모아 보는 앱 안 알림함. 소통(가족 채팅) 메시지 알림은 제외하고, 일정·가계·돌봄·가족 그룹·AI 기록의 사건을 담는다. 알림마다 분류를 구분해서 보여 준다.

사용자가 정한 것:
- 형태: 앱 안 알림함(서버 저장, 읽음 표시). 폰 푸시는 이번 범위가 아니다.
- 성격: 지난 사건 기록 + 알림마다 분류 구분.
- 분류: 일정, 가계, 돌봄, 가족 그룹·AI 기록 모두.
- 대상: **그 데이터를 볼 수 있는 사람만** 받는다. 본인이 한 행동은 제외한다.
- 방식: 공용 알림 서비스를 만들고 각 기능이 사건 자리에서 호출한다.

## 범위 밖 (이번에 하지 않음)

- 폰 푸시 알림(`expo-notifications`, 푸시 토큰, 외부 푸시 서버 전송).
- 시간 기반 알림("정산 마감 임박", "구독 결제 예정"): 날짜가 되면 생기는 알림이라 주기 작업이 필요하다. 후속으로 미룬다.
- 소통(가족 채팅) 메시지 알림.
- 알림 설정(분류별 끄기), 알림 삭제.

## 1. 데이터

공용 코드 `apps/api/app/shared/notifications.py`(모델 + `notify()`), 라우터는 `apps/api/app/features/notifications/`.
다른 기능이 서로의 내부를 import하지 않고 `app/shared`만 쓰기 위해 모델과 `notify()`는 shared에 둔다.

테이블 `notifications` (Alembic expand 리비전만, 새 head 1개, 격리 PG16에서 검증):

| 컬럼 | 설명 |
|---|---|
| `id` | PK (기존 `_uid()` 방식과 같은 12자리 hex) |
| `user_id` | 받는 사람 (FK users) |
| `group_id` | 가족 그룹 (FK groups) |
| `kind` | 분류: `schedule` `billing` `care` `family_group` `ai_record` |
| `event` | 세부 종류 (예: `event_created`, `join_requested`) |
| `title` | 제목 (고정 템플릿 문구) |
| `body` | 한 줄 내용, 없을 수 있음 |
| `target_type`, `target_id` | 눌렀을 때 이동할 대상 (없을 수 있음) |
| `actor_user_id` | 행동한 사람, 없을 수 있음 |
| `created_at`, `read_at` | 생성 시각, 읽은 시각(NULL이면 안 읽음) |

- 한 사건 = 받는 사람마다 한 줄. 읽음 표시가 사람별로 독립이고, 조회는 "내 줄만"이라 권한 확인이 단순하다.
- 인덱스: `(user_id, created_at)`, `(user_id, read_at)`.
- `schema.py`의 `SHARED_MODEL_FEATURES`에 `notifications`를 알림 기능 하나만 쓰는 것으로 등록한다(없어도 다른 기능이 503이 되지 않게).

## 2. 기록 규칙 — `notify()`

`notify(db, *, group_id, kind, event, recipients, actor_user_id=None, title, body=None, target=None)`

- 받는 사람 목록은 **호출하는 기능이 정한다**. 이미 누가 볼 수 있는지 아는 쪽이기 때문이다.
  - 공유 일정: 가족 그룹 구성원 전체, 내 일정: 본인(이면 알림 없음)
  - 정산·돌봄: 기존 권한 안의 대상자
  - 가입 요청: 관리자(owner)
- `actor_user_id`는 받는 사람에서 자동으로 뺀다(본인 행동은 알림 없음).
- 받는 사람이 그룹 구성원인지 `notify()`가 한 번 더 확인한다(`ensure_group_member` 규칙과 일관). 아니면 건너뛴다.
- 문구는 **고정 템플릿**으로 짧게 쓴다. 금액, 위치, 건강 정보, AI 요약, 채팅 내용은 넣지 않는다("정산 요청이 왔어요" 수준). 일정 제목처럼 받는 사람이 이미 볼 수 있는 값만 허용한다.
- 알림 저장 실패가 원래 기능을 실패시키지 않게 격리한다(savepoint 안에서 저장하고 실패는 삼킨 뒤 로그에 사건 종류만 남긴다. 개인 데이터는 로그에 쓰지 않는다).

## 3. API (`features/notifications`)

| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | `/notifications` | 내 알림 목록. `kind` 필터, 최신순, 커서 방식 페이지 이동 |
| GET | `/notifications/unread-count` | 안 읽은 개수 (분류별 개수 포함) |
| POST | `/notifications/{id}/read` | 하나 읽음 처리 |
| POST | `/notifications/read-all` | 전부(또는 `kind`별) 읽음 처리 |

- 항상 `current_user` 기준으로 내 알림만 다룬다. 남의 알림 id는 404(존재 여부를 숨긴다). 그룹 id는 요청에서 받지 않는다.
- 구조는 `router.py → service.py → repository.py`, 요청·응답은 `schemas.py`. 라우터는 `main.py`에서 `schema_ready("notifications")`와 함께 등록한다.
- 서버 수정 후 `docs/contracts/openapi.json`을 스크립트로 재생성하고 `docs/contracts/db.md`를 갱신한다.

## 4. 앱

- 첫 탭(AI 채팅) 상단에 종 아이콘과 안 읽은 개수 배지. 누르면 `/notifications` 화면(`src/app/notifications.js`는 얇게, 로직은 `features/notifications/`).
- 알림마다 분류를 구분한다: 분류별 아이콘과 색(`theme/` 토큰)과 분류 이름 태그. 화면 위쪽에 분류 칩 필터. 안 읽은 알림은 굵게/점 표시.
- 알림을 누르면 읽음 처리되고 대상 화면으로 이동한다(일정 상세, 가족 요청 화면 등). 대상이 없으면 읽음만 처리한다.
- 개수는 앱을 열 때와 화면에 돌아올 때 다시 읽는다(폴링 없음).
- 서버 호출은 `features/notifications/api.js`에서만 한다. 다른 기능 내부 파일을 import하지 않는다.

## 5. 만드는 순서 (PR 나눔)

1. **1차 PR(서버 기반 + 우리 영역 연결 + 앱)**
   - 공용 테이블·Alembic·`notify()`·API·시험
   - 연결: 가족 그룹(가입 요청 → 관리자, 가입 승인 → 신청자). 거절은 신청자가 아직 구성원이 아니라 알림함에 남지 않아 제외, 구성원 변경·AI 기록 처리 완료는 호출 자리가 없거나 팀원 영역이라 2차로 미룬다(구현 계획 확정)
   - 앱 알림함(종 아이콘, 목록, 분류 구분, 읽음 처리)
2. **2차 PR(팀원 영역 연결)**: 일정(공유 일정 등록·수정·삭제, 함께 일정 요청·응답), 가계(정산 요청), 돌봄(실종 안내·위치 공유 시작). `notify()` 호출을 한 줄씩만 추가하며, 팀원 협의와 승인을 받은 자리만 건드린다. 가계·돌봄은 문구에 금액·위치를 넣지 않는다.

## 6. 보안·개인정보

- 알림 저장은 서버 DB 안에서만 한다. 외부 서비스(LLM, 푸시 서버)로 보내지 않는다.
- 알림 문구에 민감 정보를 넣지 않는다(위 2번).
- 사건이 생긴 뒤 권한이 사라진 사람(그룹 탈퇴 등)의 알림은 조회에서 `group_members` 기준으로 걸러 내거나 탈퇴 시 정리한다. 구현 계획에서 어느 쪽인지 확정한다.

## 7. 시험

- `notifications` 기능 `tests/`: 목록·필터·페이지 이동, 안 읽은 개수, 읽음 처리, 전부 읽음.
- 권한: 남의 알림 조회·읽음 처리 404, 비구성원에게는 알림이 생기지 않음, 본인 행동은 알림 없음.
- `notify()` 실패 격리(알림 저장이 실패해도 원래 요청은 성공).
- 연결 지점별 시험: 가입 요청 → 관리자에게만 알림 생성.
- Alembic: 단일 head, 격리 PG16에서 upgrade/스키마 일치 검증.
- 앱: `npm run lint`, 알림 분류·이동 규칙 단위 시험, 개수 배지.
- 실기기 확인은 하지 못한 것으로 보고한다.

## 열린 질문

- 가입 요청 등 가족 그룹 이벤트의 정확한 종류 목록은 구현 계획에서 현재 서비스 코드를 읽고 확정한다.
- 알림 보관 기간(예: 90일 후 정리)은 이번에 정하지 않고 필요할 때 추가한다.
