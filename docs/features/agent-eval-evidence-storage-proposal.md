# 재채점 증거 보존 개선안 (제안 — 구현하지 않음, 2026-11-19)

> 목적: 평가 결과를 다시 채점할 때 **저장된 답변이 500자에서 잘려** 판정이 달라지는 문제(예: dev108 `chat-03` r2, 옛 사례 재채점 90 vs 공식 91)를 막는다. 개인정보 보호 정책을 지키는 범위 안에서만 증거를 늘린다. **이 문서는 설계 제안이며 코드·저장 형식·기존 결과를 바꾸지 않는다.** 구현은 별도 PR 과 별도 승인으로 한다.
> 승인하지 않는 방식: 실제 민감 원문·인증정보·가족 실데이터를 새 로그·결과 파일에 저장하는 것.

## 1. 문제

- `store.py` 는 답변을 `scrub_text`(개인정보·비밀값 제거)로 **먼저 지운 다음 앞 500자(`ANSWER_MAX`)만** 저장한다(`store.py:297`).
- 채점 기준을 바꿔 재채점할 때, 판정 근거 문구가 500자 뒤에 있으면 다시 채점해도 그 문구를 못 본다. 현재 `rescore.py` 는 저장된 답이 `ANSWER_MAX` 이상(`len(answer) >= 500`, `rescore.py:183`)이면 `answer_truncated` 한계를 붙이고 원래 판정을 유지한다(정확히 500자인 온전한 답도 절단으로 보는 보수적 판정이다). 그러나 **판정이 달라질 수 있는 행인지 아닌지**는 알 수 없다.
- 원본 답변을 그대로 더 길게 저장하면 해결되지만, 답변에는 도구 결과에서 온 이름·일정 같은 값이 들어갈 수 있어 보호 정책과 충돌할 여지가 있다.

## 2. 설계 원칙

1. **새로 저장하는 값은 기존 `scrub_text` 를 거친 값만** 쓴다(지운 다음에 저장). 거치지 않은 원문 저장 금지.
2. 평가 월드(`w1`~`w3`)는 합성 데이터(가짜 이름·가짜 번호)다. 그래도 **합성이 아닌 데이터가 섞인 실행은 증거 확장 대상에서 제외**한다(아래 3-B 의 안전장치).
3. 결과 폴더는 지금처럼 Git 에 올리지 않는다(`.gitignore`), 로컬에서만 보관한다. 보관 기간과 삭제 방법을 문서에 적는다.
4. 증거를 늘리는 것은 **채점 가능성**을 위한 것이다. 점수를 올리거나 과거 판정을 바꾸는 데는 쓰지 않는다(재채점은 항상 별도 폴더·별도 채점기 버전).

## 3. 제안(단계별, 위에서부터 채택)

### 3-A. 절단 사실과 지문을 항상 남긴다 (민감정보 추가 저장 없음) — 권장, 가장 먼저

- 각 답변 기록에 `answer_len`(지운 뒤 전체 글자 수), `answer_truncated`(참/거짓), `answer_sha256`(지운 뒤 전체 글의 해시)를 더한다.
- 재채점기는 `answer_truncated` 가 참인 행을 **"증거 부족(재판정 불가)"** 으로 따로 세고, 점수 비교 표에서 별도 칸으로 표시한다(지금은 한계 문구 한 줄뿐).
- 효과: 어떤 행이 500자 때문에 비교 불가인지 **정확히** 알 수 있다. 원문은 더 저장하지 않는다.

### 3-B. 채점 단서(criteria evidence)를 실행 시점에 저장한다 (원문 없이)

- 실행 직후 **공식 채점기**가 계산한 결과를 항목별로 저장한다: 사례의 각 조건(`contains`/`contains_any` 묶음, `not_contains`, 금지 문자열)마다 `matched`(참/거짓)와 **어느 묶음이 맞았는지의 번호**만 저장한다. 맞은 글귀 자체는 저장하지 않는다.
- 실행 시점에 한 번 더, 사례 파일의 **다음 버전 후보 기준**(예: v2)으로도 같은 판정을 계산해 `shadow_verdicts` 로 함께 저장할 수 있다(채점기 버전 번호와 함께). 이렇게 하면 같은 실행을 기준 두 가지로 채점한 결과가 원문 없이 남는다.
- 한계: 실행 때 알고 있던 기준만 반영된다. 나중에 전혀 새로운 기준을 만들면 3-C 가 필요하다.

### 3-C. 합성 월드 한정 확장 저장 (명시 동의가 있을 때만)

- 환경변수(예: `GABEE_EVAL_STORE_FULL_ANSWER=1`)와 **월드 합성 표지**(`synthetic: true`)가 **둘 다** 있을 때만(현재 `scenarios_meta.json` 의 월드 항목에는 "합성 월드"라는 서술만 있고 이 필드는 없다. 3-C 를 구현할 때 `w1`~`w3` 에 필드를 추가하고 변경 이력·해시를 새로 기록해야 한다) `ANSWER_MAX` 대신 더 긴 상한(예: 4000자, 모델 출력 상한 안)을 쓴다.
- 합성 표지가 없거나 `legacy` 분할이면 켜지지 않고 500자 그대로다(조용히 무시하지 않고 사전 점검(`--preflight`)에서 거부한다).
- 저장 전 `scrub_text` 로 이름·전화번호·주소·계좌·이메일·키 형태 문자열을 지운다. **지운 뒤에도** 키·토큰 형태가 남으면(`sk-…` 등 탐지 정규식) 그 행의 확장 저장을 막고 500자로 되돌린다.
- 보관: 결과 폴더는 로컬 전용. 기본 보관 90일을 문서에 적고, 삭제는 폴더 통째로 한다(결과 읽기 도구는 삭제를 하지 않는다).

## 4. 시험 계획 (구현 시 함께)

- 3-A: 500자 초과/이하 답변의 `answer_truncated`·`answer_len`·`answer_sha256` 값, 재채점기가 절단 행을 "증거 부족"으로 따로 세는지, 기존 결과(필드 없음)를 읽어도 깨지지 않는지(하위 호환).
- 3-B: 항목별 `matched` 만 저장되고 맞은 문구가 저장 파일 어디에도 없는지(문자열 검색 시험), 채점기 버전이 기록되는지.
- 3-C: 환경변수만 있고 합성 표지가 없을 때 거부, 합성 표지만 있고 환경변수가 없을 때 500자 유지, 키 형태 문자열이 남으면 되돌림, 이름·번호가 지워져 저장되는지.
- 공통: 기존 `real-dev-x3-b1~b4` 결과 폴더와 `_rescore` 폴더를 **열기만** 하고 바꾸지 않음(읽기 전용 시험).

## 5. 비용·영향

- 3-A/3-B: 결과 파일 크기 증가는 행당 수십 바이트 수준. 실모델 호출·비용 없음.
- 3-C: 행당 최대 약 4 KB, dev 108 행 기준 약 0.4 MB.
- 기존 결과·공식 점수 91/108 은 바뀌지 않는다. 새 필드는 새 실행부터 붙는다.

## 6. 결정이 필요한 것 (제안, 확정 아님)

1. 3-A 만 먼저 할지, 3-B 까지 같이 할지.
2. 3-C 를 도입할지(합성 월드 한정이라도 원문 성격의 값을 더 오래 두는 것이므로 팀 승인 필요).
3. 보관 기간(제안 90일)과 삭제 책임자.
