# Main Agent 과잉 라우팅 후속 설계 메모 (#542 종료, 2026-11-26)

> 설계 기록만 남긴다. 이번에는 구현하지 않는다. #542 는 병합하지 않고 후속 과제로 보존한다(추가 프롬프트 수정·국소 실모델 재평가 없음).

## 1. 문제: Over-routing
- 출처가 하나로 정해지는 질문에서 메인이 다른 담당 Agent 까지 함께 부른다. 관측: 기준선 0/54 → b669a036 7/54 → addac7c9 국소 2/12(chat-02) → 7c0a1ac9 국소 1/6(chat-02 r0).
- 형태: 소통 결과를 본 뒤의 보충이 아니라 **첫 모델 호출에서의 동시 호출**(`ask_family_chat`+`ask_schedule`). 넘김 질문에 사용자가 말하지 않은 출처('가족 공동 할 일 목록'·'일정 탭')가 붙는다.
- 영향: 호출 수·토큰·지연·비용 증가, Tool Precision 하락. 방에서는 일정 Agent 가 끼며 권한 경계에 의존하게 된다(현재는 #543 서버 필터가 막아 노출 0, 그 전에는 `scope_leak` 발생).

## 2. 프롬프트 기반 도구 선택의 확률적 한계
- #535·#542 의 문장은 같은 질문에 서로 다른 답을 주는 규칙(가족방 보조 단서 ↔ '불분명한 할 일은 둘 다')을 정리해 빈도를 줄였지만(2/6 → 1/6) 0 으로 만들지 못했다. 문장 추가는 다른 사례로 번지는 위험(chat-02 r0 의 `missing_tool` 회귀)이 있고 3회 반복으로는 1/6 과 0/6 을 통계적으로 가르기 어렵다.
- 결론: 라우팅의 **안전·범위 조건**은 프롬프트가 아니라 서버의 결정론적 경로로 옮기고, 프롬프트는 모호한 경우의 판단만 맡긴다.

## 3. Hybrid Routing (제안 구조)
1. **결정론적 1차 판정**: 채널(personal/family/direct), 질문에 명시된 출처 표현, 이전 턴 상태로 "허용 담당 집합"을 만든다.
2. **모델 2차 선택**: 메인은 허용 집합 안에서만 도구를 고른다(도구 목록 자체를 줄여 보낸다).
3. **실행 게이트**: 모델이 허용 집합 밖의 도구를 요청하면 서버가 실행하지 않고 기록한다(관찰 지표로 남김).

## 4. Intent / Source Classification
- 출력: `source ∈ {chat_history, family_todo, schedule_tab, billing_ledger, knowledge_docs, unclear}`, `compound: bool`.
- 1안(우선): 규칙·사전 기반(명시 표현: "일정 탭", "채팅에서", "장부", "올린 문서" 등 일반 표현 사전 + 채널). 새 LLM 호출 없음, 재현 가능, 비용 0.
- 2안: 경량 분류 모델(로컬 small 급). 규칙으로 `unclear` 인 경우만. 운영 CPU·지연 예산 안에서 평가 후 결정.
- 평가 질문 문장·특정 낱말(예: 장보기) 하드코딩은 금지한다(일반화 시험으로 막는다).

## 5. 서버 기반 Tool Allowlist 및 실행 게이트
- 위치 후보: `ai_assistant/agents.call` 직전(이미 1:1 방에서 일정 도구를 막는 지점이 있다).
- 규칙 예: 가족방 + source=chat_history|family_todo → `ask_schedule` 제외. source=schedule_tab → `ask_family_chat` 제외. compound=true → 명시된 영역의 담당만 허용.
- 게이트가 막은 호출은 모델에 "이 질문에는 이 담당을 쓰지 않는다"는 도구 결과로 돌려주고, 평가에서는 `blocked_tool` 로 따로 센다.

## 6. 명시적 복합 요청과 불확실한 의도
- 명시적 복합("지출이랑 할 일을 같이")은 언급된 영역 각각을 허용한다(compound-03 유지).
- `unclear` 는 현재 #535 정책(개인 채팅의 불분명한 할 일 → 소통·일정 둘 다)을 그대로 두고, 가족방에서는 소통만 허용한다. 개인 채팅의 모호한 일반 질문은 좁히지 않는다.

## 7. 잘못된 차단으로 인한 Recall 저하 방지
- 차단은 "명시된 출처와 충돌하는 담당"에만 적용하고, 판정이 `unclear` 면 막지 않는다(fail-open 은 라우팅에만, 권한은 기존대로 fail-closed).
- 지표: Tool Recall·필수 복합 호출 누락(combo_miss)·`blocked_tool` 중 정답 도구 비율을 함께 본다. 차단 도입 전후를 같은 사례·같은 채점으로 비교하고, 필수 도구를 막은 사례가 1건이라도 있으면 규칙을 되돌린다.
- 그림자 모드 먼저: 실제로 막지 않고 "막았을 호출"만 기록해 오차단률을 측정한 뒤 적용한다.

## 8. 진행 조건(향후)
- 별도 요구사항 문서·승인 후 착수. 결정론적 시험(L0·L2)과 그림자 모드 측정 → 국소 실모델 평가 순서. #542 의 합격 기준·미충족 판정은 바꾸지 않는다.
