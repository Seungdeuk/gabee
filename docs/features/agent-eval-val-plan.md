# val 18건 준비 계획 (2026-11-19, 계획 문서 — 실제 호출·val 실행 없음)

> 이 문서는 val(검증) 단계의 준비 상태와 작업 계획이다. val 정답 기준은 **모델 출력을 보기 전에** 정하고, val 결과를 본 뒤에는 기준을 바꾸지 않는다. 아래 사례별 표는 이미 존재하던 시나리오 목록(`data/scenarios_val.json`, 어떤 val 실행보다 먼저 작성됨)의 `expected_behavior` 에서만 옮긴 **초안**이며, w2 월드의 구체 값(금액·날짜·제목)은 월드 데이터가 확정된 뒤 채운다.

## 3. 정답지 누출·중복 방지

- **모델에 정답지가 가는가**: 실행기는 모델 요청을 사례의 `question`·`setup`(질문자·방·대화 이력)으로만 만들고(`runner.py` 의 입구 함수들), `expect` 는 채점(`scoring`)·보안 판정·가짜 전송 점검에서만 읽는다(`adapter.py`·`runner.py` 에서 `.expect` 를 읽는 곳은 채점과 사례별 금지 문자열 보정뿐이다). 다만 이를 직접 고정하는 시험은 없어서 WP5 에서 추가한다.
- **val 과 test 의 분리**: 월드를 분할별로 격리한다(dev=w1, val=w2, test=w3, `scenarios.WORLD_OF_SPLIT`). 질문 문장·`target_key` 가 분할 사이에 겹치지 않는지를 L0 시험으로 고정한다(현재는 겹침 없음).
- **사후 조정 금지**: 승인서에 `cases_val.json` 해시·`criteria_v2` 해시·프롬프트 해시·`SCORER_VERSION` 을 적고, val 실행 뒤에 이 중 하나가 바뀌면 그 val 결과는 무효로 표시한다. 기준 개선은 val 을 열기 **전에** dev 에서 `rescore` 로 먼저 확인한다(평가 기준 v2 문서 참고).
- **dev 에서 배운 오탐 방지**: val 사례는 처음부터 같은 값의 다른 표기(날짜·시각)와 같은 뜻의 표현 묶음을 쓰고, 미래형 안내와 완료 단정을 구분하며, 거절 묶음은 해당 제한을 직접 말하는 문구를 요구한다.

## 5. 비용과 실행 계획(추정, 실행은 별도 승인)

- 18건 × 3회 = 54 case-run. 한 번에 최대 10건·반복 3 제한 때문에 **9건 × 3회 × 2배치**다.
- dev 108 case-run 평균 $0.00329 를 쓰면 약 $0.18, 안전 여유 25%를 두면 약 $0.22. 배치별 사전 거부 기준값은 dev 배치(약 $0.35~0.38)와 비슷하게 나오리라 보며 배치마다 `--preflight` 로 확정한다.
- 신규 평가 지출 상한 $0.80 중 남은 한도는 $0.4446354(dev 108 실행 후). val 2배치는 '남은 한도 승인' 규칙(배치 k 승인 금액 = 남은 한도 − 앞선 실제 지출, 단 거부 기준값 이상)으로 수행할 수 있다. 상한을 더 늘리지 않는다.
- 전역 비용 집계(`GABEE_EVAL_EXTRA_RESULTS_ROOTS`)로 모든 작업 폴더의 누적을 합쳐 확인한다.

## 6. 결정이 필요한 사항

1. w2 월드 규모: dev w1 과 같은 규모로 만들지(약 1~2일 분량의 데이터 작성·검증), 시나리오가 쓰는 데이터만 담은 작은 월드로 만들지.
2. 평가 기준 v2 를 val 전에 공식 기준으로 채택할지(채택하면 새 dev 기준선 실행이 필요).
3. 서비스 정책 결정(도구 실패 때 대체 계산, 모호한 삭제 요청 처리, "오늘 할 일"의 의미)을 val 전에 정할지, val 에서는 해당 사례를 정직한 안내만 보도록 둘지.
